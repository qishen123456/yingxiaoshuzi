# 营销智能推送项目汇报稿

> 建议时长：2–3 分钟。面向开发总监与运营同学。

大家下午好，我简要汇报一下营销智能推送项目的设计思路、当前进度和下一步安排。

**这个项目要解决的核心问题，是把营销圈人从固定页面、人工反复筛选，逐步变成数据驱动、规则可配置、过程可复核的工作流。**

整体链路可以用五步概括：**数据准备、标签字典、产品规则、人群与频控、触达与复盘。**

首先，上游的房屋标签和线索数据进入系统，经过同步和标准化，形成可供规则使用的房屋标签数据。第二，标签类别和值由数据库字典维护。这样新增标签时，原则上只需要维护字典和数据接入，不需要每次都改前端。第三，运营可以针对不同产品分别设置必选条件、加分条件和优先级，用同一套规则口径配置和对比产品。第四，在推送前先确定城市和项目范围，再进行人群筛选、号码去重和频控。最后，系统需要记录执行结果，并关联后续线索，用于效果复盘。

这套设计有三个原则。

第一，**标签数据和页面解耦**。标签类别与可选值通过字典提供，前端负责搜索和选择；但如果新增的是上游从未接入过的物理字段，仍然需要补数据同步映射，不能只在字典里加一条记录。

第二，**规则交给业务配置**。不同产品的必选、加分和优先级独立维护，减少为每次策略调整修改页面的成本，也方便运营横向比较。

第三，**范围先收敛，执行有控制**。定时推送先选择城市，默认包含该城市项目，需要时再缩小到具体项目；正式触达还必须经过去重、频控和执行状态检查。

当前进度上，前端交互方案已经调整，产品规则对比、标签类别浏览与搜索、城市优先的项目选择和项目流程说明已提交。后端也提交了标签值表模型及动态标签、项目目录接口代码。这里需要明确，目前属于代码提交和原型验证阶段，数据库迁移、后端构建、真实数据联调和生产发送链路还没有完成验收。

下一步建议先由研发和数据团队完成数据库迁移、接口构建和真实字段映射，再用固定批次对账产品命中数、号码去重与频控结果；运营侧同步确认产品规则口径、城市项目范围和小流量验收标准。待这些结果验证通过后，再推进真实定时调度和触达闭环。

**我的总结是：这阶段先把配置方式和业务流程设计清楚，下一阶段以数据准确性和真实执行链路验证为重点，确保系统不只是能配置，还能可靠地执行、留痕和复盘。**

谢谢。
