## 0. 设计寄存器与三轴刻度（先定边界，再动手）

| 判定项 | 结论 | 依据 |
|---|---|---|
| 设计寄存器 | **Product 寄存器**（设计服务产品） | 路径形态为 `/app/*` `/task/*` `/settings/*`，主体是表格、表单、规则配置器。标杆是"赢得熟悉感"，不是"独特性" |
| 平台正交轴 | **web**（企业内部 PC 端为主） | 用户原话"PC 端办公使用"，非 C 端、非原生 App |
| DESIGN_VARIANCE | **3**（可预测） | 内部工具要可学习、可批量操作。禁止非对称 Hero、禁止破网格。固定 12 列栅格 |
| MOTION_INTENSITY | **2**（近静态） | 仅保留状态传达动效（hover/展开/Toast/Modal），150ms 收敛值。无入场编排、无脉冲微动画 |
| VISUAL_DENSITY | **7**（偏驾驶舱） | 表格行高 36–44px，卡片内边距 16px，节区间距 24px。用 1px 分割线 + 负空间分组，不用通用卡片盒子堆叠 |

**Product 寄存器带来的硬约束**（后续所有设计动作的标杆）：

- 调色板默认 Restrained —— 中性色 70–85%，品牌色 5–8%，语义色 0–5%，效果色 <1%
- 字体一族够用，固定 rem 阶梯，步进比 1.125–1.2
- **Dashboard 上禁止 Serif 展示字体**
- 每个交互组件必须全状态：default / hover / focus / active / disabled / loading / error / empty / success
- 动效 150–250ms，传递状态而非装饰，无页面加载编排
- 设计失败模式不是"平淡"，而是**无目的的奇怪**：装饰过度的按钮、不匹配的表单控件、无功能的动效

## 1. 设计调研结论（5 个竞品/同类产品界面）

> 全部为实际检索到的产品文档与规范，逐条给出「借鉴点」与「规避点」。

### 1.1 神策数据 CDP — 标签管理与人群圈选

**实际界面特征**（来源：神策分析帮助中心「标签」「人群筛选特征模板管理」）：

- 「标签管理」列表页 → 右上角「创建标签」→ 进入创建页，创建方式多选（自定义标签值 / 基础指标值 / 首次末次特征）
- 规则圈选交互：点「添加规则」→ 选择规则类型（属性 / 事件 / 分群 / 函数 / 行为序列）→ 已添加多条规则时可「添加嵌套规则」，新规则与当前规则建立 且/或 关系，并作为一个规则组合，再与其他规则形成 且/或 关系
- 已添加规则支持三种行内操作：**设置规则间逻辑关系（且/或）、拖动顺序、复制规则**
- 存在「规则组逻辑关系」配置，用于配置多个规则组之间的交并差
- 「人群筛选特征模板」把筛选项沉淀为模板：**特征组**（可命名，如"用户基础信息""近期消费情况"，支持拖拽属性/标签进组）+ **排除人群**（引用已存在分群做反向剔除）
- 字符串/集合类型字段可设「平铺值」（常用城市直接勾选，其余搜索选取）；数值类型字段可选「使用区间」或「保持为离散数字」
- 硬限制：单项目最多 500 个标签；单标签最多 24 个标签值；最多 20 个模板

**借鉴点**：
1. 「特征组」= 可命名分组容器 + 拖拽入组 —— 这是标签映射互斥组交互的直接原型
2. 规则行内三操作（逻辑关系 / 拖动顺序 / 复制）—— 拖动排序已被验证是营销/运营人员能接受的优先级表达
3. 「排除人群」反向剔除 —— 我们的互斥组需要同样的"反向排除"心智
4. 模板化沉淀（配一次，多处分群复用）—— 与本项目"营销管理配一次规则，系统自动推人推品"的产品逻辑完全同构

**规避点**：
- 神策的嵌套规则可无限层级（规则 → 规则组 → 规则组），对总部营销管理岗是灾难 —— 营销人员不是数据工程师，看到的"且/或/交并差"越多越不敢点「发布」。**我们限制嵌套最多 2 层**（互斥组 → 组内条件），组间不提供交并差选择器，固定为优先级顺序 + 互斥。
- 500 个标签的展示若无分组会变成一堵墙 —— 我们必须提供「按标签类目折叠 + 搜索 + 最近使用」三件套。

### 1.2 HubSpot Workflows — if/then 条件分支

**实际界面特征**（来源：HubSpot Knowledge Base「Use if/then branches in workflows」）：

- 分支基于「单一属性值」或「匹配过滤器条件」两类；可在面板中「为每个值创建独立分支」
- 支持 AND/OR 逻辑；**单次 if/then 分支动作最多 20 个分支**
- 关键心智模型（原文）："注册的记录会**按分支堆叠的顺序**逐个评估。如果联系人满足第一个分支的条件，它会沿该分支继续。该联系人**不会**再针对其他分支进行评估，即使它满足其他分支的条件。"
- 官方建议："由于每次注册只走一条分支路径，**建议让分支条件彼此唯一且不重叠**"
- 提供 Test workflow 模拟运行 + history tab 验证路径 + Event logs（每个动作、时间戳、决策可查）
- 官方列出的常见错误：注册时数据缺失、无理由的 delay、重复造近似分支而非嵌套、忽略重新注册逻辑

**借鉴点**：
1. **"自上而下按堆叠顺序评估，命中即停"是一套已被数百万营销人员理解的语言** —— 我们的优先级模型直接采用它，不需要发明新概念（Product 寄存器的"熟悉感"）
2. 「建议条件唯一且不重叠」= 我们把这句话变成系统能力：**发布前预检自动检测重叠/不可达规则**，而不是只写在帮助文档里
3. Test workflow + Event logs —— 对应本项目的「规则预检模拟」与「操作日志」两个必做模块

**规避点**：
- HubSpot 是画布式（canvas）节点连线。对只有 4 段流程、规则数是几十条量级的内部系统，画布会造成**大面积空白 + 节点漂移 + 小屏不可用**。我们改用**垂直堆叠的规则卡片列表**（Linear issue list 的心智），更省空间、更易批量扫读、天然支持拖动排序。

### 1.3 企业微信 SCRM 群发 — 频控、记录与止损

**实际界面特征**（来源：企业微信官方群发规则说明 + 第三方 SCRM 后台文档）：

- 频控是**管理员在后台/手机端统一设定的硬上限**，三档语义：「每日可接收 1 条」「每周可接收 7 条」「每月可接收条数为当月天数」，超出则发送失败
- 规则刷新时机有明确定义：每周规则**每周一 0 点刷新**，每月规则按当月天数计算 —— 界面上必须能解释"什么时候重置"
- **系统自动把当天已发送的客户从名单剔除** —— 硬上限兜底，从机制上杜绝对同一人反复轰炸
- 群发筛选支持「成员 / 标签 / 添加时间」三条件，且支持「**剔除标签**」（反向排除，例：发给黄金+钻石标签，剔除互联网行业）
- 「频率限制」选项：剔除掉 X 天前已经群发过的客户，按自然天计算
- 群发记录支持按**创建人 / 类型 / 时间**筛选；有「停止发送」入口作为发错内容后的最后一道补救（未发送的成员不再继续发送）
- 状态机：未发送 / 发送中 / 已发送 / 草稿 / 发送失败
- 部分渠道还有"成员人工确认后才真正送达"的防骚扰设计

**借鉴点**：
1. **状态机命名直接对齐**：待推送 / 推送中 / 已推送 / 部分失败 / 失败 / 已拦截 / 草稿。用户在不同系统间迁移零学习成本
2. **「拦截」必须是表格里的可见结果，不是静默丢弃** —— 我们的推送记录表必须有独立的「拦截(频控)」数字列，否则用户会以为系统没推
3. **「停止发送」是系统层确定性能力，「撤回已送达」物理不可行 —— 两者必须拆开** —— 企微的中止窗口来自"成员需人工确认才送达"这一链路特性，不是通用能力；短信一旦送达**不可召回**。架构已裁定：**停止发送**（停未下发 + 在途尽力）由本系统实现，**P0 必做**；**撤回已送达**不做，且界面文案不得出现任何暗示可撤回的表述（见 §8.3.1）
4. 剔除标签 + X 天内已触达剔除 = 我们的频控策略需要提供「跨渠道合并计数」与「回看窗口」两个可配项

**规避点**：
- 三档频控（日/周/月）在界面上若表现为三行独立输入框，用户无法判断"到底哪个先生效"。我们必须在规则行内用一句自然语言复述真实语义（如"同一客户 7 天内最多接收 2 条短信"），并在冲突时按**更严格者优先**显式提示。
- 官方后台把频控藏在「客户与上下游 → 客户联系 → 群发工具」四级菜单里 —— 本项目频控是"防翻车"的一等公民，必须是侧边导航一级项。

### 1.4 Airtable — 条件筛选与条件组

**实际界面特征**（来源：Airtable Support「Filtering records using conditions」+ 用户实测教程）：

- 条件**读起来像一个句子**：`Field – Operator – Value`，例如"Show me the records where the DRI is Jordan Peretz"
- Operator 下拉项**由字段类型决定**：文本字段给 contains / does not contain / is empty；数字字段给 is greater than / is less than；关联字段给 is exactly / has any of / has all of / has none of
- 条件之间默认 AND，**点一下 "And" 即可切换为 OR**
- `+ Add condition group` 支持嵌套条件组，表达 `(A AND B) OR (C AND D)`
- **重排条件：条件行最右侧有六点手柄图标**，悬停时光标变成手型，可拖动到目标位置
- 「隐藏字段」按视图独立配置：一个视图只显示 5–8 个字段，其余隐藏；字段顺序可拖动，最常用的放最左
- 官方建议：命名要表达意图（`[Audience] [Purpose]`），动态日期（this week / next month / the past 30 days）替代硬编码日期

**借鉴点**：
1. **条件句式（字段–操作符–值）是三段式下拉，学习成本最低** —— 标签映射条件行直接采用，但值选择用"可搜索多选 + 常用值平铺"
2. **六点手柄 = 拖动排序的通用视觉符号** —— 优先级拖动用同一个符号，用户照搬肌肉记忆
3. **操作符按字段类型动态变化** —— 避免给日期标签展示 "包含" 这种无意义选项
4. **相对时间替代绝对日期**（"近 30 天""本季度"）—— 每日 T+1 生成人群包，规则里的时间条件必须是相对的，否则规则次日就失效
5. **按需隐藏列** —— 推送记录表 12 列必然溢出，必须提供「列设置」

**规避点**：
- Airtable 是通用表格，条件是"技术用户玩具"，可无限叠加。我们的规则编辑器**必须对每条条件行做语义校验**（标签是否已下线、产品包是否已下架），而不是只在保存时报错。

### 1.5 Dify / Coze 规则引擎 — 优先级与互斥

**实际界面特征**（来源：Dify 工作流实战资料与配置文档）：

- 优先级配置在可视化控制台的 Workflow 模块 → Edit Tools → **拖动工具卡片调整顺序，位置越靠前优先级越高**，保存后按新优先级重排执行路径
- 执行策略字段 `execution_policy: first_match_only` —— 多个工具可触发时**仅执行列表中最靠前的那个**，避免重复处理
- 另有「手动设定优先级数值 0–100」+「基于置信度自动选择最高匹配项」的数值化方案
- **「互斥组」用于防止并发执行**（原文明确提到互斥组防并发）
- 意图冲突处理实践：业务操作类意图（如退款、下单）优先级 > 问题反馈 > 普通咨询，靠"在路由节点前加一个仲裁节点"实现
- **模拟运行 + 触发日志分析面板**：记录触发时间戳与会话 ID、匹配路径（规则 or LLM）、各条件命中状态、置信度分数
- 多条件分支设计的官方陷阱清单：未显式定义优先级时系统可能按字典序执行分支；宽泛条件置于具体条件之前会导致后续分支永不命中（**死规则**）；缺少互斥逻辑时多个分支被同时激活

**借鉴点**：
1. **`first_match_only` 是本项目的核心算法心智**，必须在规则配置页顶部用一句人话显式声明，不能只留在代码里
2. **「拖动即优先级」+「互斥组防冲突」是同一套工程界已验证的解法** —— 直接采纳
3. **模拟运行面板 + 命中状态逐条回显** —— 对应我们的「预检」与「命中预览」，预检结果要能指出具体是哪条规则、哪个条件导致的问题
4. 官方陷阱清单直接变成了我们的**预检规则库**：重复条件、重叠条件、被前置规则完全覆盖的死规则、缺失标签值

**规避点**：
- **绝不把 `priority: 100` 这类数值暴露给营销管理岗**。数字优先级在规则数超过 10 条后完全无法维护（插入一条新规则要么改一堆数字，要么出现并列）。我们用"序号 01/02/03 + 拖动"表达，序号是拖动的结果而非输入。
- **绝不暴露"置信度分数""匹配路径"这类工程概念**。日志页面记录这些字段供排查，但不进入主界面文案。
- 画布连线（node + edge）在规则条目多时必然变成"意面图"。用卡片堆叠 + 分组容器替代。

### 1.6 调研横向结论

| 维度 | 行业现状 | 我们的决策 |
|---|---|---|
| 优先级表达 | 拖动排序（Airtable / Dify）与数值输入（Dify 高级模式）并存 | **拖动排序为主 + 序号徽章回显**，不提供数值输入 |
| 互斥表达 | 分组容器（神策特征组）/ 互斥组配置（Dify） | **分组容器 + 组头徽章**，不画连线、不用侧边条纹 |
| 冲突提示 | 多在文档里写"建议不要重叠"（HubSpot） | **升级为系统能力**：发布前预检 + Error/Warning 双档 + 定位跳转 |
| 命中预览 | 模拟运行是独立入口（Dify / HubSpot test） | **升级为常驻同屏面板**，编辑即刷新（debounce 800ms），不跳转 |
| 记录型页面 | 状态机 + 多条件筛选（企微 SCRM） | 对齐命名 + 增加「拦截(频控)」独立列 + 三段微条 |
| 风险提示 | 硬上限静默兜底（企微） | **前置为可视化**：保存前强制展示影响面 + 偏松阈值风险横幅 + 一键改推荐值 |
| 止损 | 停止发送（企微，因其"人工确认才送达"而天然存在中止窗口） | **两个能力拆开**：「停止发送」（系统层，P0，已实现 `POST /push-tasks/{id}/halt`）**必做**；「撤回已送达」（通道层，物理不可行）**不做、界面不明示**（见 §8.3.1） |

## 2. 对标品牌与设计语言

### 2.1 主对标：**Linear**

借鉴：
- **信息密度与"工具感"的克制美学** —— Linear 的列表行在 40px 内塞进状态图标、标题、标签、负责人、时间，且不显拥挤。这正是本项目推送记录表要的密度
- **`1px` 边框 + 极轻阴影的层级表达** —— 层级靠边框色差（`--border` / `--border-strong`）而非投影堆叠；阴影只授予浮层（Dropdown / Modal / Toast）
- **行内操作不常驻** —— 只在 hover 时出现，避免每行右端三四个文字按钮造成的视觉噪音（企业后台最常见的毛病）
- **键盘优先** —— 全流程可键盘完成，focus ring 显著且统一
- **规避**：Linear 的深色主题与偏冷的中性色不适合长时间白天办公的中文后台；我们采用浅色主题 + 中性色微调（见 §3）

### 2.2 主对标：**Ant Design / Ant Design Pro**（企业后台事实标准）

借鉴其**已形成肌肉记忆的组件行为契约**（这是 Product 寄存器"熟悉感"的最大来源）：
- `PageHeader`：面包屑 + 标题 + 描述 + 右侧主操作，Tab 切换不影响页面级按钮位置
- `ProTable`：行选择 + 分页 + 排序 + 列筛选 + 密度切换
- `FooterToolbar`：**勾选行后底部悬浮批量操作条**（左「已选 N 项」+ 右操作按钮）
- `Drawer`：详情/编辑走右侧抽屉（宽 560–600px），而非跳页或弹窗
- `Popconfirm` / `Modal.confirm`：**所有删除类操作必须二次确认**；破坏性操作需高安全级别验证
- `ModalForm`：表单项 > 6 时两列布局宽 800px，≤ 6 时单列宽 400px
- 空状态：列表无数据或无搜索结果时**必须**展示空状态（引导文案 + 操作按钮）
- 结果反馈：成功 `message.success`，失败 `message.error('操作失败：xx')` **必须告知具体原因**；异步操作必须有 Loading，禁止界面"假死"

**规避**：
- 不沿用其默认圆角（2px）、默认蓝（`#1677ff`）、默认字号（14px/22px）造成的"泛用感"；全部换成本文 §3 的自有 Token
- 不使用其 `border-left: 3px` 类强调式卡片 —— 这是 AI 味设计的典型特征（见 §3.5 禁则）

### 2.3 主对标：**Stripe Dashboard**

借鉴：
- **数字的排版处理** —— 所有金额/数量用 `font-variant-numeric: tabular-nums` + 右对齐 + 千分位，列内数字能垂直对齐成一条线。这是"专业数据界面"与"网页表格"的分水岭
- **状态徽章 = 图标 + 文字 + 语义色底**，不使用纯色圆点（色盲不可辨）
- **微条（Microbar）表达比例** —— 成功/失败/拦截用一段堆叠条，比三个数字更快被扫读
- **筛选的渐进披露** —— 默认只展示 2–3 个常用筛选条件，其余收进「更多筛选」，避免筛选区占据半屏

### 2.4 补充参考（非对标，只借单个模式）

- **HubSpot Workflows**：借「自上而下评估，命中即停」的顺序心智模型
- **Airtable**：借条件句式（字段–操作符–值）与六点手柄拖动符号
- **企业微信管理后台 / SCRM**：借状态机命名与频控硬上限的语义

## 3. 设计原则（内部工具型后台）

### P1. 密度优先，扫描优先（Scan > Scroll）

一屏内给出做决策所需的全部信息。禁止把"命中多少人""拦截多少人"这类关键数字藏进二级页或 tooltip。表格默认紧凑密度（行高 36–44px），页面级节区间距 24px（远小于营销页的 80px）。

### P2. 编辑与反馈同屏（Edit-With-Preview）

规则编辑区与命中人数预览**不分离**。用户在拖动一条规则、勾一个标签的同一屏内就能看到人数变化。所有把"预览"做成独立按钮的设计一律否决。

### P3. 破坏性操作先暴露影响面（Impact-Before-Confirm）

二次确认必须说清「影响多少人、哪些批次、什么时候发生」，而不是"确定吗？"。
- 重推确认 Modal 必须含：受影响人数 / 去重后人数 / 是否受频控拦截的预估 / 预计送达时间
- 频控设置保存前必须展示影响面预估
- 高风险操作（批量重推 > 阈值、关闭频控）需要输入批次号后段或勾选确认项

### P4. 状态永远三件套（Icon + Text + Color）

状态标识 = 图标 + 文字 + 语义色，**三者缺一不可**。禁止仅靠颜色传达含义（色盲不可辨），禁止纯色圆点，禁止只有 emoji 或只有色块。

### P5. 用系统已有的语言，不发明新交互（Restrained Novelty）

优先级 = 拖动排序 + 序号（Airtable / Dify 已验证）；删除 = 二次确认（AntD 契约）；批量 = 底部悬浮操作条（FooterToolbar 契约）；详情 = 右侧抽屉（560px 契约）。
新交互只在旧交互明确不足时引入，且必须能在键盘上完成。

### P6. 克制装饰（Zero Decoration Tax）

无渐变主视觉、无毛玻璃、无抽象几何装饰、无入场动画编排。动效仅用于传达状态变化，150ms 收敛值。任何"为了让界面好看一点"而增加的视觉元素都是成本。

### P7. 权限与影响范围可见

总部营销管理岗与大区/营业部人员看到的是不同范围的数据与操作。权限差异必须在 UI 上显式可读（按钮禁用 + 原因 tooltip：`当前账号无「发布规则」权限`），不能让用户点了才发现失败——这是 ERP 类系统的灵魂（见行业规范：不要忽视权限体系的 UI 表达）。

### P8. 不提供不生效的配置项（No Dead Controls）

界面上不出现"看起来能配、实际会引发不一致或根本不起作用"的旋钮。

上一版我在频控表单里画了 `回看窗口（重复触达剔除）[ 3 ] 天` 的输入控件。它看起来无害，实则是**伪配置项**：产品包冷却期可配到 180 天，而用户配的统一窗口只有 3 天或 30 天时会盖不住长冷却期，导致**长冷却期静默失效、同一产品包被重复推送**——不报错、不告警、界面上也看不出来。这类错误是"防翻车功能自己翻车"，比功能缺失严重得多。

**可操作的判断方法（结论 → 方法）**

判断一个字段该做成 **输入控件** 还是 **只读说明**，问一句话：

> **用户改了这个值，系统行为会不会随之产生一致且可预期的变化？**

- **会** → 做成输入控件
- **不会**（被别的参数盖住、需要系统推导、改了也不生效）→ 做成**只读说明**，数值由系统回传
- **用户改了会诱导出错误期待**（例如"渲染了开关但后端没实现"）→ **连只读说明都不要给**，直接不出现

**这条方法的关键区分是"只读说明 vs 输入控件"**：

> **只读说明不会诱导用户去改，输入框会。**

具体落到三个档位：

| 档位 | 处理 | 本项目实例 |
|---|---|---|
| 用户可安全配置 | **输入控件** | 房屋冷却期、日/周/月上限、可发送时段、全局日上限、**线索静默期（同包冷却 / 跨包冷却）**、**线索异常降级策略（`fail-open` / `fail-closed`）** |
| 系统推导 / 不可配置，但需要解释 | **只读说明**（一行，`--muted`，配 Tooltip 说明为什么） | `回看窗口 max 30 天（由各维度自动推导，不可配置）`、`系统按每批 500 条、间隔 5 分钟分批下发（内部常数，不可配置）`、**`归因窗口 15 天（默认值，快照回显）`**（契约暂无配置端点，见 §8.4-H） |
| 能力不存在 / 不生效 | **完全不出现** | `channelRecall` 开关（通道未确认支持撤回 API）、`mutex_group.mode` 切换器（契约只有 `single`）、`dayType` / `holidaySkip` 在 P0 阶段的控件形态、**`归因窗口` 输入控件**（契约未提供配置字段/端点前不渲染） |

**保留只读说明不是装饰**：运营看到"全局日上限 5,000 条"时必然会问"那这 5,000 条多久发完"，一行只读说明（约 25 分钟）直接回答它。区别在于——**这一行不会诱导用户去点，输入框会。**

**P8 在本轮补充需求上的第二次应用（重要，防止后来人重蹈覆辙）**：PRD §12.5 要求"归因窗口默认 15 天、可配（短信/企微可分别设）"，但 **`openapi.yaml` 中并不存在归因窗口的配置字段或端点**（只有 `LeadRecord.attributionWindowDays` 这个**回填快照**，以及 `AttributionRun.windowDays` 这个**运行记录**，两者都不是配置源）。因此按 P8 判据——"用户改了这个值，系统行为会不会随之产生一致且可预期的变化？"——**当前答案是"不会"**（没有字段可写）。处理：**做成只读说明**（`归因窗口 15 天`，team-lead 裁决默认值 15 天），并在 §11 记为 Q13（**已裁决：只读保持、默认 15 天**）。**绝不**画一个"归因窗口 [15] 天"的输入框——那正是上一轮 `lookback_days` 的翻版：配了不生效，还会让运营以为调大窗口能"归因更多线索"，实际归因作业并不读它。

**反面清单（本项目已按此清理过的死控件）**：`lookback_days` 输入框、`分批节流` 输入框、`单批次触达上限` 输入框、`mutex 模式` 切换器、`day_type` 分日配置入口（降为 P1 收起态）、`channelRecall` 开关（不渲染）、**`归因窗口` 输入框（契约无字段，改为只读，见 §8.4-H 与 Q13）**。

## 4. 配色体系（Design Token · 四层架构）

### 4.1 为什么不用被禁的紫粉渐变

- **寄存器判据**：Product 寄存器默认 Restrained 调色板。紫→粉渐变（Indigo 系紫 → Pink 系粉的跨色相渐变）+ 发光边框 + 毛玻璃的三位一体是 Brand 寄存器营销页的做法，出现在保险/房屋责任盘的内部业务后台会直接损害可信感——行业规范原文："不要用紫色/粉色渐变做 ERP（企业用户会觉得不专业）"。
- **业务判据**：本系统的核心视觉信息是"人数 / 状态 / 拦截量"。渐变会让语义色（红/绿/琥珀）与主视觉抢夺注意力，直接破坏 P4（状态三件套）的可读性。
- **替代方案**：主色用**单一纯色墨钢蓝**（`#1D5A96`）承担品牌与主操作，层级靠中性色阶与 1px 边框表达，色彩预算全部留给状态语义。

### 4.2 A1-Identity（品牌核心）

| Token | 值 | 角色 | 对比度 |
|---|---|---|---|
| `--bg` | `#F5F7FA` | 页面背景（冷调浅灰，非纯白，长时间办公不刺眼） | — |
| `--surface` | `#FFFFFF` | 卡片 / 表格 / 表单容器 | — |
| `--surface-sunken` | `#EEF1F5` | 表头 / 只读区 / 内嵌区块 | — |
| `--fg` | `#131A22` | 主文本（带冷调近黑，不用纯黑 `#000`） | 15.9:1 on `--bg` 通过 |
| `--muted` | `#5B6675` | 次级文本 / 说明 / 表头 | 5.8:1 on white 通过 |
| `--primary` | `#1D5A96` | 品牌主色：主按钮 / 当前导航 / 关键数字 | 7.1:1 通过 |
| `--border` | `#DFE4EA` | 默认边框 / 表格分割线 | — |
| `--border-strong` | `#C7CFD8` | 输入框边框 / 强调分割 | — |

**主色阶（A1-identity 扩展）**

```
--primary-50:  #F1F6FB
--primary-100: #E1EBF5
--primary-200: #C7DCEB
--primary-300: #9EBFDA
--primary-400: #5C93BE
--primary-500: #2B6FAE
--primary-600: #1D5A96   ← 基准值（= --primary）
--primary-700: #17497B   ← hover
--primary-800: #123A61
--primary-900: #0C2745
```

选用"墨钢蓝"而非 Tailwind 默认 Indigo / Blue-600 的原因：后者在 2024–2026 的中后台模板中被过度使用，已成"一眼 AI/一眼模板"信号。`#1D5A96` 饱和度更低、明度更深，是保险/金融行业可信色的合规区间，同时在白底上仍有 7.1:1 对比度。

### 4.3 A2-Semantic（语义色）

| Token | 值 | 底色 Token | 用途 | 对比度 |
|---|---|---|---|---|
| `--success` | `#0F7A48` | `--success-bg: #E8F5EE` | 已推送 / 成功 / 通过 | 5.4:1 通过 |
| `--warn` | `#B4530A` | `--warn-bg: #FDF3E3` | 部分失败 / 待审批 / 频控预警 / 草稿 | 5.0:1（底色上 4.6:1）通过 |
| `--danger` | `#B3261E` | `--danger-bg: #FBEDEC` | 失败 / 破坏性操作 / 阻断级错误 | 6.6:1 通过 |
| `--info` | `#1D5A96` | `--info-bg: #E1EBF5` | 提示 / 进行中（复用主色） | 7.1:1 通过 |

语义色刻意**取深色变体**（如 danger 用 `#B3261E` 而非流行但对比不足的 `#DC2626`），保证作为 12px 小字文本时仍满足 AA。

### 4.3.1 线索与闸门 0 状态色（本轮新增 · 全部复用既有 Token，不新增色值）

线索联动模块**不引入任何新色值**，全部由 §4.3 语义色映射而来，保证"每屏强调色 ≤ 2 处"与"语义色 0–5%"两条纪律不被打破。

| 状态 | 契约枚举 | 语义色 | 底色 Token | 图标（Lucide） |
|---|---|---|---|---|
| 无线索 | `gateStatus=clear` 且无 `lastLeadAt` | `--muted`（中性） | `--surface-sunken` | `user-round-search` |
| 有线索 · 静默期内 | `lead_package_cooldown` / `lead_house_cooldown` | `--warn` | `--warn-bg` | `shield-off` |
| 线索超期（已出静默期） | `clear` 且有 `lastLeadAt` | `--info` | `--info-bg` | `circle-check` |
| 线索数据不可用 | `data_unavailable` | `--danger` | `--danger-bg` | `triangle-alert` |

**关键纪律**：`data_unavailable`（线索数据缺失/过期）**必须用 `--danger`**，因为它是"防打扰闸门已失效"的异常态，而不是中性提示——架构 §8 明确要求 fail-open 时"显著标注 + 告警"，若用中性灰会让运营误以为"当前没有线索，一切正常"。

**线索质量等级色（A/B/C/无效）**

| 等级 | 含义 | 语义色 | 底色 Token |
|---|---|---|---|
| A 高意向（有效） | 已预约/已报价/已确认需求 | `--success` | `--success-bg` |
| B 意向（有效） | 主动留资并咨询 | `--success` | `--success-bg` |
| C 弱意向（待培育） | 仅留联系方式、无互动 | `--warn` | `--warn-bg` |
| 无效 | 空号/非本人/明确拒绝/重复 | `--muted` | `--surface-sunken` |

- **A 与 B 同为 `--success`，靠文字区分而非新增色相**——`--success` 表达"计入有效线索率"，A/B 的差异由徽章文字（`A 高意向` / `B 意向`）承担，避免为 4 个等级引入 4 个色相而挤占语义色预算。这与 P4"状态三件套"一致：区分靠**文字**，颜色只表达"有效 / 待培育 / 无效"三档语义。
- **`--meta`（3.1:1）禁止用于线索等级文字**——等级是高价值业务信息，必须用 `--success` / `--warn` / `--muted` 这些达 AA 的色。

|---|---|---|

### 4.6 色彩使用纪律

- **中性色 70–85%**：背景、边框、正文、分割线
- **品牌色 5–8%**：主按钮、当前导航项、选中行、关键数字
- **语义色 0–5%**：仅状态徽章、错误文本、风险横幅
- **效果色 <1%**：聚焦环、浮层阴影
- **每屏可见 `--primary` 使用 ≤ 2 处**（多则形成视觉噪音）。反例：把所有标题都染成蓝色
- **标题永远用中性色**（`--fg`），不用品牌色
- 深色模式不在 MVP 范围（内部白天办公场景），但 Token 结构已预留（用亮度递进替代阴影：`#F5F7FA → #EEF1F5 → #DFE4EA`）

## 5. 字体方案

### 5.1 字体选择过程（不是拍脑袋）

**三个品牌声音词**（物理对象）：
1. **精算表** —— 一列列数字必须能对齐成一条线
2. **仪表盘刻度板** —— 冷静、精确、无情绪
3. **保单条款** —— 内容密、可逐条核对、不含糊

**直觉首选的三个字体及其否决理由**：
- `Space Grotesk` —— 字符独特性强，但它有"科技创业公司官网"的味道，出现在保险业务后台是**错位**（否决）
- `DM Sans` —— 圆润几何感与"精算表"的冷硬气质相反，且是被 AI 工具过量使用的字体（否决）
- `Playfair Display` —— Product 寄存器明确规定 **Dashboard 上 Serif 展示字体严格禁止**（否决）

**最终选择**：单一无衬线字族（Inter）+ 中文回退链 + 等宽字族。Product 寄存器"单一字族靠字重差建立层级"是正解——后台不需要字体表演。

### 5.2 字体栈

```css
/* A1-identity */
--font-sans: "Inter", "PingFang SC", "Microsoft YaHei", "Noto Sans SC",
             system-ui, -apple-system, "Segoe UI", sans-serif;
--font-mono: "JetBrains Mono", "SFMono-Regular", Consolas, "PingFang SC", monospace;

/* 数字专用（表格、KPI、命中人数） */
--font-num: "Inter", "SFMono-Regular", "PingFang SC", monospace;
```

**为什么把 PingFang SC 放在 Noto Sans SC 之前**：内部企业环境为 macOS + Windows 混合，`PingFang SC`（macOS）与 `Microsoft YaHei`（Windows）是本机字体，零网络请求、字形质量最佳；`Noto Sans SC` 作为 Web Font 兜底，仅在前两者缺失时加载。这样既满足"必须指定 Inter + Noto Sans SC + 等宽"，又不为内部系统引入不必要的字体加载成本。

```css
/* 需要时按需引入，display=swap 避免阻塞 */
@import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600&family=Noto+Sans+SC:wght@400;500&family=JetBrains+Mono:wght@400;500&display=swap');
```

### 5.3 字号阶梯（8 级，固定 rem，步进比 1.14–1.20）

| Token | px | rem | 行高 | 字重 | 用途 |
|---|---|---|---|---|---|
| `--text-xs` | 12 | 0.75 | 1.40 | 400 / 510 | 徽章、辅助说明、表格脚注 |
| `--text-sm` | 13 | 0.8125 | 1.45 | 400 / 510 | **表格单元格、表头、表单辅助文字（默认密度）** |
| `--text-base` | 14 | 0.875 | 1.55 | 400 | **正文、表单值、卡片描述（系统默认字号）** |
| `--text-md` | 16 | 1.0 | 1.55 | 400 / 510 | 段落正文、抽屉标题 |
| `--text-lg` | 18 | 1.125 | 1.40 | 510 | 区块小标题、卡片标题 |
| `--text-xl` | 20 | 1.25 | 1.35 | 590 | 页面内一级小节标题 |
| `--text-2xl` | 24 | 1.5 | 1.30 | 590 | 页面标题（PageHeader） |
| `--text-3xl` | 30 | 1.875 | 1.25 | 590 | 命中人数等 KPI 大数字（唯一使用场景） |

**基准字号定为 14px**（而非营销页的 16px）：内部后台信息密度高，13px 表格 + 14px 正文是中文后台可读性与密度的最佳平衡点。正文永不小于 12px。

### 5.4 字重三级体系

| 级别 | 字重 | 用途 |
|---|---|---|
| Read | 400 | 正文、表格单元格、说明文字 |
| Emphasize | 510 | 表头、按钮文字、徽章、小标题、标签 |
| Announce | 590 | 页面标题、KPI 大数字、Modal 标题 |

只加载 400 / 500 / 600 三个字重（映射到 400 / 510 / 590 语义），控制体积。

### 5.5 字距规则

| 场景 | 字距 | 理由 |
|---|---|---|
| 正文（13–16px） | `0` | 中文正文不需要额外字距 |
| 表格小字 / 标签 / 徽章（11–13px） | `0.01em` | 小字补一点呼吸感 |
| 全大写英文（状态码、规则编码、`ALL CAPS`） | **`0.06em`** | 强制规则，全大写必须拉开 |
| 页面标题（≥20px） | `-0.01em` | 大字收紧 |
| KPI 大数字（30px） | `-0.02em` | 大字收紧 |
| 中文标题 | `0` 或 `-0.01em` | 中文不需要西文那种负字距 |

### 5.6 数字排版纪律（本项目最关键的一条排版规则）

```css
.num, td.num, .kpi-value, .badge-count {
  font-variant-numeric: tabular-nums;
  font-feature-settings: "tnum" 1;
}
```

所有人数、条数、百分比、时间、编号一律使用等宽数字 + 千分位分隔 + 右对齐（表格列）。**这是"专业数据界面"的第一道门槛**：比例字体下 `1,248` 与 `9,830` 宽度不同，整列数字会呈锯齿状，用户无法用眼睛做纵向比较。

## 6. 间距、圆角与阴影规范

### 6.1 间距（4px 基准网格）

```
--space-0:  0
--space-1:  4px    /* 图标与文字、徽章内边距 */
--space-2:  8px    /* 同组元素、行内按钮间距 */
--space-3:  12px   /* 表单元素间距、卡片内元素间距 */
--space-4:  16px   /* 卡片内边距（默认）、表格单元格左右内边距 */
--space-5:  20px   /* 区块内模块间距 */
--space-6:  24px   /* 区块间距、页面栅格 gutter */
--space-8:  32px   /* 大区块间距 */
--space-10: 40px   /* 页面级留白 */
--space-12: 48px   /* 抽屉/弹窗内部大分段 */
--space-16: 64px   /* 仅登录页等极少数场景 */
```

**禁止**非标值：`5 / 7 / 13 / 15 / 22 / 30`。

### 6.2 节区节奏（内部系统专用，远小于营销页）

| 断点 | 节区纵向间距 | 说明 |
|---|---|---|
| 桌面（≥1280px） | `--space-6` = 24px | 内部工具，信息紧凑 |
| 平板（768–1279px） | `--space-4` = 16px | — |
| 手机（<768px） | `--space-3` = 12px | MVP 不重点保障 |

对照说明：营销页的标准是 80/48/32px，本项目采用 24/16/12px，因为后台的"节区"是表单分组而非内容板块。

### 6.3 圆角阶梯（上限 8px，杜绝过度圆滑）

```
--radius-xs:   2px     /* 表格内联小标记 */
--radius-sm:   4px     /* 徽章、标签、小按钮 */
--radius-md:   6px     /* 按钮、输入框、下拉框（默认交互控件） */
--radius-lg:   8px     /* 卡片、面板、表格容器（硬上限） */
--radius-xl:  12px     /* Modal、Drawer、Toast */
--radius-full: 9999px  /* 头像、数字徽章圆点 */
```

**卡片圆角硬上限 8px**。超过 24px 会立刻产生"AI 生成"的过度圆滑感，本项目直接封在 8px。

### 6.4 阴影层级（三级 + 浮层）

```css
/* A2-structure */
--elev-flat:    none;                     /* 表格内元素、扁平区块 */
--elev-ring:    0 0 0 1px var(--border);  /* 卡片默认：1px 边框环，无投影 */
--elev-raised:  0 1px 2px rgba(19,26,34,.06),
                0 4px 12px rgba(19,26,34,.06);   /* Dropdown / Popover / Tooltip */
--elev-overlay: 0 12px 32px rgba(19,26,34,.16);  /* Modal / Drawer / Toast */
```

**核心纪律：禁止「1px 边框 + blur ≥16px 阴影」同时出现在同一元素**（幽灵卡片）。卡片默认只用 `--elev-ring`；需要浮起时改用 `--elev-raised` 并去掉边框环。

### 6.5 层级 z-index

```
--z-base:     0
--z-sticky:   100     /* 吸顶表头、吸底批量操作条 */
--z-drawer:   900
--z-dropdown: 1000
--z-modal:    1200
--z-toast:    1300
```

## 7. 图标系统

### 7.1 候选图标库（2 个主候选 + 1 个备选）

> 本阶段只给候选与取舍，**最终锁定由架构师在 Spec 中确认一套**，全项目统一、不混用。

#### 候选 A：**Lucide**（推荐）

| 维度 | 评估 |
|---|---|
| 规模 | 1500+ 图标，仍在增长 |
| 网格 / 描边 | 统一 24px 网格，默认 `stroke-width: 2`，纯描边线性风格 |
| 授权 | ISC（MIT 等价，可商用） |
| 技术 | `lucide-react` / `lucide-vue-next` / `lucide-static`，按需 tree-shaking，单图标 < 1KB |
| 生态 | 与 shadcn/ui、Radix 生态天然对齐；React/Vue/Svelte/原生都有官方包 |
| 覆盖度 | 通用后台语义完备：`filter` `list-filter` `send` `history` `ban` `shield-alert` `users` `tags` `layout-list` `grip-vertical` `circle-alert` |

**优点**：体积小、风格统一、三档尺寸（16/20/24）映射干净、社区活跃。
**取舍**：偏"通用现代"，缺少本项目的行业专有语义（"责任盘""人群包""频控拦截"）。解决方式：用**组合**（`users` + `layers` = 人群包）或用**项目自定义 SVG 图标**补齐 3–5 个业务图标，自定义图标必须严格遵循同一网格与描边宽度。

#### 候选 B：**Phosphor Icons**

| 维度 | 评估 |
|---|---|
| 规模 | 9000+（含变体），常规图标 1500+ |
| 变体 | **6 个字重**：thin / light / regular / bold / fill / duotone |
| 网格 / 描边 | 24px 网格，regular 权重描边约 1.5，另有 16px 优化网格 |
| 授权 | MIT |
| 技术 | `@phosphor-icons/react` / `@phosphor-icons/vue`，支持 tree-shaking 与 React Context |

**优点**：`fill` 变体天然适合表达"选中/激活"状态（导航项选中用 fill、未选中用 regular），状态表达力强于 Lucide；图标覆盖度更广，冷门语义基本都有。
**取舍**：6 个字重是双刃剑——团队若不设纪律，很容易在同一界面混用 thin 与 bold 造成风格碎裂；包体积大于 Lucide；`duotone` 变体与"克制装饰"原则冲突，本项目**禁用 duotone**。

#### 备选 C：Tabler Icons

5700+ 图标，24px 网格，`stroke-width: 2`，MIT。可作为 Lucide 的等价替代（两者风格极为接近）。列出仅作为风险备份：若架构师的技术栈已有 Tabler 依赖，可直接沿用，不必引入新包。

### 7.2 取舍与建议

| 判据 | Lucide | Phosphor |
|---|---|---|
| 体积优先（内部系统，首屏性能） | **胜** | 略大 |
| 状态表达（选中/未选中的强区分） | 需换图标 | **胜（fill / regular 配对）** |
| 风格统一风险 | **低（单一风格）** | 中（6 字重需纪律） |
| 业务冷门语义覆盖 | 需补 3–5 个自定义 | **覆盖更全** |

**我建议选 Lucide**，理由：
1. 本项目是 Product 寄存器内部工具，图标的作用是**语义传达**而非状态表演，"选中态用背景色 + 左侧 3px 指示条"已经足够，不需要 fill 变体
2. 单一风格把"风格碎裂"的风险归零，符合 P6 克制装饰
3. 体积小对本项目"表格 + 大量行内图标"的渲染量是关键优势
4. 若导航选中态确实需要更强的视觉区分，用 `--primary-subtle-bg` 背景 + 字重 510 即可解决，不必升级图标库

**若架构师选择 Phosphor**：必须在 Spec 中写死纪律——"全项目只允许 regular 与 fill 两个变体，禁用 thin / light / bold / duotone"，否则风格一定失控。

### 7.3 尺寸与描边规范（尺寸由 team-lead 定义，此处补充工艺细节）

| 尺寸 | 使用场景 | 描边宽度 |
|---|---|---|
| **16px** | 行内（表格单元格内、徽章内、按钮文字左侧、输入框内前后置） | `1.75`（比 24px 略细，保持视觉重量一致） |
| **20px** | 按钮内（独立按钮）、工具条、Tab 标签、面包屑分隔 | `1.75` |
| **24px** | 侧边导航、页面级独立图标、空状态插图 | `2` |

**纪律**：
- 颜色一律 `currentColor`，继承文本色；语义图标用对应语义色
- 全项目 `stroke-linecap: round`、`stroke-linejoin: round`，禁止混用方头
- 同一界面禁止混用不同描边宽度
- 图标必须 `aria-hidden="true"`（装饰性）或配 `aria-label`（唯一语义载体，如纯图标按钮）
- **纯图标按钮必须有 `aria-label` + Tooltip**

### 7.4 绝对禁令

- **禁止使用任何 emoji 作为功能图标**（火箭、图表、星光、靶心一类的符号字一律禁止）。所有图标来自锁定的单一 SVG 图标库
- **设计中不出现任何 emoji 字符**。emoji 仅允许出现在 UGC 内容中（如用户上传的海报文案、客户备注），绝不进入 UI chrome
- 禁止图标 + 文字语义重复导致冗余（如 `filter` 图标旁写"筛选筛选"）

### 7.5 线索联动模块图标（本轮新增 · 沿用 Lucide，同一套库不混用）

| 语义 | 图标（Lucide） | 尺寸 |
|---|---|---|
| 线索事件（时间线上的线索节点） | `user-round-plus` | 16px |
| 推送事件（时间线上的触达节点） | `send` | 16px |
| 有线索 / 已关联 | `link` | 16px |
| 命中线索静默期（闸门 0 拦截） | `shield-off` | 16px（与明细 `suppressed` 同图标，强调"这是同一类主动保护"） |
| 线索数据不可用（降级态） | `triangle-alert` | 16px |
| 首触归因 | `circle-dot` | 16px（窗口内最早一次触达） |
| 末触归因 | `flag` | 16px（窗口内最近一次触达） |
| 效果看板（一级导航） | `chart-column` | 24px |
| 有效线索率 | `percent` | 16px |
| 归因覆盖率 | `target` | 16px |

**纪律**：首触/末触是**两个并列口径**，图标必须可区分（`circle-dot` 起点 vs `flag` 终点）；**禁止**用同一个图标加不同颜色表达两个口径——颜色只承担语义色职责，口径区分靠形状（P4 的"不靠颜色单独传达含义"）。

```
│            │                                    │ │ （该规则永不命中） [定位]   │ │
│            │                                    │ └────────────────────────────┘ │
└────────────┴────────────────────────────────────┴────────────────────────────────┘
```

**右栏三张卡的数据来源必须分清**（否则会做出假数据）：

| 卡片 | 数据来源 | 性质 |
|---|---|---|
| 抽样预览（命中人数 / 互斥归并抑制 / 分产品包分布 / 命中样本） | `POST /rules/preview`（`mode=sample`，`sampleSize` 默认 50000）返回 `matchedCount` / `suppressedByMutexCount` / `samples[]` | **服务端抽样估算**，非精确值。必须标注"抽样估算"字样，不能写成确定值 |
| 抽样预览（全量） | `mode=full` 返回 `previewTaskId` → 轮询 `GET /rules/preview/{taskId}` | **异步全量**，需展示进度态（`预览计算中 42%`），完成后替换抽样值 |
| 冲突提示 | 同上接口的 `conflicts[]`（`ruleId` / `ruleName` / `overlapCount`） | **服务端诊断**，可直接渲染，无需前端重算 |
| 预检结果（标签下线 / 死规则 / 条件重复） | 前端本地静态校验 + 规则/标签/产品包元数据接口 | **客户端校验**，与上行的服务端诊断是两套，UI 上需与「冲突提示」分开呈现，避免用户误以为是一件事 |

`suppressedByMutexCount` 的呈现是本页的独有价值：它是"因为互斥被放弃掉的人"——用户第一次能直观看到**互斥组到底起了多大作用**。上一版没有这个数字，等于互斥配置的效果完全不可观测。

**关键交互解法**

**(1) 优先级如何表达 —— 拖动排序为主 + 「序号 + 数字优先级」双显式，不让用户手填数字**

契约事实（对齐 `openapi.yaml`）：`mapping_rule.priority` 是 **int，数字越小优先级越高，全表统一排序**；`PATCH /rules/reorder` 接受 `items[{id, priority}]` 批量重排。规则引擎执行顺序是：先按互斥组归并（同组内只保留 priority 最小者），再全局取 priority 最小者定包。

设计推论：**拖动是唯一的编辑手段，但优先级必须是显式可读的**。上一版只画了 `01/02/03` 序号徽章，序号只是"看起来有顺序"，用户无法判断两条规则之间有多大的优先级空隙，也无法对照日志与接口排查。因此每一行同时显示两组信息：

```
┌─ ⠿  #01  P10   规则：重疾险升级版                    [已启用] ─┐
│  ↑ 拖动     ↑序号 ↑数字优先级                                  │
```

- **六点手柄**（`grip-vertical` 图标，Airtable 同款符号）—— 唯一的拖动抓手，符号已被跨产品验证
- **序号徽章 `#01 / #02 / #03`** —— 拖动后自动重编号，表示"实际评估次序"，无跳号无并列
- **数字优先级 `P10`（等宽字体）** —— 直读 `priority` 字段值。拖动结束 → 前端按新次序计算 priority → 调 `PATCH /rules/reorder` 落库 → 用接口返回值**回显**（不做本地乐观值长期驻留，避免与后端不一致）
- **`priority` 不是输入框**。用户永远不手填数字：数字型优先级在规则数 > 10 后无法维护（插入一条要改一堆数字，或出现并列）。数字只作为**只读诊断信息**存在——当运营与开发对话（"P30 那条为什么没生效"）时，双方有共同语言
- 顶部署法条（Info Banner）显式声明算法心智：**"规则自上而下逐条评估，命中即停止（first-match-wins）。同一互斥组内只保留优先级最高的一条。"**（HubSpot + Dify 已验证的语言 + 架构引擎的真实语义）
- 卡片高度可折叠（默认展开条件，收起时只留产品包名 + 序号 + 优先级 + 启用开关），规则数 > 15 时自动折叠
- **键盘等价方案（无障碍必需）**：聚焦卡片 → `Alt + ↑/↓` 移动 → `aria-live` 播报"规则 P30 已移动到第 2 位，优先级 P20"
- 拖动中目标位置显示 2px `--primary` 插入指示线（不是整卡缩放/阴影抖动）
- 拖动结束前不落库；拖动作废（Esc）则回滚到原位。**并发保护**：若 `reorder` 返回冲突（他人已改），整体回滚 + Toast `规则顺序已被他人修改，已刷新为最新顺序`

**(2) 互斥组如何表达 —— 分组容器 + 组头，不画连线、不用左侧条纹**

契约事实（对齐 `openapi.yaml` / `ARCHITECTURE.md`）：`mutex_group.mode` 目前**只有 `single` 一个取值**，语义是"组内最多命中一个，取优先级最高（priority 最小）"。上一版我画了「互斥·组内任一 / 互斥·组内全部」两种模式徽章——**这是错的，契约里没有第二种模式**，按那时的设计会做出一个后端不支持的切换器。已修正为单一模式。

- 互斥组 = 一个带组头的浅底容器（`--surface-sunken` 背景，`--radius-lg` 8px 圆角）
- 组头包含：组名（可编辑） + **模式徽章（固定文案 `互斥 · 组内取最高优先级`，只读、不可切换）** + 组内命中人数 + 折叠箭头
- **组头必须写清"取最高优先级"而不是只写"互斥"**：`mutex` 这个词对运营人员是黑话，而"这组里只会有一个人收到、谁的优先级高谁赢"是能直接理解的业务后果
- 组内规则卡片使用**白色背景 + 1px 边框**，与组容器形成两级视觉层（inset 关系），自然表达"这些规则属于同一互斥组"
- 组内规则的 `P20 / P30` 优先级并列展示，用户能一眼看出**组内谁赢**；组头右侧显示 `组内归并抑制 N 人`（来自 `suppressedByMutexCount`）
- **禁止**用 `border-left: 3px solid` 做互斥组标识（AI 味特征）；组间用 `--space-6` (24px) 间距 + 一条 1px `--border` 分隔线区分
- **禁止**画连线（node-edge canvas）：规则条目一多就变意面图，且小屏不可用
- 组间逻辑固定为**全局优先级顺序**，不提供"并/交/差"选择器（规避神策的复杂度陷阱）
- **`mode` 字段不出现在界面上**（已裁决：固定 `single`，不预留扩展。理由：「组内全部命中」在语义上等于互斥失效，若预留该枚举值，会让人误以为系统有这个能力）。原 Q9 已关闭

**(3) 规则冲突如何提示 —— 发布前预检（系统能力，非文档建议）**

预检规则库（直接来自调研中 HubSpot 与 Dify 的官方陷阱清单）：

| 级别 | 检测项 | 提示文案示例 |
|---|---|---|
| 错误（阻断发布） | 条件完全相同但产品包不同（重复矛盾） | `规则 05 与规则 02 的标签条件完全一致，但映射到不同产品包，无法判断优先级归属` |
| 错误（阻断发布） | 互斥组内条件存在交集 | `互斥组 A 中规则 02 与规则 03 的命中人群存在 1,240 人重叠，与互斥语义冲突` |
| 错误（阻断发布） | 引用的标签已下线 / 产品包已下架 | `规则 06 引用的标签「车险意向-2025」已于 2026-08-30 下线` |
| 警告（可发布待确认） | 死规则：被前置规则完全覆盖，永不命中 | `规则 07 被规则 03 完全覆盖，该规则永远不会命中，建议删除或上移` |
| 警告（可发布待确认） | 规则命中人数为 0 | `规则 04 当前命中 0 人，可能是标签条件过严` |
| 警告（可发布待确认） | 规则命中人数超阈值，触发频控风险 | `规则 01 命中 12,480 人，按当前频控预计 3,200 人被拦截` |

- 结果呈现在右栏「预检结果」卡片（常驻），同时在页面顶部出现一条汇总横幅：`预检发现 1 个阻断问题、2 个待确认警告    [查看全部]                        [重新预检]`
- 每条问题带 **[定位]** 按钮 → 滚动并高亮对应规则卡（3 秒 `--primary-subtle-bg` 闪烁，同时尊重 `prefers-reduced-motion` 时改为静态描边）
- 「发布」按钮在存在错误时**置灰 + Tooltip 说明原因**（遵守 P7：不能点了才失败）
- 预检是**自动触发的**（编辑后 debounce 1.2s 静默预检）+ 手动「预检」按钮双通道

**(4) 命中人数预览放哪里 —— 右侧 sticky 常驻面板，不跳转**

- 位置：三栏布局右栏，`position: sticky; top: 56px`，随规则编辑**实时刷新**（debounce 800ms）
- 结构自上而下：
  1. **预计命中人数**（30px / 590 / tabular-nums）—— 单一最大视觉重量，这是营销管理岗最关心的数字
  2. 覆盖率百分比 + 横向比例条
  3. **分产品包命中分布**（横向堆叠条 + 数值，非饼图 —— 饼图在 5 项以上不可读）
  4. **去重后人数**与重叠量提示
  5. 数据口径脚注：`基于 2026-09-17 T+1 数据，每日 06:00 自动更新，更新于 06:04`（T+1 特性必须显式可见，否则用户会以为数据是实时的）
- **禁止**把命中预览做成一个"点击预览"按钮 —— 这是本系统最高频的反馈回路，必须零跳转
- 平板（768–1279px）时右栏折叠为抽屉，由页面右上角「命中预览」按钮唤起；手机端改为顶部吸顶小结条

**(5) 数据缺口规则的禁用态 —— 浴改淋规则（依赖 GAP-2 未接入标签）**

浴改淋规则条件依赖 `house_feature_tags`（房屋是否带浴缸），该标签在一期数据源中不存在（见 DATA-CONTRACT GAP-2）。规则以 `disabled` 状态预置在库，但**不删除**——数据接入后零改动即可启用。其呈现与交互是"缺口可见"原则的样板：

1. **行整体灰化**：规则名、条件、产品包 Tag 透明度降至 45%（`.rule-row-disabled`），明确表达"存在但不参与跑批"，但仍可读、可拖拽排序、可预览命中数（预览结果预期为 0）。
2. **常驻缺口标记**：规则名后跟橙色 Tag `依赖标签未接入（GAP-2）`，不需要悬停即可看到禁用原因——遵守 P8 的反面解释：*不生效的配置必须自带原因*，而不是只给一个置灰控件。
3. **不禁用 Switch，采用「尝试 → 解释」而非「神秘置灰」**：点击开关仍弹确认框，但确认框内容已特化为 `该规则依赖的户型标签（house_feature_tags，浴缸有无）数据源尚未接入（DATA-CONTRACT GAP-2），启用将被系统拒绝。请先推动标签接入。`，确认按钮为红色警示态。
4. **服务端硬拒绝是最终闸门**：确定后 PATCH 返回 400，页面顶部红色 message 原样回显服务端文案 `标签 house_feature_tags 数据尚未接入（DATA-CONTRACT GAP-2），该规则在数据源确认前禁止启用`，Switch 状态保持停用、不发生乐观翻转。前端特判仅用于提前解释，**禁用判定的唯一权威在服务端**（防止前端规则被绕过）。
5. 数据源接入、标签字典补齐后：移除前端 `house_feature_tags` 特判、规则可正常启用，行灰化与 Tag 自然消失，无需数据迁移。

**图标语义纪律**（这是我在上一轮自己踩过的坑）：`halted` 用 `circle-slash`（禁止继续）而不是 `undo-2`。`undo` 暗示"可回退、可恢复"，而停止发送是**不可逆**的终止动作；用 `undo` 会诱导用户以为"还能恢复成待推送"，这是错误的预期。同理，界面文案统一为「**停止发送**」，**全站不得出现「撤回」「召回」「撤销推送」这类暗示可恢复的表述**。

**三组状态必须彼此分开，不能合并同类项**：
- 「已拦截（`suppressed`）」是**频控主动保护**的结果（系统正常工作的证明）
- 「发送失败（`failed`）」是**系统/通道异常**（需要排查）
- 「已停止（`halted`）」是**用户主动决策**（不应被计入通道质量指标）

把三者合并成一个"未成功"数字，会让运营在复盘时误判通道质量，也会让"我停了一个批次"看起来像"系统出了事故"。

**四段微条（Microbar）**：在状态列下方用一段 100% 宽的堆叠条表达比例 —— 已发送 `--success`、拦截 `--warn`、停止 `--muted`（斜纹填充，与实色区分）、失败 `--danger`。每段最小可见宽度 4%，不足时在 tooltip 中列出。鼠标悬停显示 tooltip 明细。比若干个并列数字更快被扫读（Stripe 模式）。
- `--muted` 段用**斜纹/斜线填充**而非实色：它是"主动停止"而非"结果"，视觉上应与实色的成功/失败区分开（同时也满足"不靠颜色单独传达含义"）。

**明细查询的筛选能力必须暴露给用户**（对齐 `/push-details` 的 query 参数）：页面筛选区除人群包 / 产品包 / 渠道外，必须提供 **`msgType`（全部 / 营销 / 通知）** 与 **`reasonCode`（原因码）** 两个筛选器。原因码用中文释义而非裸枚举：

| 原因码 | 界面文案 |
|---|---|
| `LEAD_PACKAGE_COOLDOWN` | 同包线索冷却（业主近 90 天有同产品包线索） |
| `LEAD_HOUSE_COOLDOWN` | 线索客户冷却（业主近 15 天有任意有效线索，跨产品包） |
| `NO_MOBILE` | 无手机号（补号链路未覆盖，**归「数据缺口」组，不是客户拒绝**） |
| `HOUSE_COOLDOWN` | 房屋冷却期内（近 7 天触达过任意营销） |
| `PACKAGE_COOLDOWN` | 产品包冷却期内（近 30 天触达过同包） |
| `HOUSE_DAILY_CAP` / `HOUSE_WEEKLY_CAP` / `HOUSE_MONTHLY_CAP` | 超出触达日 / 周 / 月上限（1 / 2 / 4 次） |

| `GLOBAL_CAP_DEFERRED` | 全局日上限 5000，顺延下一窗口 |

**14 个原因码按六组着色**（工程实现见前端 `reason-codes.ts`，Tag 配色全系统唯一来源）：线索闸门=`LEAD_*`（金）、数据缺口=`NO_MOBILE`（橙）、名单=`OPT_OUT`/`BLACKLIST`（红）、频控=冷却与 CAP 类（墨钢蓝 #1D5A96）、发送时段=`OUT_OF_WINDOW`/`BLOCKED_WINDOW`（青）、节假日=`HOLIDAY_SKIP`（灰）。**`NO_MOBILE` 必须与客户主观拒绝类（退订/黑名单）颜色拉开**：它是数据源问题（GAP-1 补号覆盖率不足），运营据此推动数据接入而非调整营销策略；推送记录页顶部的分组聚合 Tag 顺序固定为「线索闸门 → 数据缺口 → 名单 → 频控 → 发送时段 → 节假日 → 已发送」，与闸门执行顺序一致。

#### 8.3.1 停止发送 与 撤回：两个能力必须拆开（已按架构裁定落地）

**架构裁定结论**（此前我把它设计成"条件性能力"，已被证伪，这里是修正后的口径）：

| 能力 | 归属 | 可行性 | 本系统是否实现 |
|---|---|---|---|
| **停止发送**（停掉尚未下发的明细） | 系统层（本系统的队列） | **确定可行**，不依赖外部通道 | **P0 必做**，已实现 `POST /push-tasks/{id}/halt` |
| **撤回已送达**（把已到用户手机上的短信收回来） | 通道层（外部） | **物理不可行** —— 短信一旦送达不可召回 | **不做**，且界面不得出现任何暗示可撤回的文案 |

企微之所以有「停止发送」，是因为它的送达链路里存在"成员需人工确认才送达"这一环，中止窗口是**链路特性带来的**，不是通用能力。本系统的触达通道没有这个环节，所以**只有「停止发送」，没有「撤回」**。

这与 OPEN-DECISIONS 的裁定一致：`停止发送` / `撤回已送达` 拆为两个独立能力，前者系统层确定可做，后者通道层物理不可行。

**契约事实（`openapi.yaml` / `ARCHITECTURE.md`，设计必须逐条对齐）**

| 契约 | 值 | 对设计的约束 |
|---|---|---|
| 端点 | `POST /push-tasks/{id}/halt` | 按钮动作即调它 |
| 确定性语义 | 把该批次 `status=queued` 的明细置为 `halted`，不再下发 | 影响面必须显示 **待发送（可停止）** 的数量 |
| 在途明细 | **尽力而为**，以通道回执为准，可能仍发出 | 影响面必须诚实写出"在途部分可能仍会发出"，不能承诺 100% 拦住 |
| 已送达明细 | **不撤回**，不影响其统计 | 必须显示 **已送达（不可收回）** 的数量，且文案不得用"撤回" |
| `HaltRequest.reason` | **必填**，`maxLength: 255` | 确认 Modal 必须有**必填的原因输入框**，不是可选的备注 |
| `HaltRequest.channelRecall` | boolean，**默认 false**；仅当外部通道提供撤回 API 时有效，成功与否以回执为准 | 默认关闭。仅在通道确认支持时才渲染为可勾选项；未确认时**不渲染**这个开关（避免暗示可撤回） |
| 不可逆 | 停止后不可恢复为待推送；如需继续走重推 | 确认文案必须写明"不可恢复" |
| 已结束批次 | `done / failed / halted` 再调用返回 **`40900`** | 按钮在批次已结束时**前置置灰**，不能等点了才报错 |
| 状态落库 | `push_task.status=halted` + `halted_count` / `halted_at` / `halted_by` / `halt_reason`；`push_detail.status=halted` | 表格需有 `停止` 数量列；详情抽屉需显示操作人与原因 |
| `halted` 明细可重推 | 是 | 已停止批次**仍可重推**，不禁用 |
| 审计 | 写 `operation_audit(action=push.halt)` | 无需专用 UI，操作日志页可查 |

**(1) 按钮位置与出现条件**

- **表格操作列**：`停止发送`（Ghost 文字按钮），仅在批次状态为 `queued` / `sending` 的行出现
- 批次状态为 `done` / `failed` / `halted` 的行**不显示**该按钮（对应 `40900` 的前置防御，不能让用户点了才知道不行）
- **底部批量操作条**：`[停止发送选中批次]` 排在 `[重推选中批次]` **之前**（止损优先于补发）。混合选中（含已结束批次）时按钮置灰 + Tooltip `已结束的批次无法停止，请取消勾选后重试`
- **权限**：停止发送是止损动作，建议与「发起任务」同级授权（大区/营业部即可操作，不需要总部审批），因为它本身就是纠错手段——审批链会让止损失效

**(2) 二次确认 Modal（宽度 560px；有已送达明细时升 640px 高风险档）**

弹窗必须同时说清三件事：**能拦住多少、拦不住多少、以及为什么这件事不可逆**。

```

│ 停止发送 1 个批次                                       [×]  │
```

关键设计点：

- **三段拆分（待发送 / 在途 / 已送达）是这个弹窗存在的全部意义**。如果只写"确定停止 2,410 人吗？"，用户会以为 2,410 人都能拦住，实际只有 2,030 人能拦住——这是典型的"点了才发现不是我想的那样"。**先给坏消息**：已送达与在途的说明排在前面，不要让用户误判止损效果
- **"不可收回"这个词必须出现**，但**不许用"撤回"**（用了就等于承诺了一个不存在的能力）
- **停止原因必填**（契约 `required: [reason]`，`maxLength: 255`）。这是硬约束不是可选项：不给原因就没法审计"为什么这个批次被停了"，事后归因将失去依据。输入框下方实时显示 `0 / 255`
- **`channelRecall` 开关默认不渲染**。仅当通道方书面确认提供撤回 API 时才增加一个默认关闭的勾选项，文案为 `同时请求通道尝试撤回在途消息（不保证成功，以通道回执为准）`。当前状态下**这个开关不出现在界面上**——渲染一个不生效的开关同样是虚假承诺
- 「确认停止发送」按钮用 `--danger`；Modal 打开时**默认焦点在「取消」**；原因未填或确认项未勾选时按钮置灰
- 「已送达明细 > 0」时升为 640px 高风险档（因为存在不可收回的部分，决策代价更高）

**(3) 停止后状态展示**

- 批次徽章 → `已停止发送`（`circle-slash` + `--muted`），明细徽章 → `已停止`
- 表格数字列的语义：`计划 2,410 / 成功 350 / 停止 2,030 / 失败 0 / 拦截 0`。**停止量绝不计入"失败"** —— 停止是用户主动决策，失败是系统异常；混列会让运营复盘时误判通道质量
- 四段微条：待发/成功 `--success`、拦截 `--warn`、**停止 `--muted`（斜纹）**、失败 `--danger`
- 详情抽屉新增一行：`停止信息：由 张启明 于 2026-09-18 13:52 停止`，附带 `停止原因：产品包选错了，应为「定额给付型 2026 版」`（`halted_by` / `halted_at` / `halt_reason` 三字段直接渲染，无需前端拼装）
- **已停止批次仍可重推**：操作列保留 `重推`。重推确认 Modal 需额外提示一句 `该批次曾于 09-18 13:52 停止，重推将重新下发全部计划人群`，让用户意识到停止后重推 = 重来一遍
- 停止后 `push_detail.status=halted` 的明细，在明细列表里可用 `状态=已停止` 筛选，且**可被选中做单条/批量重推**

---

**(4) 这里绝不做的三件事**

1. **不做「撤回」按钮、不发任何可撤回的暗示** —— 短信物理不可召回。OPEN-DECISIONS 的裁定是"UI 口径：界面不出现任何暗示可撤回的文案"
2. **不把停止包装成"万无一失的保险"** —— 在途明细可能仍发出，已送达的收不回。界面必须诚实呈现这两段
3. **不因为"有停止发送"就削弱下发前的影响面预览** —— 停止发送只能救 `queued` 部分，而一个批次从创建到跑完可能只需几分钟。**影响面预览仍然是第一道也是主力防线**，不是可以放松的次要件（见 §8.4 的补偿设计）

**（附）关于「重推」与「停止」的关系**

两者是成对的反向操作，但**不等权重**：
- `停止发送` 是**止损**，作用是"少发一些"，只对未下发部分有效
- `重推` 是**补发**，作用是"再发一次"，代价是二次打扰已触达客户

界面上并列但不并重：停止发送用 `--danger` 语义（收手），重推用中性按钮（继续）。两者都写 `operation_audit`，都可在操作日志页追溯。


### 8.3.2 推送记录列表新增「线索结果」列（本轮新增）

业务诉求"每次发送后真实产生线索的质量"落到列表层，需要一列**线索结果**。它与既有列的区别是：**其它列都是"发送侧"事实（我们自己发的），这一列是"线索侧"回填事实（外部系统回填的）**——因此必须把两个口径的**时间差**说清楚（`syncedAt` 滞后于 `sentAt`）。

**批次列表（`/push-tasks`）**

| 列 | 内容 | 数据来源 | 空值态 |
|---|---|---|---|
| 线索结果 | `线索 12` | `PushTask.leadCount`（契约已落，按 `lead_id` 去重） | 无归因线索时显 `—`，**不显 0**（0 与"尚未归因/数据未到"必须区分，见下） |
| 最近线索间隔 | 悬停 `线索结果` 显示最近一条线索距本批次下发的间隔 | `min(lead_created_at − push_detail.sent_at)`（前端聚合，或下钻取） | 无则显 `暂无` |

**明细列表（`/push-details`，客户级）**

| 列 | 内容 | 判定 | 空值态 |
|---|---|---|---|
| 线索结果 | `已出线索`（`--success`，`link` 图标） / `未出线索`（`--muted`） | 该 `customer_key` 在 `lead_record` 是否有 `lead_created_at ≥ 本明细 sent_at` 的记录 | 见下方"数据未到"态 |
| 线索间隔 | `4 小时 20 分`（`lead_created_at − sent_at`，等宽 tabular-nums） | 同上 | — |

**三种"没有线索"必须区分（这是本列最容易做错的地方）**

| 显示 | 含义 | 什么时候出现 |
|---|---|---|
| `未出线索` | 已确认无线索（外部数据已到齐） | T+1 数据已同步（`syncedAt` 覆盖该时段）且无匹配 |
| `—` | 尚未归因 / 数据未到 | 明细较新，T+1 数据尚未同步，或 `attributed_at` 为空 |
| `数据不可用` | 线索数据源整体不可用（降级态） | `gateStatus = data_unavailable` |

> **纪律**：把"数据未到"画成"未出线索"，会让运营得出"这批推送完全没效果"的错误结论并据此砍掉投放。**"没有数据"和"数据是没有"是两件事**，必须在界面上是两种显示。这与 P8 同源：不给用户一个会诱导错误判断的显示。

**本列数据来源（契约已补齐，直接渲染真实数字）**

- 契约已落：`PushTask.leadCount`（批次级，按 `lead_id` 去重）+ `PushDetail.leadCount`（明细级，该明细作为首触/末触归因到的线索数）。**本列直接渲染真实数字**（批次级 `线索 12`；明细级 `leadCount>0` → `已出线索`）。
- **线索间隔**：契约 `PushDetail` 未提供 `lead_created_at`，故间隔列**保留"悬停/下钻取间隔"**（下钻 §8.5 时间线取 `lead_created_at − sent_at`）；若后续契约补 `lastTouchLeadAt` 再内联展示（轻量建议，见 §11 Q17）。
- **有序降级仍保留**：数据未到（T+1 未同步、`attributedAt` 为空）时显示 `—`，**不渲染 0 假数字**（见"三种没有线索"）。
- **有效线索率不在本列**：契约仅提供 `leadCount`（线索数），**未提供批次级/明细级「有效线索数」**。有效线索（A/B 级）占比在 §8.6 看板展示，**本列不渲染有效线索率**（避免自造字段，P8）。
- 明细级下钻入口长期保留：点单元格 → `/customers/{customerKey}/timeline`（§8.5）。

**原因码筛选器需纳入闸门 0 的两个码，且置顶**

**重推弹窗必须显式声明"线索静默不可被重推覆盖"**

`ARCHITECTURE §8` 的覆盖边界：重推**可**覆盖冷却期与频次上限，**不可**覆盖线索静默（`LEAD_PACKAGE_COOLDOWN` / `LEAD_HOUSE_COOLDOWN`）、退订黑名单、禁发时段、全局日上限。因此 §8.3 的重推二次确认 Modal（含 §8.3.1 高风险档）**必须新增一行**：


- 位置：影响面区块内、`实际预计送达` 行下方；数字用 `--warn` 510 字重（这是运营必须提前知道的信息，不能等发完才发现"怎么少了 1,120 人"）

**（B）删除 `lookback_days` 控件 —— 为什么这不是"少配一项"而是"修一个会静默出错的 bug"**

这是本轮最重要的一处删除。

原设计里我画了一个 `回看窗口（重复触达剔除）[ 3 ] 天内已触达的客户自动剔除` 的可配置控件。它看起来无害，实际上是**伪配置项**，会必然诱发下面的故障：

- 产品包冷却期可配到 **180 天**（`packageCooldownDays` 上限 180）
- 若实现时用一个统一固定窗口（比如用户配的 30 天）去盖住所有维度的查询
- 那么"90 天前给这个房屋推过产品包 A"这条历史记录就会落在窗口外
- 结果：**长冷却期静默失效** —— 系统认为没推过，于是重复推送同一个产品包

而这个错误**不会报错、不会告警、界面上也看不出来**，只会在业主侧表现为"又给我推了一遍"。这正是"防翻车功能自己翻车"。

正确做法（架构已裁定）：**各维度按自身语义独立查询，不对用户暴露任何回看窗口参数**。

| 维度 | 查询窗口 |
|---|---|
| 房屋冷却 | `houseCooldownDays` |
| 产品包冷却 | `packageCooldownDays` |
| 日上限 | 当日 00:00 起 |
| 周上限 | 近 7 天 |
| 月上限 | 近 30 天 |

界面上的处理：
- **删除输入控件**，改为一行只读说明：`回看窗口 max 30 天（由各维度自动推导，不可配置）`，值直接取 `effectiveLookbackDays`（`readOnly: true`）
- 只读说明旁配 Tooltip：`为避免长冷却期失效，系统按每个维度各自的参数独立查询，不提供统一窗口配置`
- 数字 `30` 是 max(生效冷却期, 30) + 缓冲的推导结果，**是排查用的诊断信息，不是配置项**。放在影响面区块的脚注位置，不放进表单区（放进表单区会诱导用户以为可以改）

**这也是一条设计原则的沉淀**：**界面上不提供"看起来能配、实际会引发不一致"的旋钮。** 一个不能安全生效的配置项，比没有这个配置项更危险。该原则已升格为 §3 **P8「不提供不生效的配置项」**，并给出可操作判据（"用户改了这个值，系统行为会不会随之产生一致且可预期的变化？"）与三档处理表（输入控件 / 只读说明 / 完全不出现）。

**（C）多时段控件（本轮新增）**

契约：`sendWindows` 是 1–N 段列表（`SendWindow[]`），每段 `windowStart` / `windowEnd`（HH:mm）/ `crossDay` / `enabled` / `sortOrder` / `dayType`。保存时后端**自动合并重叠段**。

设计要求：
- 每段一行：`[开始时间] – [结束时间]` + 跨天开关 + 启用开关 + 六点手柄（拖动排序，对应 `sortOrder`）+ 删除
- `+ 添加时段` 新增一行，默认 `10:00 – 12:00`
- **校验规则必须与契约一致**：每段「开始 < 结束」，否则报错 `时段 3 的结束时间必须晚于开始时间`；跨天段（如 `19:30 – 21:00` 之外真正跨 0 点的）必须勾选"跨天"才允许结束 ≤ 开始，否则报错
- **必须回显合并结果**：保存后展示 `当前合并后：10:00–12:00、15:00–18:00 共 2 段`。用户添加了重叠段（如 `10:00-11:00` + `10:30-12:00`）时，系统合并为一段——**如果不回显，"我明明加了两段怎么变一段了"会变成一次客服工单**
- **与禁发时段的重叠必须即时提示**：任何落在 `22:00–08:00` 内的时段都是无效配置（禁发时段不可越过），保存前报错 `时段 2（21:00–23:00）与禁发时段 22:00–08:00 冲突，请调整`
- 时段数量上限给一个软提示（如 > 6 段时提示"时段过多会显著碎片化下发节奏"），但不在契约未定前硬限制

**（D）`day_type` 与 `holidaySkip` 降为 P1（不占 P0 位置）**

上一版我把"工作日/周末分时段"画成了与多时段并列的常规控件。按 PRD §6.3 与 ARCHITECTURE §8.4，这两个是**P1 可选、默认关闭**（`dayType` 默认 `all`、`holidaySkip` 默认 `false`）。因此：

- 表单上**不出现"工作日/周末分别配置"的入口**，只显示一行只读的 `生效日：全部（工作日与周末共用）`，右侧挂一个 `配置分日策略` 的次级链接
- 该链接默认收起，点开后才显示 P1 的分日配置，且在面板标题上明确标 `P1 可选能力`
- `holidaySkip` 同理：默认只显示 `节假日策略：关闭（保持行为可预期）`，标 `P1 可选`
- **理由**：P1 能力若占据 P0 的视觉位置，会让用户在 MVP 阶段就误以为"这两项是必须配的"，从而产生"我是不是没配全"的焦虑，并可能配出非预期的行为（例如开启分日策略后周末时段为空 → 周末一条都发不出去）
- **同时这也是一个防错设计**：`dayType` 一旦启用，就会出现"工作日一套时段 + 周末一套时段"，任何一套为空都会导致该类型日期完全静默。P1 默认关闭是最安全的状态

**（E）营销 vs 服务通知：两处必须写清楚的地方（本轮新增）**

架构在下发 payload 携带 `msgType`（`marketing` / `notice`），频控校验入口按 `msgType` 短路 —— `notice` 直接放行，仅 `marketing` 进入频控校验。这带来两个必须在 UI 上落地的后果：

**E1. 频控页顶部的作用范围说明（防止运营误关频控）**

页面最上方常驻一条说明（`--primary-subtle-bg` 底，非警示色）：

```
本频控只作用于【营销类】触达（产品包推荐）。
服务通知类消息 —— 维修进度、缴费提醒、验证码、紧急通知 ——
不计入营销频控、不被拦截、不受禁发时段限制，正常送达。
```

- **为什么必须写**：如果不写，运营看到"每日最多 1 条"会立刻想到"那业主的维修进度通知是不是也被限了"，然后**去把频控关掉**。一个防打扰机制因为"怕误伤服务通知"而被关闭，是这个功能最讽刺的失败方式
- **为什么用 `--primary-subtle-bg` 而不是 `--warn-bg`**：这是常态化的范围说明（每天都会看到），不是异常警告。常态化警示会脱敏，反过来削弱真正的风险提示
- 位置必须在**表单之上**，不能放在表单下方或被折叠

**E2. 影响面预览的人数口径必须注明"仅统计营销类"**

影响面预估卡片（见上方 wireframe 与 §8.4-F）的标题与每个数字旁都必须带口径限定：

- 卡片标题：`影响面预估（仅统计营销类 · 保存前强制展示）`
- 主数字标签：`可触达 9,280 人（营销类）` / `被拦截 3,200 人（营销类）`
- 分布图标题：`每人触达次数分布（仅营销类）`、`拦截原因分布（仅营销类）`
- 卡片底部脚注：`服务通知类消息不计入上述任何统计，也不受本页频控限制`

- **为什么必须写**：影响面预览是运营判断"这次会打扰多少人"的唯一依据。如果这个数字里混进了服务通知，用户会得出偏高的打扰预估，进而过度收紧频控；反之若用户以为它包含服务通知，也会对"为什么维修通知还是发出去了"产生困惑
- **实现提示**：`push_detail.msgType` 是冗余自批次字段，且频控统计本身就按 `marketing` 过滤，因此这个口径是天然成立的——**设计要做的只是把它说出来**，不需要额外计算

**（F）让用户一眼看懂"我这次会打扰多少人"的四个设计决策**

1. **影响面预估是强制区块，不是可选**。位置紧贴规则编辑区下方，始终可见，不需要点"评估"按钮。选择人群包后自动计算。
   - 核心数字用**大字号 + 横条比例**（`可触达 9,280 人` / `被拦截 3,200 人（25.6%）`），一眼看出触达与打扰的比例关系
   - **每人触达次数分布**用横向条形图（不是饼图）—— 用户真正想知道的不是"平均几次"，而是"有多少人被发了 3 次"（重度打扰人群）
   - **本轮新增「拦截原因分布」**：知道"被拦了多少人"之后，运营的下一个问题是"为什么被拦"。原因分布直接回答它，并顺带让用户理解各维度频控各自起了多大作用（这比让他们去明细页逐条筛原因码高效得多）

2. **偏松阈值的风险横幅置顶**。当设置高于推荐值时，页面顶部出现 `--warn-bg` 横幅，包含三件东西：具体的当前值、行业建议值、一键修正按钮。**横幅带 2px `--warn` 左边框做视觉锚定**（注意：这是功能性风险提示边框，与"禁止侧边条纹强调卡片"的禁令不同 —— 该禁令针对的是给普通信息卡加 3px 彩色左边框）。
   - 阈值档位：每日 ≤1 条（推荐，正常态）、每日 2 条（提示）、每日 ≥3 条（警告横幅）
   - **待澄清**：这里的"建议值 1 条"目前来自 PRD 的行业基准，但**公司内部合规口径未确认**（OPEN-DECISIONS 仍 OPEN）。因此这个横幅的阈值必须是**可配置项或至少集中在一处常量**，等业务/法务给出合规底线后一次替换，不能把 `1` 硬编码散落在多处

3. **每条规则行内用自然语言复述真实语义**。用户看到的不是三个孤立输入框，而是"同一房屋 7 天内不再接收任何营销触达，无论产品包"。**重置时机必须显式写出**（企微 SCRM 的教训：每周一 0 点刷新这件事必须能被解释，否则用户无法预测行为）。
   - 多档频控（日/周/月）同时存在时，行内提示必须声明**"系统按更严格的一档生效"**，并**算出当前实际生效的是哪一档**（截图里是"当前实际生效：每日 1 条"）—— 只说"取更严格者"是让用户自己算，把最严格的一档直接算出来告诉他才是可用的
   - 计数锚点必须说清是**「房屋」不是「客户」**：`同一房屋当日短信 + 企微合并计 1 次`。这是 `crossChannelCount` 的真实语义，也是 PRD 反复强调的"计数锚点始终是房屋"

4. **常驻不可回收说明**（与 §8.3.1 呼应）。在影响面区块正下方追加一行静态说明（`--muted` 12px，非警示色）：

   ```
   频控是本系统防止打扰客户的最后一道自动防线：触达一旦下发不可回收。
   ```

   频控页负责"事前把住阈值的闸门"，推送记录页负责"事前说清不可回退"（§8.3.1 方案外的补充说明）。两处都必须在，因为用户是从不同入口进入这两件事的。

   **注**：`停止发送` 已落地为 P0 能力，但它只能救尚未下发的明细；营销短信一旦发出即不可收回，因此这条说明**口径不变**。

**（G）两项"PRD 有要求但契约无字段"的裁决结果（已由 team-lead 拍板，无需 UI 入口）**

设计当初把这两个"PRD 要求 vs 契约缺口"记下来是对的——但它们**都不需要 UI 入口**，裁决如下：

| 项 | PRD 要求 | 裁决 | 设计侧落地 |
|---|---|---|---|
| 分批节流 `batchThrottle` | 每批 500 条、间隔 5 分钟，可配 100–2000 条 / 1–30 分钟 | **不暴露给用户，不设配置项**，作为系统内部常数 | 表单区**不出现任何控件**。仅在「全局发送上限」卡片内保留一行只读说明：`系统按每批 500 条、间隔 5 分钟分批下发（内部常数，不可配置）`——保留它的唯一理由是解释"5000 条为什么需要约 25 分钟发完"，这是运营会问的问题 |
| 无互动降频 `no_engagement_pause` | 连续 3 次无互动 → 暂停 30 天，阈值 2–5 次；原因码 `ENGAGEMENT_PAUSED` | **列入一期 Out-of-Scope**，架构侧不新增字段与原因码 | 一期**不做**该能力：表单无入口、状态与原因码筛选器不包含 `ENGAGEMENT_PAUSED`。文档保留此条以便二期回溯，但**不作为待实现项** |

**裁决带来的一个副作用需要注意**：`no_engagement_pause` 不做，意味着本期的防打扰能力只剩"频次上限 + 冷却期 + 禁发时段 + 退订黑名单"四类，**缺少一个"对方已经不响应了就主动停手"的机制**。这不影响一期交付，但值得在给用户说明时讲清楚——避免用户以为系统会自动识别"推不动的人"。二期若重启该能力，需要补 `FrequencyRule` 字段 + `reasonCode` 枚举值，UI 侧我会在此预留的位置上补一个 P1 面板（形态与 §8.4-D 的分日策略一致：只读一行 + 次级链接），不需要重构表单。

**（H）线索静默期配置（本轮新增 · 闸门 0）**

线索静默期是**新增的一类前置拦截**，**执行顺序优先于全部频控**（`ARCHITECTURE §8.4`：闸门 0 → 闸门 1~11）。它不是"又一个冷却期"，而是表达一个更高的业务语义：**"这个客户已经在被跟进了，不该再被营销打扰"**。因此它放在频控页的**最上方**（在"冷却期"之上），并单独成组。

**H1. 两个冷却配置（用户可配置 → 输入控件，符合 P8）**

```
┌─ 线索静默期（优先于下方全部频控）─────────────────────────────┐
│ ⓘ 客户一旦产生过线索，说明需求已在跟进；此时再推营销消息即为二次骚扰。│
│   本组规则优先于全部频次/冷却规则，不可被手动重推覆盖。             │
│                                                              │
│ 已产生同产品包线索     [ 90 ] 天   范围 1–365，推荐 90        │
│   ⓘ 客户对【同一产品包】已有线索 → 该产品包 90 天内不再推        │
│ 近期已产生线索（房屋级）[ 15 ] 天   范围 1–90，推荐 15         │
│   ⓘ 客户对【任意产品包】近 15 天有线索 → 其全部营销推送暂停      │
│                                                              │
│ ⓘ 判定基准时间 = 该客户最近一次产生线索的时间（见客户详情·线索时间线）│
└──────────────────────────────────────────────────────────────┘
```

- 两行都用**自然语言复述真实语义**（P5/F3 的延续），不写"冷却天数"这类抽象词：第一行说清"同一产品包"，第二行说清"房屋级（任意包）+ 全部暂停"
- **为什么同包更长、他包更短**（必须写进 Tooltip，否则用户无法理解为何两个数差 6 倍）：`同一产品包已有线索 → 需求已在跟进，重复推同款打扰最重，故冷却最长；他包有线索 → 客户已与公司建立跟进关系，此时任何营销都易被视为骚扰，故设全量短冷却，待其冷却后再评估`
- **未映射产品包的线索走哪档冷却（必须解释，否则运营看不懂看板的未映射口径）**：线索的 `packageSource` 为**二值推断**——推断成功 → 按**包级**冷却（90 天）；推断不出（`packageSource=none`）→ **无法定位产品包，只走房屋级冷却（15 天）**。Tooltip 文案：`线索若能对应到产品包，按同包长冷却；对不上产品包时，只能按房屋级短冷却处理`。这与 §8.6 的未映射两口径呼应。
- **字段映射（按 team-lead 定稿命名，三方一致）**：同包冷却 = `leadPackageCooldownDays`（90 / 1–365）；房屋级冷却 = **`leadHouseCooldownDays`**（15 / 1–90，**已随原因码 `LEAD_HOUSE_COOLDOWN` 定稿，替换旧名 `leadRecentDays`**）；线索数据异常降级 = `leadGateFailMode`（`open` / `closed`，默认 `open`）。
- **校验**：`leadPackageCooldownDays` 输入 < `leadHouseCooldownDays` 时给**软提示**（非报错）：`同包冷却通常应长于房屋级冷却（默认 90 > 15），当前同包短于房屋级，请确认是否符合预期`
- **`notice` 豁免待确认**：本组下方需留一行**待确认占位说明**（P1，暂不渲染开关）：`服务通知类（维修进度/缴费提醒）是否豁免本条静默：待业务确认`（见 Q14）。

**H2. 异常降级策略（`leadGateFailMode`，风险决策）**

线索数据来自外部系统，**存在整体拿不到 / 未就绪 / 过期的可能**。此时闸门 0 无法判定，系统必须让运营**显式选择**该怎么处理，而不是默默跳过。

```
┌─ 线索数据异常时的处理（危险决策，默认保守）───────────────────┐
│ 线索侧数据缺失 / 过期（同步滞后 > 2 天）时：                      │
│   ● 继续发送，但显著告警（默认）         ← leadGateFailMode=open │
│      ⓘ 跳过线索静默判定继续下发；任务详情与看板会挂出醒目横幅      │
│        「线索数据缺失/过期，线索静默未生效」。发送不受阻，风险自担。│
│   ○ 暂停营销下发并告警                  ← leadGateFailMode=closed│
│      ⓘ 宁可少发也不误发已有线索的客户。适用于线索数据对合规敏感的 │
│        场景；代价是数据异常期间全部营销停发。                     │
└──────────────────────────────────────────────────────────────┘
```

- **默认 `open`（continue + alert）**，与架构 `ARCHITECTURE §8.4 闸门 0 降级` 一致（`fail-open + 强告警`）。
- **两个选项都不能"安静地跳过"**：`open` 的代价是"可能误推已有线索客户"，必须用**横幅 + 告警**把风险显式化；架构原话"**绝不静默跳过，否则运营会误判已判重**"。
- 切换为 `closed` 属**收紧投放**行为，走轻量确认；切换为 `open`（放宽）需**风险确认**（复用 §8.4"调松阈值"的升级确认，因为它的后果是"可能骚扰已有线索客户"）。
- **数据新鲜度阈值（> 2 天）**暂作为**内部常量**展示为只读说明，不提供控件（P8：它由系统与外部数据源节奏决定，运营改了不生效）。

**H3. 归因窗口 —— 只读说明（P8 第二次应用）**

```
归因窗口 15 天（默认值，快照回显）   [?]
```
- 契约现状：**只有 `LeadRecord.attributionWindowDays`（回填快照）与 `AttributionRun.windowDays`（运行记录），没有配置字段或端点**。
- 按 P8 判据（"改了会不会产生一致可预期的变化？"→ 不会），**不提供输入控件**，只做只读展示；并在 Tooltip 写明 `归因窗口决定"线索归因到窗口内哪几次推送"；当前为系统默认值，如需按短信/企微分别配置需要契约先支持`。
- **归因窗口 ≠ 冷却期（必须写进 Tooltip，防止运营混淆两个"天数"）**：`冷却期是闸门规则，决定「发不发」；归因窗口是统计口径，决定「一条线索算给窗口内哪几次推送」。两者相互独立——调冷却期不会改变归因结果，调归因窗口也不会改变发送行为。`

**保存的二次确认（因影响面大）**

点「保存」→ Modal 展示 **diff + 影响面**：左列为改前值、右列为改后值（变更项用 `--warn` 底色高亮），下方展示"生效后预计可触达人数将从 11,320 人降至 9,280 人"。有实质影响时才弹（纯文案修改不弹，避免确认疲劳）。**变更全量写审计日志**（操作人 / 时间 / 变更前后值 / 生效范围）。

**调松阈值时（加强项）**：当本次保存是**放宽**频控（如每日 1 条 → 3 条、缩短冷却期、关闭跨渠道合并计数、提高全局日上限），确认 Modal 必须升级：

- 顶部风险横幅：`本次调整将放宽频控，预计新增触达 4,100 人次，且营销短信发出后不可收回`
- diff 区块中新增风险数字（"被拦截人数 3,200 → 0"）用 `--warn` 底色 + 510 字重高亮，不用小字灰
- 需**输入新阈值数字**确认（如输入 `3`），而非勾选——放宽防线是高风险决策，确认动作的摩擦度要与风险成正比
- 收紧阈值（3 → 1）、以及不涉及触达量的修改，仍走轻量勾选确认
- **本轮补充**：**放宽线索静默期**（缩短 `leadPackageCooldownDays` / `leadHouseCooldownDays`，或把 `leadGateFailMode` 由 `closed` 改为 `open`）**同样触发升级确认**——后果是"可能对已产生线索的客户重复营销"，与放宽频控同级。横幅文案：`本次调整将缩短线索静默期，预计新增对 520 名已产生线索客户的营销触达，存在投诉风险`。
- 反之**收紧线索静默**（延长冷却期、或 `open → closed`）走轻量确认。

**四态设计（契约 `gateStatus` 的 4 个枚举，与业务方原话的 3 态对齐）**

业务方原话是"3 种情况"（无线索 / 有线索 / 线索超期），而契约 `gateStatus` 是 4 个枚举——多出的第 4 态 `data_unavailable` 是**外部数据缺失的降级态**，必须画出来（否则运营会把"没数据"当成"没线索"）。映射如下：

| 业务语义 | 契约 `gateStatus` | 摘要条徽章（三件套） | 徽章语义色 | 行为约束文案 |
|---|---|---|---|---|
| **无线索** | `clear`（无 `lastLeadAt`） | `user-round-search` 无线索 | `--muted` / `--surface-sunken` | `该客户暂无线索记录，可正常进入营销推送` |
| **有线索 · 静默期内** | `lead_package_cooldown` / `lead_house_cooldown` | `shield-off` 有线索 · 静默期内 | `--warn` / `--warn-bg` | `该客户已产生线索，全部营销推送将被暂停，手动重推亦不可覆盖`（附 `剩余 88 天`） |
| **线索超期** | `clear`（有 `lastLeadAt`） | `circle-check` 线索超期 | `--info` / `--info-bg` | `该客户最近线索已超出静默期（0 天前），可再次评估触达` |
| **线索数据不可用** | `data_unavailable` | `triangle-alert` 线索数据不可用 | `--danger` / `--danger-bg` | `线索数据缺失/过期，线索静默未生效，请勿据此判断客户是否已有线索` |

- `cooldownRemainDays` 必须显示（"剩余 88 天"）——只写"静默期内"而不写还剩多久，运营无法判断"什么时候能再推"，会把这条变成一次不必要的工单
- **`data_unavailable` 必须用 `--danger` 且文案带"勿据此判断"**：这是防打扰闸门失效的异常态，中性化会让运营误判（架构 §8："绝不静默跳过，否则运营会误判已判重"）

**时间线节点规范（P4 状态三件套）**

| 节点 | 图标 | 颜色 | 附带信息 |
|---|---|---|---|
| 线索产生 | `user-round-plus` | 实心圆点 `--success`（质量有效） / `--warn`（C 弱意向） / `--muted`（无效） | 质量等级徽章（A/B/C/无效）、来源系统、`lead_created_at` |
| 触达下发 | `send` | 空心圆环 `--muted`；`suppressed`/`halted` 用对应状态色 | 批次号、产品包、`pushStatus` 徽章、海报缩略图（`posterUrl`） |
| 归因角色 | 首触 `circle-dot` / 末触 `flag` / 未归因 `—` | `--info`（首触）/ `--primary`（末触） | 挂在**线索节点**下（归因是线索的属性，不是触达的属性）——`attributionRole` 来自 `LeadTimelineEvent` |

- **归因角色挂在"线索节点"下**：`first_touch_push_id` / `last_touch_push_id` 是**线索**字段，因此"首触/末触"必须显示为线索节点下方的两个指向标签，而不是触达节点上的徽章——否则用户会以为"这次触达是末触"，混淆了主语
- **未归因必须显式**：窗口外的触达显示 `未归因（窗口外触达，不参与归属）`，而不是留空——留空会让用户以为漏数据
- 时间线用 `<ol>` / `role="list"` 语义，节点顺序=时间倒序；归属角色同时用**文字**表达（不靠颜色）

**三态覆盖（Empty / Error / Edge）**

- **空**：该客户无任何线索也无触达 → 空状态 `user-round-search` + `该客户暂无线索与触达记录`（不画空时间线骨架）
- **空窗但有触达**：显示触达节点 + 顶部一行 `该客户暂无线索记录`（这本身就是重要信号："推了但没出线索"）
- **错误**：`/timeline` 失败 → 行内错误条 + 重试，**不清空摘要条**（摘要可能已成功返回）
- **Edge**：线索数很多（如 100+）→ 分页加载；单条海报缩略图失败 → 占位符（`image-off` 图标），不破版

**转化指标口径标注（强制 · arch 技术契约要求）**

`ARCHITECTURE` 明确"**禁止做出无标注的漂亮转化率**"。因此**每一个转化类指标（KPI 卡 / 漏斗每段 / 分维度表头 / 质量分布图头）都必须随身携带口径角标**，而不是只在页面顶部写一次：

- **统一角标文案**：`触达=发送成功（非已查看）· 归因为发送相关性`
- **载体**：指标标题后的 12px `--muted` 角标，或数字右侧的 `ⓘ`（hover 展开契约返回的 `attributionLimitNote` 全文）
- **禁止**把口径说明只放在页脚 / 帮助文档：运营截图分享某个 KPI 时，脱离上下文的转化率会被当成因果结论 —— 角标必须**跟着数字走**

**首触 / 末触双口径（不押注单一归因）**

- 筛选栏「归因口径」切换 `attribution=first|last`（契约默认 `last`），作用于漏斗 / 分维度 / KPI 的线索口径
- **必须提供"双口径并列对比"视图**（PRD §12.5"看板同时出两个口径"）：在分维度质量表右侧加两列 `首触线索量` / `末触线索量` 逐行并列，或提供 `[首触] [末触] [对比]` 三态分段控件，`对比`态左右并列两条漏斗
- 理由：单一口径必然过誉某一类触点（首触过誉认知类、末触过誉临门一脚类），并列展示才能让运营看到"认知 vs 转化"的差异

**图表类型清单（显式规定，避免"无数据画漂亮图"）**

| 区块 | 指定图表 | 明确禁止 |
|---|---|---|
| 发送→线索→有效线索 | **横向漏斗条**（3 段，宽度按比例，等宽数字标注） | 禁止 3D 漏斗、禁止无数据时画满格 |
| 分维度质量 | **排序横向条形图 + 数据表**（默认按线索转化率降序） | 禁止饼图、禁止无排序 |
| 线索质量分布 | **排序横向条形图**（A/B/C/无效） | 禁止饼图 / 环形图（占比用条形 + 数字表达） |
| 时间趋势（可选） | 折线（发送量 vs 线索量，双轴） | **数据未覆盖的时段必须留空并标注"数据未到"**，禁止用 0 连接伪造连续 |

**「归因局限与数据缺口」区块（本看板的诚实底线，P0）**

这是本页**最重要**的区块，常驻、`--surface-sunken` 底、不可折叠，**五行分别对应五类标注（前四项为 arch 技术契约强制）**：

1. **口径局限**（来自 `attributionLimitNote`）：`触达 = 发送成功，非「已查看」；归因为发送相关性（非因果）` —— 原样展示契约文案
2. **未归因数**（来自 `unattributedLeads`）：`未归因线索 71 条（7.7%），未计入上方转化率` —— **必须显示**（契约强制），否则转化率会被高估
3. **未映射产品包线索（拆两个口径，不合并）**（来自 `externalPackageCode` / `packageSource` / `packageId`）：这是**两种不同的病**，合并成一个数字就白标了 ——
   - ① **集成问题**（`externalPackageCode` 非空、`packageId` 空）：外部给了包编码但本系统字典对不上 → 文案 `包编码对不上（需核对字典映射）`
   - ② **上游问题**（`externalPackageCode` 空、`packageId` 空）：外部根本没提供 → 文案 `外部未提供包编码（上游数据缺失）`
   - 两者**分别单列，均不并入任何产品包桶**（合并会让人不知道该去找集成还是找上游；并入产品包桶则会虚高该桶转化率）
4. **点击 / 行为数据缺口（默认态；条件可升级 —— 见下方「条件性 P0」）**：**默认**一期不埋点击点 → `本看板仅算「发送→线索」两端，不展示点击 / 打开 / 落地页类图表`（**没有数据就不画图**，画了即为虚假承诺）。**但**按 `ARCHITECTURE §15.6`，点击埋点是**条件性 P0**：外部通道能提供「带参短链 + 点击回传」时升级为**三段漏斗**，否则维持两端。**判据是通道能力，不是设计偏好。**
5. **维度缺口**（契约 `groupBy` 仅 `package` / `tag` / `poster_template`）：`分标签 / 分海报模板的「有效线索率」当前契约不可得`（见下方缺口表）

**降级态横幅（`degraded=true` 时显示，最高优先级）**

当 `/analytics/lead-conversion` 回传 `degraded=true`（架构 §15.5 二级/三级降级），页面顶部挂 `--warn-bg` 横幅（2px `--warn` 左边框）：

```
本次为弱归因 / 包级归因，仅反映「批次发送量」与「某时段线索量」的宏观相关性，不可用于个体判定。
```

- 一级降级（可达客户级但键不稳）：正常展示 + 归因覆盖率可能偏低
- 二级（弱归因 / 包级）：挂上述横幅，**个体级下钻入口置灰**
- 三级（无法建 `customer_key`）：`customer_key` 缺失 → **闸门 0 关闭并告警**，看板显著标 `线索静默未生效`，且看板只保留包级宏观相关性

**闸门 0 降级告警态（与 `degraded` 独立触发 · arch 要求）**

当线索数据缺失 / 过期（`lead_record.max(synced_at)` 滞后 > 2 天）且 `leadGateFailMode=open` 时，闸门 0 **未生效**。此时看板**必须**挂 `--danger-bg` 横幅（2px `--danger` 左边框，**警示色，非 `--warn`**）：

```
! 线索静默未生效：线索数据缺失/过期（最近同步 09-14，滞后 4 天）。
  本次统计中的「未出线索」不代表真实未出线索，请勿据此判断静默期。
```

- **触发条件与 `degraded`（归因降级）是两件事**：`degraded` 是"归因质量下降"，本条是"防打扰闸门失效"。二者**可同时出现，横幅分别显示、不合并**（合并会让两类完全不同的问题都糊成"数据有点问题"）
- 用 `--danger` 而非 `--warn`：它意味着"本该被静默拦住的客户可能已被推送"，属**合规风险级**（与 §8.5 的 `data_unavailable` 同色，保持全局一致）
- `leadGateFailMode=closed` 时（营销已暂停）：看板顶部改为中性提示 `线索数据异常，营销下发已暂停`——此时无新发送数据，转化统计冻结并标注"截至 09-14"

**数据缺口一览（诚实标注，一期不渲染）**

| 缺口 | 原因 | 界面处理 |
|---|---|---|
| 点击 / 打开 / 落地页行为 | 一期默认不埋点；**条件性 P0**（外部通道能提供「带参短链 + 点击回传」即做，`ARCHITECTURE §15.6`） | **默认**不渲染该类图表；**条件成立**则升级「发送 → 点击 → 留资」三段漏斗（见下方「条件性 P0」） |
| 分标签 / 分海报模板的有效线索率 | **已支持**（`groupBy` 扩展后） | 已补入分维度质量表（§8.6），不再是缺口 |
| 大区 / 项目 维度分组 | `groupBy` 已扩展至 `{package, tag, poster_template}`，仍**不含**大区 / 项目（PRD §12.6 提到但契约未提供） | 不渲染该切项；记为 Q18 |
| 多触点 / 营收级归因 | 一期只做首触+末触（PRD O15） | 不出现；口径切换器只有 first/last |

**条件性 P0：点击埋点与「发送 → 点击 → 留资」三段漏斗（`ARCHITECTURE §15.6` 预案）**

点击数据的**有无不取决于设计偏好，取决于外部通道能力**。因此看板做**双形态**设计，按通道能力二选一、不预设：

| 形态 | 触发条件 | 漏斗 | KPI | 口径角标 |
|---|---|---|---|---|
| **两端（默认）** | 通道**不能**提供带参短链 + 点击回传 | 发送量 → 线索量 → 有效线索 | 发送量 / 线索量 / 有效线索率 | `触达=发送成功（非已查看）· 归因为发送相关性` |
| **三段（条件启用）** | 通道**能**提供 | 发送量 → **点击量** → 留资（线索量）→ 有效线索 | 追加 **点击率** / **留资率** | 收窄为 `留资归因 = 点击相关性` |

- **契约纪律（与 arch §15.6 一致）**：三段漏斗所需字段（`clicked` / `clickRate` / `leadRate`）与 `POST /click-events` **暂不进 `openapi.yaml`**——契约里存在但不生效的端点最易被误实现为半成品。**通道确认后由 arch 生成 Spec 段落，UI 再启用三段形态。**
- **UI 实现要求**：漏斗组件与 KPI 行**参数化段数**（3 / 4 段自适应），**不写死段数**；`degraded` 与「线索静默未生效」两个横幅在两种形态下都要显示。
- **升级后的诚实收窄**：三段形态能把「发了没点（文案/海报问题）」与「点了没留资（落地页问题）」分开——这是**真实收窄**上一个条目的盲区，而不是把两端数据包装成三段。

**三态覆盖**

- **Loading**：KPI 与图表用**骨架屏**（不发光的静态块，MOTION=2 下不做 shimmer 扫光）
- **Empty**：所选时间范围内无发送 → 空状态（`chart-column` 图标 + `所选时间范围内暂无发送记录`），**不画满格 0 的图**
- **Error**：端点失败 → 行内错误 + 重试，保留筛选栏状态
- **Edge**：某分组桶 `sent=0` → `conversionRate` 显示 `—` 而非 `0%`（除以零无意义）；某桶线索数极少（< 10）→ 数字旁标 `样本少`，避免运营据小样本下结论

**a11y**：漏斗每段有文字标签 + 数字（不靠长度单独传达）；图表容器 `role="img"` + `aria-label` 概述（如"发送 38400，线索 920，有效线索 416"）；颜色不单独承载语义（每条都带数字）。

| 变体 | 背景 | 文字 | 边框 | 用途 |
|---|---|---|---|---|

| Secondary | `--surface` | `--fg` | 1px `--border-strong` | 次操作 |
| Ghost | transparent → hover `--surface-sunken` | `--primary` | 无 | 三级操作、行内操作 |

小屏触摸区域不小于 44×44px（PC 端按钮视觉高 32px，但通过 padding 扩展点击热区）。

### 9.6 批量操作条（Batch Action Bar）

- 位置：视口底部居中悬浮，`bottom: 24px`，宽度自适应（最大 720px）
- 样式：`--surface` 底 + `--elev-overlay` + `--radius-xl` 12px + 1px `--border`
- 结构：左 `已选 N 项`（510）+ `取消选择`（Ghost）；右 最多 1 Primary + 2 Secondary
- 动效：出现/消失 `translateY(12px) → 0` + 透明度变化，200ms `--ease-standard`；`prefers-reduced-motion` 时仅保留透明度变化
- 全选行为：表头勾选框支持"全选本页"与"全选全部 128 条"，选中后卡片文案明确区分——**必须让用户知道选了多少**，这是误操作的主要来源

| 态 | 表格 | 规则列表 | 表单区 |

| Edge | 超长文本省略 + tooltip；零命中规则高亮提示；大数据量分页 + 虚拟滚动（> 200 行） | 规则数 > 50 时自动折叠 + 虚拟滚动 | 超长文本字数计数 + 上限提示 |

## 10. 无障碍与响应式基本要求

### 10.1 无障碍（a11y）

> 说明：按团队规则，a11y 在设计期只做"不许做错"的底线约束，完整审计在 audit 阶段专项执行。

**对比度（已逐项核算，全部通过 AA）**

| 组合 | 比值 | 结论 |
|---|---|---|
| `--fg` `#131A22` on `--bg` `#F5F7FA` | 15.9:1 | 通过（AAA） |
| `--muted` `#5B6675` on `#FFFFFF` | 5.8:1 | 通过（AA） |
| `--primary` `#1D5A96` 与白字互为正反 | 7.1:1 | 通过（AA+） |
| `--success` `#0F7A48` on white | 5.4:1 | 通过（AA） |
| `--warn` `#B4530A` on `--warn-bg` `#FDF3E3` | 4.6:1 | 通过（AA，临界） |
| `--danger` `#B3261E` on white | 6.6:1 | 通过（AA+） |
| `--meta` `#8A94A3` on white | 3.1:1 | **未达正文标准** → 仅限非必要辅助信息 |

**键盘可达**

- 全流程可纯键盘完成，无鼠标依赖
- 统一 `:focus-visible` 样式：`outline: none; box-shadow: var(--focus-ring)`，3px
- 焦点顺序符合视觉顺序（DOM 顺序 = 视觉顺序，禁止用 `tabindex` 正数打乱）
- 表格支持 `↑/↓` 移动行、`Space` 勾选、`Enter` 打开详情
- **拖动排序必须有键盘等价方案**：聚焦卡片后 `Alt + ↑/↓` 调整优先级，`aria-live="assertive"` 播报位置变化
- Modal / Drawer 打开时焦点陷阱，Esc 关闭，关闭后焦点返回触发元素
- 跳过导航链接（Skip to main content）作为第一个可聚焦元素

**语义与屏幕阅读器**

- 表格用原生 `<table>` / `<thead>` / `<th scope>`，排序状态用 `aria-sort`
- 状态徽章的文字不被图标吞掉（图标 `aria-hidden="true"`，文字保留）
- 纯图标按钮必须有 `aria-label` + Tooltip
- 命中人数等动态更新区域用 `aria-live="polite"`，避免每次刷新都打断朗读（debounce 800ms 已降低频率）
- 错误用 `aria-describedby` + `aria-invalid`
- 表单分组用 `<fieldset>` + `<legend>`（互斥组 = 天然 fieldset）
- 不使用仅靠颜色的信息传达（徽章三件套、微条配 tooltip 数字、删除线配文字徽章）

**动效**

- 全局 `@media (prefers-reduced-motion: reduce)` 规则：动画时长降至 1ms 或改为纯透明度变化，禁用 `transform` 位移与缩放
- 禁止弹跳缓动 `cubic-bezier(0.68, -0.55, 0.265, 1.55)`
- 无自动播放动画；`推送中` 的旋转 loader 属于状态必需，在 reduced-motion 下改为静态图标 + 文字
- 单次动效不超过 400ms；同时动画元素不超过 3 个

**其他**

- 不使用 `user-scalable=no`（允许缩放）
- 语言标注 `lang="zh-CN"`
- 触摸目标（触屏设备）不小于 44×44px

### 10.2 响应式

| 断点 | 宽度 | 布局策略 |
|---|---|---|
| xl（大屏） | ≥ 1536px | 规则页三栏完整（280 / flex / 360）；表格显示全部列 |
| lg（桌面，主战场） | 1024–1535px | 规则页三栏紧凑（240 / flex / 320）；表格 10 列，次要列可隐藏 |
| md（平板） | 768–1023px | 侧边导航收起为 56px 图标栏；规则页右栏预览折叠为**右侧抽屉**，由页面按钮唤起；表格横向滚动 + 首列 sticky |

**响应式纪律**

- **mobile-first 是方法论，本项目的主战场是 PC**：优先保证 1280px 与 1440px 下的完整信息密度，再向下降级
- 手机端不追求功能对等，只保证**查看与轻操作**（查看推送记录、单条重推）；规则配置等重操作在手机上明确提示"建议在电脑端操作"
- 使用 CSS Grid 主流式布局，避免固定 px 宽度导致的横向滚动
- 图片/海报预览使用 `srcset` + 懒加载，预留固定宽高比容器避免 CLS
- 表格在 < 768px 时改为 `定义列表` 形态（每行一张卡片，字段名 + 值上下排列），不做"表格横向滚动 3000px"的事
