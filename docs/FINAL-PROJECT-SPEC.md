# 研选责任盘营销智能推送系统｜最终项目说明

> 文档定位：以 \`demo/index-v3.html\` 的功能原型为依据，供产品、数据、后端、前端联调时作为统一业务说明。
> 当前仓库中的 HTML 是静态 Demo；页面交互、模拟数据和“推送成功”状态不代表已接通生产数据或真实发送通道。

## 1. 项目目标

将目前依赖人工完成的“房屋标签筛选 → 产品/标签映射 → 客群命中 → 海报生成 → 推送清单 → 外部通道发送 → 结果记录”流程，收敛为一套内部营销作业工具。业务人员维护产品和规则，系统基于每日更新的房屋标签生成可核对、可追溯的命中与推送清单，并遵守发送时间和频次限制。

一期以可控的规则营销为主，不建设新的短信/企微通道，不建设电商商品中心，也不把尚未接通的数据包装成实时效果看板。

## 2. 原型页面与生产能力边界

| 页面 | 业务用途 | 生产实现要求 |
|---|---|---|
| 映射配置 | 维护产品包、标签条件、规则优先级和互斥关系 | 读取 \`product_package\`、\`mapping_rule\`、\`tag_dictionary\`、\`tag_value\`；保存后可预览命中结果 |
| 筛选推送 | 查看筛选范围、规则命中房屋和最终待推送清单 | 区分“规则命中”与“通过频控/号码/黑名单后的可推送”；记录筛选批次 |
| 海报配置 | 维护产品海报模板和可个性化文案区域 | 保存模板版本；品牌标识、二维码和固定区域不能被 AI 改写 |
| 定时推送 | 配置执行时间、频控和任务状态 | 只能生成任务或调用已有发送通道；每次调用都必须留存请求与返回结果 |
| 项目说明 | 解释标签来源、房屋明细、线索详情和推送链路 | 明确区分示例数据、T+1 数据与通道真实回执 |

## 3. 最终数据分层

### A. 房屋标签信息：T+1 刷新

- 上游来源：MaxCompute \`weijia.dwd_yanxuan_responsible_project_hosue_label\`。
- 系统目标表：PostgreSQL \`house_label_snapshot\`，一套房屋一行。
- 主关联键：上游 \`code\` 对应系统 \`house_id\`（Pride 房屋编码）；\`house_code\` 保存在 \`zhantu_house_id\`，作为备用关联键。
- 所有已接入的标签值集中保存在 \`labels\` JSONB 字段中，key 使用稳定的系统 \`tag_key\`，多值标签按 JSON 数组存储，数值标签按数字存储。
- 每日全量数据校验通过后更新快照和 \`stat_date\`。必须监控源/目标行数、唯一房屋数、空值率和与近 7 日均值的偏差；异常批次不得进入推送。
- 不把手机号明文写入标签字段；标签快照只保留必要的房屋、组织、标签和受控的联系方式引用字段。

### B. 标签配置：人工维护，不随 T+1 刷新

配置使用两张已有表：

1. \`tag_dictionary\`：定义标签类别、系统 key、显示名称、值类型、上游字段、是否开放给规则搜索器。
2. \`tag_value\`：定义每个枚举类别下允许选择的具体标签值、排序和启停状态。

配置表由业务/管理员维护，不属于每日数据同步范围。新增标签值只增加/更新 \`tag_value\`；新增标签类别先维护 \`tag_dictionary\`，再登记可选值。前端类别和选项应通过 API 读取，不得硬编码在页面。

**边界必须说清：** 仅在配置表登记新标签，不代表上游已有数据，也不代表同步 SQL 已能抽取新物理列。若新增标签来自新的上游字段，必须完成字段探查、数据映射、同步和验收之后，才能把该规则置为可用。

### C. 产品与标签映射：人工维护、按规则计算

\`mapping_rule\` 定义“哪些标签条件命中哪个产品包”，包括条件组合、优先级、互斥组、启停状态和备注。它与“标签字典”不是同一张表：

- 标签字典回答“系统有哪些标签/值可配置”。
- 映射规则回答“满足哪些标签条件时推荐哪个产品”。
- 房屋标签快照回答“这套房今天实际有哪些标签值”。

规则条件存为 JSON，使用受控操作符：多值标签使用 \`contains_any\` / \`contains_all\`，枚举使用 \`eq\` / \`in\` / \`not_in\`，数值使用 \`gte\` / \`lte\` / \`between\`。同互斥组内优先级数字越小越先命中；没有互斥组的规则可独立命中。规则变更需记录操作人、时间和变更前后内容。

### D. 线索详情：按房屋编码查询既有线索源

- 现有线索数据源：ADB PostgreSQL \`yanxuan.ads_yx_clue_full_detail\`。
- 用户打开某套房屋详情时，后端用房屋 Pride 编码优先、战图编码兜底，查询这套房屋关联的线索并按创建时间倒序分页展示。
- 线索查询只读，不在房屋标签宽表中复制线索记录，也不因查看详情而触发整表同步。
- 线索详情至少展示线索 ID、创建时间、项目/服务站、一级/二级意向、是否维修、客户等级、商机状态、来源渠道、最近成交时间和订单数；手机号等不必要的敏感字段不下发给前端。

**数据新鲜度说明：** 当前契约中的 \`ads_yx_clue_full_detail\` 是 T+1 全量快照。因此“实时查询”是指用户打开详情时实时向现有表发起查询，不代表上游线索在产生后立即进入该表。若业务要求秒级/分钟级新线索，需另行确认上游源表或实时接口，不能仅靠修改查询 SQL 实现。

仓库中已有的 \`lead_record\` 可继续用于跑批的线索闸门、频控、归因和运营统计；线索详情页面的读取路径按本方案直接查询既有线索源，避免把镜像表的同步延迟误当成实时数据。

## 4. “命中清单”与“推送清单”必须分开

### 命中清单（规则结果）

展示符合已启用映射规则的全部房屋/规则组合。用于业务验证和解释“为什么命中”，允许同一房屋因不同规则出现多条记录。需要展示：房屋编码、项目、标签值、命中产品、规则名称、优先级、互斥组以及命中时间/快照日期。

### 推送清单（可执行结果）

在规则命中基础上，再应用互斥优选、号码可用性、退订/黑名单、触达时间窗口、同房屋/同产品冷却期、日/周/月次数上限、全局日发送量和已有推送状态。推送清单以“房屋 + 产品包 + 规则 + 批次”为可追踪粒度，并标注未入选原因。

建议原因码至少覆盖：\`NO_MOBILE\`、\`SUPPRESSED\`、\`HOUSE_COOLDOWN\`、\`PACKAGE_COOLDOWN\`、\`DAILY_CAP\`、\`OUTSIDE_WINDOW\`、\`MUTEX_LOST\`、\`RULE_NOT_MATCHED\`、\`SOURCE_NOT_READY\`。原因码由后端统一定义，前端只负责展示。

生成推送任务时必须幂等。同一业务日期不可重复创建两批默认任务；人工重推需要引用原推送记录、记录操作人和原因，并重新执行退订、号码、频控等安全校验，不能简单把状态改回待发送。

## 5. 每日业务流程

1. **T+1 标签同步**：同步任务从上游标签宽表读取数据，映射成 \`house_label_snapshot.labels\`；配置表和产品规则不得被同步脚本覆盖。
2. **数据就绪校验**：检查行数、唯一房屋数、关键字段空值、标签值分布及快照日期；异常时停止自动发送，只允许查看或预览。
3. **规则预览**：根据 \`mapping_rule\` 计算规则命中清单；在预览页核对命中数、互斥冲突和未命中原因。
4. **生成推送候选**：应用联系方式、退订、时间窗和频控规则；达到批次上限后落为正式待发送清单。
5. **海报与审核**：根据产品包和房屋标签套用已发布模板；按业务要求抽查或全量审核。
6. **执行与回执**：调用公司既有触达通道；逐条保存成功、失败、渠道消息 ID、时间和失败原因。
7. **查询与重推**：支持按日期、项目、产品、规则、状态和原因码检索；重推保留完整历史记录。

## 6. 数据库与接口约定

| 对象 | 责任 | 更新方式 |
|---|---|---|
| \`house_label_snapshot\` | 最新房屋、组织、标签快照 | 上游 T+1 同步 |
| \`tag_dictionary\` / \`tag_value\` | 标签类别和值配置 | 人工维护，不由同步作业覆盖 |
| \`product_package\` / \`mapping_rule\` / \`mutex_group\` | 产品包、标签映射规则和互斥优先级 | 业务界面维护 |
| \`push_frequency_rule\` / \`push_frequency_window\` / \`suppression_list\` | 频控、发送窗口、退订/黑名单 | 管理界面维护 |
| \`push_task\` / \`push_detail\` | 批次与逐条执行结果 | 作业创建、通道回执更新 |
| \`yanxuan.ads_yx_clue_full_detail\` | 已有线索明细只读源 | 由上游负责刷新；详情页按房屋编码查询 |
| \`lead_record\` | 跑批闸门、线索归因与统计镜像（如启用） | 独立同步，不作为房屋标签表的一部分 |

建议接口边界：
- \`GET /api/tags\`：返回已启用的标签类别及值。
- \`GET /api/houses\`：按项目、组织、标签、分页检索房屋。
- \`GET /api/houses/:houseId/leads\`：后端查出房屋 Pride/战图编码后查询既有线索源。
- \`POST /api/rules/preview\`：返回规则命中明细与命中统计，不发送消息。
- \`GET /api/campaigns/:id/matches\`：查看完整命中清单。
- \`GET /api/campaigns/:id/push-details\`：查看最终推送清单与执行结果。
- \`POST /api/push-tasks/:id/retry\`：受控重推并写审计记录。

## 7. 必须保留的业务口径与风险提示

- 标签宽表的 \`code\` 是 Pride 房屋编码，\`house_code\` 是战图房屋编码。跨源关联必须明确使用哪一种编码，不按房屋名称猜测关联。
- 环境标签实际枚举值为 **“渗水/返潮”**；家庭结构真实值带 \`A_\` 至 \`E_\` 前缀，展示可去前缀，但匹配使用原始值。
- \`decorate_status = '未装修'\` 在当前上游 SQL 中是缺少装修备案时的兜底结果，不能简单解释为已确认“从未装修”。
- \`house_feature_tags\` / “带浴缸户型”当前未在确认的标签宽表中提供。数据源及字段没有验收前，对应浴改淋规则必须保持禁用，不可用普通户型字段推断浴缸存在。
- 标签快照覆盖率和手机号覆盖率必须作为推送前闸门；敏感手机号须最小化、加密和脱敏，退订必须能阻断后续批次和重推。
- 当前 HTML 演示中的 1,053 户与 1,036 个号码是历史演示批次口径，不可作为生产实时数据或效果承诺。

## 8. SQL 文件说明与验收标准

- \`sql/06_final_rule_engine_and_queries.sql\`：PostgreSQL 规则判断函数、全量命中视图、互斥优选视图、待推送候选查询与数据核验 SQL。
- \`sql/07_live_house_lead_lookup_adb.sql\`：ADB PostgreSQL 从既有线索明细表按房屋双编码查询线索的只读 SQL。
- 既有 \`sql/dw_01_house_label_extract.sql\`：负责 T+1 房屋标签抽取；实施时需确保目标字段与本项目规则函数使用的标签 key 一致。
- 既有 \`sql/01_tag_dictionary_seed.sql\` 与 \`sql/03_mapping_rule_seed.sql\`：初始化配置/规则样例；上线前必须审查样例规则启停状态。

上线验收至少包括：同一快照可重复跑出一致命中结果；配置新增枚举无需改前端；未接入的物理字段不会被误判为已生效；双编码关联覆盖率可量化；退订/冷却期生效；并发跑批不会重复入队；通道失败可定位并安全重推；线索详情只返回请求房屋的数据并正确分页。
