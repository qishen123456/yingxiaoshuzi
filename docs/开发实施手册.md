### 2.2 三条必须遵守的设计约定（违反了后续会返工）

**① 三段式同步：staging（明文）→ merge（加密清洗）→ 主表（密文）**

```
DataWorks 节点 → *_staging（明文手机号短暂存在）
                      ↓  后端 merge 作业
              HMAC 客户键 + AES 加密 → 主表（密文）
                      ↓
              staging 明文列立即清空
```
理由：明文手机号不得落主表、不得进日志。`crypto.util.ts` 注释已明确"明文只允许出现在同步管道/staging"。

**② 日期列 `stat_date` 存"上海自然日的 UTC 午夜"**

不允许用本地时间直接比较。必须走 `backend/src/common/time.util.ts` 的 `shanghaiCalendarDay()`。
理由：Prisma `@db.Date` 按 UTC 日历日编解码，混用会造成跨日偏移（跑批幂等锁失效 / 归因窗口错位）。

**③ `push_detail` 不做分区**

schema 顶部注释明确硬约束：**不使用 PostgreSQL 声明式分区**，用普通表 + `createdAt` 时间索引。
理由：一期数据量级（日 ≤5000 条）用不上分区，且分区会显著增加 Prisma 迁移复杂度。

### W1 · 数据同步上线（最关键，最先做）

**目标**：三个数据源每日自动进库，号码覆盖率可量化。

**怎么做**

1. **DataWorks 侧（数仓同学）**：把 `sql/dw_01~03_*.sql` 配成 3 个数据集成节点，每日 02:00 / 02:10 / 02:30 调度，目标写 RDS PostgreSQL 的对应 staging 表。
   - `dw_01` 源：`weijia.dwd_yanxuan_responsible_project_hosue_label`（MaxCompute，125.7 万行，T+1 全量覆写）
   - `dw_02` 源：住儿 / 企微（ADB PostgreSQL，三源 UNION + 优先级窗口函数）
   - `dw_03` 源：`yanxuan.ads_yx_clue_full_detail`（ADB，~180 列，T+1 TRUNCATE+INSERT）
   - **铁律**：不改上游生产 SQL，只新增同步节点

2. **后端 merge 作业**：检查 `house-sync.service.ts` / `lead-sync.service.ts` 是否满足：
   - 标签多值列（水路/电路/家电/环境）从逗号串**拆成 `string[]`** 存进 `labels` JSONB ← 规则引擎的 `contains_any` 依赖这个
   - 三源号码按优先级 `rich > qywx > crm` 取一条，写 `is_preferred`
   - 线索：算 HMAC 客户键 + 产品包词典识别 + 消失线索打 `stale_in_source`
   - **merge 后必须清空 staging 的明文列**

3. **覆盖率报表**：`ReadinessService.check()` 已实现，把它挂到接口上（`/campaigns` 或新建 `/sync/readiness`）。

**验收**

### W2 · 规则与频控补齐

**目标**：业务能自助配规则、看命中预览；频控可配置。

**怎么做**

1. **规则预览**（`/rules/preview`）—— 契约是**异步任务模式**（POST 建任务返 taskId → GET 查结果）。实现要点：
   - 用 `matchRulesForHouse()` + `selectWinningRule()` 对全量房屋跑一遍，**不要**在请求线程里同步跑 125 万行
   - 返回结构包含：预计命中户数、**组内冲突提示**（哪些规则重叠、谁胜出、重叠多少户）
   - 预览必须只读，不落 `push_detail`

2. **规则拖拽排序**（`/rules/reorder`）—— 批量改 `priority`，同互斥组内重新编号。放事务里做，避免中间态。

3. **频控配置页**（`/frequency-rules`）—— 读写 `push_frequency_rule` + `push_frequency_window`。注意 `PushFrequencyWindow` 有唯一约束 `(frequencyRuleId, dayType, windowStart)`。

4. **节假日跳过**：`holiday_skip` 字段一期默认 `false`，原因是 `BLOCKED_WINDOW` / `HOLIDAY_SKIP` 两个原因码已在闸门里预留。要做就补一张节假日表 + 在 `frequency.guard.ts` 闸门 11 处补齐。

**验收**：单测覆盖 10 个操作符 + 边界（空条件返回 false、`contains_all` 空数组返回 false、互斥组平级按 ruleId 兜底）。

### W3 · 跑批生产化 + 通道对接（**风险最高，卡在外部依赖**）

**目标**：真实发出去、有回执、能停止、挂了会告警。

**怎么做**

1. **真实通道适配器**：新建 `HttpChannelAdapter implements` 同一接口，在 `ChannelAdapter` 里按渠道/产品包路由。
   - **硬约束（写在原注释里了）**：适配器内**不得抛异常**，失败必须返回 `{ok:false, failReason}`，由 runner 逐条落 `failed`——否则一条失败会中断整批，其他业主收不到。
   - `MOBILE_DECRYPT_ERROR` 必须单独识别（密文坏了要告警，不是业务失败）

2. **回执接收**（`/push/callback`）：通道异步回执 → 更新 `push_detail.status` / `channelMsgId`。注意幂等（回执可能重复投递）。

3. **批次停止**（`/push-tasks/{id}/halt`）：置 `push_task.status='halted'` + `haltedAt/haltedBy/haltReason`，runner 每发一批前检查该状态。

4. **失败告警**：`campaign_task.status='failed'` 时推送到企微/邮件。至少覆盖：跑批失败、覆盖率跌破 70%、通道连续失败。

5. **摘除 DRY_RUN**：把 `.env` 的 `DRY_RUN=false`。**前置条件两项同时满足**：覆盖率 ≥70% + 频控合规口径书面认可。

**验收**

```bash
# 小流量灰度：先把 globalDailyCap 调到 20，验证真实通道
docker compose exec db psql -U marketing -d yanxuan_marketing \
  -c "update push_frequency_rule set global_daily_cap=20 where scope_type='global';"

# 触发后检查
docker compose exec db psql -U marketing -d yanxuan_marketing -c "
  select status, reason_code, count(*) from push_detail
  where created_at::date = current_date group by 1,2 order by 3 desc;"
```
关键看：`sent` 有值、`channel_msg_id` 非 mock 前缀、`failed` 有明确 `fail_reason`。

## 5. 十个必须先知道的坑

1. **时区**：任何日期比较都用 `shanghaiCalendarDay()`。直接用 `new Date()` 比较会导致跑批幂等锁跨日失效。
2. **幂等**：`campaign_task.stat_date` 唯一约束就是幂等锁。同日重跑会被拒绝——**失败任务需先置 `failed` 才能重跑**。
3. **密钥同源**：`CUSTOMER_KEY_SECRET` 三处共用（同步 merge、跑批、归因）。换密钥 = 闸门 0 与全部归因失效。
4. **明文生命周期**：手机号明文只允许在 staging，merge 后立即清空；日志里一律打脱敏号 `maskMobile()`。
5. **BigInt 序列化**：`main.ts` 已全局挂 `BigInt.prototype.toJSON`。新写序列化逻辑前先确认，别重复处理导致双重转义。
6. **分页游标**：跑批用 `take: 5000 + cursor` 而非 `offset`。125 万行用 offset 会越跑越慢。
7. **fail-open 只对线索闸门**：线索数据过期（>2 天）时跳过闸门 0a/0b 放行，但**必须告警**（`leadGateState='bypassed_open'`）。号码缺失等其他情况**不 fail-open**。
8. **空条件是危险操作**：`evaluateRule()` 对空条件返回 `false`（不命中）。这是防全量误圈的保护，别改成 `true`。
9. **通道失败不抛异常**：适配器内 catch 一切，返回 `{ok:false}`。抛异常会中断整批发送。
10. **`DRY_RUN` 摘除是双门槛**：覆盖率 ≥70% **且** 合规书面认可，两项缺一不可。
