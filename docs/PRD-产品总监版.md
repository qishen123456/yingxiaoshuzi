## 产品定位

**一句话定义**：把「推谁、推什么、什么时候推、推过没有」四件事，**从个人经验与手工表格，固化为可配置、可预览、可追溯的系统规则**，并由系统每日自动执行。

**要解决的本质问题不是"缺工具"，而是"营销经验无法沉淀"**。当前的圈选标准、产品匹配判断、发送节奏，全部存在于个人员工的经验与手工操作中：

- **无法复用** —— 每次活动都要重新拉表
- **无法审计** —— 配错了查不出原因
- **无法追溯** —— 发完了查不到结果

价值主张：营销管理岗配置一次规则，系统每日自动完成圈选、匹配、生成、发送与归因；日常运营从"执行链路"退到"配置 + 查看结果"。

## 01 现状问题与目标用户

链路被拆成四段独立的人工操作，每段都有结构性断点。

| # | 环节 | 当前做法 | 结构性断点 |
|---|---|---|---|
| 1 | **人群圈选** | 人工用 Excel 按标签筛选目标房屋 | 重复劳动；筛选口径不统一、跨人不可比；易错 |
| 2 | **产品匹配** | 依赖个人经验判断"哪类房屋推哪个产品包" | 经验不可沉淀、不可复用、不可审计；人员变动即断档 |
| 3 | **海报制作** | 逐张手工设计制作 | 无法个性化、无法规模化；产量受人力上限约束 |
| 4 | **触达下发** | 名单整理后交平台批量群发 | **无频次控制 → 重复触达引发投诉与拉黑**；**无发送记录 → 不可追溯、不可补推** |

### 目标用户

**主用户 · 营销管理岗（总部）**
- 职责：维护产品包、配置「产品包 × 标签」映射规则、设定频控策略
- 核心诉求：**规则配一次能长期复用**；不会配错、不会推错人；推完有数据可汇报
- 能力边界：熟练使用 Excel 与后台管理界面，**不具备 SQL 与规则引擎能力**

**次用户 · 大区 / 营业部运营**
- 职责：发起推送、查看执行结果、对重点客户手动重推
- 核心诉求：判断当天推荐是否合理；**未发送的能查到原因**；能对指定对象补推
- 能力边界：熟悉企微与短信后台，能读懂数据表格

## 02 产品链路与自动化机理

七环节链路中，**「映射配置」是本期唯一新增的产品能力**，其余环节由既有数据资产与外部通道承载。

```
标签数据基座 → 人群圈选 → [映射配置] → 推荐匹配 → 海报生成 → 触达下发 → 效果回流(二期)
   125.7万行     按规则筛     产品包×标签    单包收敛    模板套版     频控后下发    归因分析
   T+1 更新       当日目标     优先级+互斥    一户一包    变量填充     走既有通道
```

### 每日自动运行时序（T+1，Asia/Shanghai）

| 时间 | 环节 | 说明 |
|---|---|---|
| 02:00 | 标签同步 | 房屋标签快照入库 |
| 02:10 | 号码补齐 | 三源优先级解析（住儿 > 企微 > CRM） |
| 02:30 | 线索同步 | 全量线索快照，产品包词典识别 |
| 07:30 | **跑批与发送** | 规则圈选 → 频控校验 → 海报生成 → 窗口内下发 |
| 09:10 | 归因回填 | 15 天窗口，首触 / 末触回填 |

**人在环中的位置**：全链路无人值守。人工仅在两处介入——① 配置映射规则与频控策略（低频、一次性）；② 查看执行结果与归因数据（日常）。

跑批具备**按日幂等**能力：`campaign_task.stat_date` 唯一约束，同日重复触发自动拒绝，避免误发。

## 03 三个核心机制

本期系统的产品价值集中在这三个机制上，均已由原型验证。

### A. 映射规则模型

- **实体**：产品包为单一实体，清单由业务方自行维护；**不含** SKU、价格、库存、订单
- **规则结构**：条件（标签表达式）→ 动作（推荐产品包）
- **冲突消解**：优先级排序 + 互斥组；同一房屋、同一周期**收敛为单一产品包**
- **配置体验**：保存前提供命中预览（预计命中户数、组内冲突与胜出规则提示）

### B. 频控模型（P0 一等功能）

- **名单类**：退订名单、黑名单，按**号码与房屋双键**校验
- **冷却类**：房屋冷却 7 天｜产品包冷却 30 天｜线索静默（同包 90 天 / 客户 15 天）
- **频次类**：房屋日 1 / 周 2 / 月 4 次｜全局日上限 5000 条
- **时段类**：可发窗口 10:00–12:00、15:00–18:00｜**22:00–08:00 硬禁发**
- 数据缺失时 **fail-open**（放行并告警），避免因上游断数误停业务
- 全部拦截**落盘并给出原因码**，可解释、可重推

### C. 归因模型

- **窗口**：15 天，固定常量不可配置
- **口径**：首触 / 末触**双模型回填**，明细可追溯至 lead_count
- **数据来源标注**：外部未标注产品包时记为 `inferred`，**不与外部数据混算准确率**
- **口径声明**：「触达」= 发送成功，非已查看；相关 ≠ 因果，看板强制标注

> **合规前置**：频控阈值（冷却天数、日上限、禁发时段）需经业务与合规书面认可后方可正式发送；退订名单必须形成回流闭环，否则不得开启真实触达。

## 04 AI 的角色与边界

本节回答一个必须先对齐的问题：**这个系统的"智能"来自哪里**。

> **结论**：系统的自动化能力来自**规则引擎 + 数据驱动**，而非模型推理。生成式 AI 在本链路中定位为**可选增强**，不承担圈选、匹配、频控、发送等任何主链决策——这保证了结果**可解释、可审计、可复现**，也符合营销场景对"可控"的硬要求。

| 链路环节 | 执行主体 | 产品说明 |
|---|---|---|
| 人群圈选 | **规则引擎** | 规则由业务自行配置，支持保存前命中预览，随时可调整 |
| 产品匹配 | **规则引擎** | 优先级 + 互斥组收敛，同一房屋同期只输出一个产品包 |
| 频控校验 | **规则引擎** | 14 项闸门硬约束，不通过即落盘原因码 |
| 海报生成 | **模板套版**（变量填充 + 图像合成） | 按房屋真实标签自动选择痛点文案并套用模板；单张 20–200ms，边际成本趋近于零，文字零错字 |
| 背景素材生产 | **生成式 AI**（离线 · 可选） | 可用生成式 API 批量产出背景图素材池，**经人工审核后入库**作为模板背景，**不在跑批链路内调用** |

### 决策依据：为什么主链路不采用生成式出图

| 维度 | 生成式出图 | 模板套版（采用） |
|---|---|---|
| **成本** | 约 0.2 元/张；日发 5000 张 ≈ 3 万元/月，成本随发送量线性增长 | **边际成本趋近于零**，复用自有算力 |
| **准确性** | 中文渲染不可控，**存在错字风险**；横幅含小区名、联系方式等零容错字段 | 文本层由变量注入，**零错字** |
| **时延** | 单张数秒（异步任务），无法满足 T+1 单批次产出 | 单张 20–200ms，**单批可分钟级完成** |
| **可回归性** | 同输入不同输出，**问题不可复现**，抽查与验收困难 | 同输入同输出，**可抽查、可验收** |

### 个性化的实现路径

- 「个性化」的诉求被保留，但实现方式从**「模型逐张现画」**调整为**「模板 + 变量逐张组装」**
- 推送内容由房屋**自身标签**决定
- 海报痛点文案取自该房屋**真实标签**（如"墙面发霉"）
- 社会证明仅在**真实数据达标**时展示，禁止编造数字

### 生成式出图的启用条件（满足其一）

1. 单批实验量 ≤ 200 张，且已设定成本上限与人工复核；
2. 用于背景素材池生产，人工审核后入库；
3. 业务明确接受成本与不可复现性，并书面确认。

不满足上述条件时默认不开启，跑批链路中不出现任何生成式调用。

> **二期演进方向**：基于归因结果自动优化规则权重、辅助生成人群定向文案。仍以「人在环上确认」为前提，不引入自动决策。

## 05 范围边界与成功指标

### 一期范围（In Scope）

- 三源数据接入 + 映射规则配置（优先级排序、命中预览）
- 每日跑批 + 14 项频控闸门 + 发送时间窗口
- 模板套版个性化海报（零错字，边际成本趋近于零）
- 推送明细、原因码分布、单条重推、批次停止
- 短信 / 企微通道对接（由外部通道团队拉通）
- T+1 归因看板

### 一期明确不做（Non-goals）

- 生成式 AI 出图进主链路（降级为可选背景素材池）
- 点击 / 短链归因（依赖通道能力，待通道团队确认）
- 撤回已送达短信（物理不可行，产品不承诺）
- AI 自动调规则、无互动自动降频、多包同推
- 自建 CDP / MA 平台级能力（出价、跨渠道归因建模）
- 改动上游生产数据仓库（生产 SQL 零改动，仅新增同步节点）

### 成功指标

| 层级 | 指标 | 定义与口径说明 |
|---|---|---|
| **北极星** | 单位触达的线索产出 | 归因窗口内产生的去重线索数 ÷ 成功触达数，仅统计同口径数据源 |
| **过程指标** | 号码覆盖率 | 可解析出有效号码的房屋占比，**≥70% 为发送前置门槛** |
| | 规则命中率 | 命中任一规则的产品包候选房屋占比，用于评估规则覆盖度 |
| | 拦截率与原因码分布 | 按 14 类原因码分布，用于定位是数据缺口还是频控生效 |
| | 发送成功率 / 重推率 | 通道回执成功占比；人工重推占比反映规则与数据质量 |

> **验收门槛（DRY_RUN 摘除条件）**：号码覆盖率 ≥ 70% 且频控合规口径获书面认可，两项同时满足方可开启真实发送；覆盖率未达标时系统仅生成待发送清单、不执行发送。

## 06 外部依赖、风险与待决策项

### 外部依赖

| 依赖项 | 归属方 | 状态与影响 |
|---|---|---|
| T+1 标签数据同步 | 数据团队 | 同步方式待架构确认；未就绪时跑批自动中止并告警 |
| 短信 / 企微通道对接 | 外部通道团队 | 通道存在已确认，接口标准待拉通；影响发送层与点击归因可行性 |
| 海报素材与品牌规范 | 业务 / 设计 | 未提供时模板规格无法冻结，海报页仅能占位 |
| 产品清单与产品包定义 | 业务方 | 业务自行维护，系统不介入 |

### 主要风险

- **R1 通道能力未确认**：是否支持回执、带参短链直接决定点击归因能否纳入一期
- **R2 上游数据缺口**：「浴改淋」产品包依赖的户型标签数据源未接入，系统已**锁定该包不可启用**
- **R3 合规闭环未定**：营销授权来源与退订回流方式未确认，**缺失则不能正式发送**
- **R4 素材未定**：海报模板规格无法冻结，影响 M2 交付
- **R5 需求实现方式变更**：海报由"AI 生成"调整为"模板套版"，**需书面确认以防验收争议**
- **R6 覆盖率不达标**：号码覆盖率若长期低于 70%，系统将持续处于"只出清单不发送"状态

### 待决策项（阻塞开发，需会上闭环）

| # | 事项 | 需要的结论 | 决策人 | 不决策的后果 |
|---|---|---|---|---|
| 1 | 通道接口协议 | 同步/异步、回执机制、带参短链、限流配额的接口文档 | 外部通道团队 | 发送层无法对接；点击归因可行性悬置 |
| 2 | 海报素材来源 | 模板与素材由业务方或设计方提供、明确交付时间 | 业务 / 设计 | 模板规格无法冻结，海报页只能占位 |
| 3 | 海报方案降级确认 | 接受「模板套版」替代原始诉求「生成式 AI 海报」，需书面确认 | 业务负责人 | **需求实质变更未签字，存在验收返工风险** |
| 4 | 单包输出确认 | 确认一个周期内单套房屋仅推送一个产品包 | 业务负责人 | 若需多包同推，规则模型与频控需返工重做 |
| 5 | 频控合规口径 | 冷却 7/30 天、日 1 条、禁发时段等默认值获合规认可 | 业务 / 合规 | 阈值无合规背书，短信通道存在封号风险 |
| 6 | 退订授权与回流 | 营销授权来源、退订入口、退订名单回流方式 | 业务方 | **合规命门，无退订闭环不得正式发送** |
