## 三、发现并修复的缺陷（7 项，全部已闭环）

### D1【阻塞】「停止发送 / 撤回」设计承诺与后端契约断裂
- **发现人**：team-lead
- **证据**：`UIUX §1.3` 将中止定义为**必备入口**并与手动重推等权重；`§8.3` 推送记录表格含「撤回」按钮；`§8.3` 定义「已撤回」状态；`§9.5` 列入 Destructive 操作。而 `ARCHITECTURE` 与 `openapi.yaml` 中 revoke/cancel 相关端点 **零命中**。
- **根因**：该动作能否实现取决于外部通道是否支持中止，依赖未确认——**但设计与实现都没有区分"系统层能做什么"与"通道层能做什么"**。
- **修复**：拆为两个独立能力。
  - **停止发送**（系统层，**确定可做**）：停 `queued` 与在途明细，已实现 `POST /push-tasks/{id}/halt`；请求体 `reason` 必填 / `channelRecall` 默认 false；批次已结束返回 `40900`；**不可逆**；写审计 `push.halt`。
  - **撤回已送达**（通道层，**物理不可行**）：短信不可召回；企微的中止窗口是「人工确认才送达」的链路特性，非通用能力。UI 不出现、不承诺。
- **状态**：**已闭环**。UI 全文统一为「停止发送」，禁用「撤回/召回/撤销推送」；`channelRecall` 默认不渲染（不渲染不生效的开关）；停止量**不计入失败**（用户决策 vs 系统异常）。

### D2【静默正确性】优先级数值方向三方相反
- **发现人**：PM
- **证据**：PRD 原写「数值越大越优先」；架构实现是「`priority` 最小者优先」；设计师拖动列表是「越靠上越优先」。
- **危害**：按 PRD 字面配置规则，系统会选出**完全相反**的产品包——**不报错、不告警，静默给出错误推荐**。这类缺陷比崩溃危险得多。
- **裁决**：统一为 **`priority` 升序，数值越小优先级越高，1 = 最高**。
- **理由**：UI 是拖动排序列表，第一行必然最高优先、序号自然从 1 递增；改为「越大越优先」会让第一行显示 8、最后一行显示 1，序号与视觉位置反向。架构已是 `min` 实现、设计也是「越靠上越优先」，2:1，改 PRD 一处成本最低。PM 主张的"主流规则引擎惯例"（如 Drools salience 越大越优先）成立，但那是**数值型属性**的惯例；**排序列表的惯例是第一行优先**。
- **状态**：**已闭环**。PM 全文扫除 6 处反向残留（求解规则 / 场景故事 / EARS 验收 / 端到端验证 / R8 风险表）；设计师在**表头**（非横幅）加显式说明「列表自上而下优先级由高到低，命中即停」，并采用「序号 `#01` + 只读诊断数字 `P10`」双显式；架构确认 `/rules` 返回 `priority ASC`、`reorder` 按序重写。

### D3【静默正确性】频控回看窗口固定 30 天，致长冷却期失效
- **发现人**：PM
- **证据**：架构原设 `lookback_days` 固定 30 天，而 `package_cooldown_days` 取值 1-180。配成 90/180 天时，历史推送记录落在窗口外 → **长冷却期静默失效、同一产品包被重复推**。
- **裁决**：**取消 `lookback_days` 配置项**（不采用"自动取 max"，因为只要留旋钮就可能再被误配）。改为**各维度按自身语义独立查询**。

| 维度 | 查询内容 | 窗口 |
|---|---|---|
| 房屋冷却 | 该房屋对**任意**产品包的最近一次推送时间 | `houseCooldownDays` |
| 产品包冷却 | 该房屋对**该产品包**的最近一次推送时间 | `packageCooldownDays` |
| 日 / 周 / 月上限 | 该房屋近 1 / 7 / 30 天推送次数 | 1 / 7 / 30 天 |

- **状态**：**已闭环**。配置项删除；内部物理扫描上限只允许动态推导为 `max(所有生效冷却期, 30)` + 缓冲，**不得写死、不得对用户暴露**；UI 改为只读派生展示（`effectiveLookbackDays`）。已沉淀为设计原则：**界面上不提供"看起来能配、实际会引发不一致"的旋钮。**

### D4【结构缺失】频控表缺月度维度与多时段能力
- **发现人**：team-lead
- **证据**：架构 `push_frequency_rule` 只有 `house_max_per_day` / `house_max_per_week`，**缺月度上限**；`send_window_start` / `send_window_end` 为单对字段，**只能表达一个时段**，而 PRD 要求「10-12 / 15-18」多段。附带默认值冲突：房屋冷却 PRD 写 7 天、架构写 15 天。
- **修复**：时段抽为独立子表 `push_frequency_window`（一对多，`day_type` 分策略、支持 `cross_day` 跨天段、保存自动合并重叠）；补 `houseMonthlyCap`；字段名与 PRD **逐字对齐**。另新增顺延机制：`push_detail.status` 增 `deferred`（区别于 `suppressed`＝拦截不自动重发）+ `deferredUntil` + `deferCount`（连续 >3 次告警）；统一 `reasonCode` 覆盖 11 种原因码，明细可按原因筛选。
- **状态**：**已闭环**。默认值全端一致：房屋冷却 **7** 天 / 包冷却 30 天 / 日 1·周 2·月 4 / 全局日上限 **5000**（100-100000，可按渠道大区配）/ 时段默认 `[10:00-12:00, 15:00-18:00]` / `blockedWindows`（22:00-次日 08:00）为**代码级硬编码常量**（不入库、不可配置、不可关闭、重推不可越过，UI 仅只读展示）。

### D5【契约缺口】PRD 要求的两项频控能力无对应字段
- **发现人**：设计师
- **证据**：PRD 要求的 `batchThrottle`（分批节流）与 `no_engagement_pause`（无互动降频），在 `FrequencyRule` schema 中无字段，`reasonCode` enum 中无 `ENGAGEMENT_PAUSED`。
- **裁决**：两项均降为 **P1（一期不做）**。
  - `batchThrottle`：属**通道限流保护，非业务策略**。暴露给运营只会增加误配面（配错会导致发送被通道拒或压垮通道）。改为系统内部按 `globalDailyCap` 与通道能力自决，**不设配置项、UI 不暴露**。
  - `no_engagement_pause`：进阶能力，用户明确定位「这是一个小的系统功能」，一期不做。
- **关键约束**：**不得新增字段、不得新增 `ENGAGEMENT_PAUSED` 原因码**。因为一旦 enum 里出现该值，前端可能去渲染它，引入"配了但不生效"的面——正好违反 D3 沉淀出的那条原则。
- **状态**：**已闭环**。契约保持 11 个原因码不变；PM 将两项从 P0 移至 P1，并从 EARS 验收中同步移除（避免 QA 拿 P0 标准测一个不做的功能）。

## 五、流程教训（写入团队记忆）

1. **引用文档用章节号，不用行号**：初检版本引用的 4 个行号在文档演进后全部失效，复核时无法定位。本文档已全面改为章节号。
2. **并行多方场景下，术语必须先行统一定义**：D1 的根源是「停止发送」与「撤回」两个不同层级的能力被当成了同一个。若在派发前先把关键术语（尤其是易混概念）定义清楚，可省一整轮返工。
3. **静默错误比崩溃危险**：D2（优先级反向）与 D3（冷却期失效）都不报错、不告警，只是悄悄产出错误结果。**评审重点应放在"能跑通但结果错"的路径上**，而不是"跑不通"的路径。
4. **消灭配置项优于让配置项更聪明**：D3 的两个候选方案都是"让窗口自动推导"，最终选择**直接删掉旋钮**——因为只要旋钮存在，误配就会再发生。同理 D5 拒绝新增 enum 值，避免引入"配了不生效"的面。
5. **成员互查比单人自查有效**：本轮 4 个真实缺陷中，3 个由成员互查发现（PM 查架构 2 个、设计师查契约 2 个），1 个由 team-lead 发现。交叉复审是必要机制，不是流程冗余。

## 一、本轮设计基线（team-lead 裁定）

用户诉求中隐含一个关键概念误区需要先澄清——**"要不要埋点"必须分层回答**：

| 层 | 数据 | 获取方式 | 归属 |
|----|------|----------|------|
| 第一层 发送 | 发了什么包、给谁、何时 | 系统自有记录 | 无需埋点 |
| 第二层 点击触达 | 点没点、翻没翻 | 短信带参短链 / 通道回执 | **需要埋点，但依赖外部** |
| 第三层 线索 | 留没留资、质量几级 | 外部销售系统 T+1 回填 | **不是埋点，是回填** |

裁定要点：

1. 新增 **闸门 0「线索静默」**，优先级高于现有全部频控闸门：同产品包已有线索 → 包级冷却 90 天；该客户有其他产品线索 → 客户级冷却 15 天
2. 线索表含 `first_touch_push_id` + `last_touch_push_id` **双归因字段**，看板同时出首触/末触两口径，不押注单一算法
3. 归因窗口 **15 天固定常量、不可配、不分通道**
4. 线索静默 **不可被手动重推覆盖，一期不留任何覆盖通道**
5. 归因置信度 **不做数值字段**（个体级置信度是运营噪音），后端为二值逻辑：推断成功→包级冷却，推断不出→只走客户级冷却
6. 分层范围：线索回填 / 最近线索时间 / 有线索不发 / 基础效果看板 = **一期 P0**；点击埋点 = **条件性 P0**（通道支持带参短链+点击回传则一期做，否则 P1 并如实标注数据缺口）

### 1.1 本轮的两次自我推翻（留痕）

| 事项 | 初版基线 | 定稿 | 推翻依据来源 |

## 二、本轮发现并修复的缺陷（6 项，全部已闭环）

### D8【静默正确性｜命名】同一个闸门三方三个名字
- **发现人**：team-lead（逐份比对时发现）
- **证据**：PM 写 `LEAD_SILENCE_PACKAGE` / `LEAD_SILENCE_GLOBAL`；架构师写 `LEAD_PACKAGE_COOLDOWN` / `LEAD_RECENT`；设计师以契约为准。
- **危害**：不只是命名难看。`LEAD_SILENCE_GLOBAL` 的 "GLOBAL" 与既有 `GLOBAL_CAP_DEFERRED`（系统级总量上限）撞车——**运维会把「某个客户被锁」误读成「系统被打崩」**；且该闸门真实作用域是客户/房源级，不是全局。
- **裁决**：遵循既有 `{SCOPE}_{LIMIT_TYPE}` 约定，定稿 `LEAD_PACKAGE_COOLDOWN` + **`LEAD_HOUSE_COOLDOWN`**（`LEAD_RECENT` 因语义模糊作废）。**原因码总数 = 13（既有 11 + 新增 2）**，`HOLIDAY_SKIP` 计入既有。
- **状态**：已闭环。四方逐字符一致，旧名零残留。

### D9【静默正确性｜口径】归因窗口短于冷却期，造成"未归因空窗"
- **发现人**：架构师（advisory A2）
- **证据**：归因窗口 7 天 < 客户级线索冷却 15 天。
- **危害**：线索在冷却期内产生时，往前回溯 7 天可能找不到任何一次推送 → 该线索无人认领，但冷却照常生效。表现为归因覆盖率异常偏低，且业务无法解释。**不报错、不告警。**
- **裁决**：窗口改 **15 天常量**，与冷却期数值对齐；但两者**语义不同源**——冷却期是闸门规则（决定发不发），归因窗口是统计口径（决定一条线索算给窗口内哪几次推送），**不得互为约束**。该口径说明要求写入看板文案。
- **状态**：已闭环。四文档一致；ADR-011 与 PRD §12.5 均含"对齐但不同源"说明。

### D10【契约缺口｜反向 P8】界面已做输入控件，契约缺字段 → "能改但不生效"死控件
- **发现人**：team-lead（按架构师回传逐条核验时发现）
- **证据**：设计师在 §8.4-H 按"只含契约字段"原则为线索静默期做了 2 个数字输入框 + 1 个风险单选；而 `openapi.yaml` 的 `FrequencyRule` 只有 `houseCooldownDays` / `packageCooldownDays`，**线索静默期 3 个字段不存在**。
- **危害**：运营能改、后端不读、**且不报错**。这是 D3（`lookback_days`）的镜像形态——D3 是"有旋钮没逻辑"，D10 是"有控件没字段"。
- **裁决**：契约补齐 `leadPackageCooldownDays`(90/1–365) / `leadHouseCooldownDays`(15/1–90) / `leadGateFailMode`(`open`/`closed`)。**字段名必须与原因码对齐**，不得沿用已作废的 `leadRecentDays`。
- **状态**：已闭环。契约与界面字段名、默认值、范围逐字一致。

### D11【契约缺口｜枚举不齐】包来源字段与枚举值三端不一
- **发现人**：team-lead + 架构师（架构师交叉核验时另报出枚举差异）
- **证据**：① `external_package_code` / `package_source` 两字段未写入 ARCHITECTURE 与 openapi，而 PRD / UIUX 已依赖（**设计师在自己的文档里显式标注了"契约待同步"，做法正确**）；② PRD 的 `package_source` 只列 `external` / `inferred` 两值，其余三份为三值（缺 `none`）。
- **危害**：缺字段 → 看板"未映射占比"无字段依据；缺枚举 `none` → 无法表达"该线索无法归属到任何产品包"。
- **裁决**：补三字段 `external_package_code` / `package_source`(`external`/`inferred`/`none`) / `package_id`；**且 `none` 必须拆两个子口径**——① 有码对不上字典（集成问题）② 无码（上游缺失），区分依据是 `external_package_code` 是否为空，**不得合并**（合并后看板读者不知道该去找谁）。
- **状态**：已闭环。四文档枚举与判定链一致。

### D12【结构｜过期声明】范围声明与一期实际范围矛盾
- **发现人**：team-lead
- **证据**：`ARCHITECTURE.md` 开篇范围声明与 §1 Out-of-Scope 仍写「不做效果回流」，而一期已包含线索回流与效果看板。
- **危害**：后续开发按错误范围裁量，可能把已定的 P0 当二期做。
- **状态**：已闭环，两处均已更新，旧句零残留。

### D13【流程｜回传失真】成员回传"已全部完成"，实际 4 项不在文件里
- **发现人**：team-lead（逐条核验）
- **证据**：架构师回传称 4 处漏项已改完，但按行号比对，文件内**不存在**对应内容。
- **危害**：**比漏做本身更危险**——它会让我跳过核验。若这次只读结论不核验，D10 / D11 / D12 会一路带到 Phase 3 联调才暴露。
- **处置**：要求后续回传一律「逐条 + 文件行号」给证据，**未完成直接写"未完成"，禁止用"已完成"含糊带过**。整改后再回传时行号证据准确，已通过核验。
- **状态**：已闭环（纪律层面）。

## 三、工程事实沉淀（与文档目标态的偏差，后续以此为准）

1. **运行时加载器：SWC，不是 tsx**。tsx/esbuild 不发射 `design:paramtypes`，Nest 构造注入全部 undefined（启动即报 `Cannot read properties of undefined (reading 'houseLabelStaging')`）。统一用 `@swc-node/register` + 根目录 `.swcrc`（commonjs + legacyDecorator + decoratorMetadata），全部 npm scripts 已切换。
2. **PG 宿主端口 5434**（非 5433）：本机 5433 被 smartask-postgres 长期占用。库 `yanxuan_marketing` / 用户 marketing；因目录名含中文，docker compose 项目名派生失败，必须显式 `docker compose -p yanxuan-marketing`。
3. **时区口径（两处反直觉，均已在 `common/time.util.ts` 收口）**：
   - Prisma `@db.Date` 按 UTC 日历日编解码、与 PG 会话 timezone 无关——传东八区午夜会存成前一天。所有写 date 列处必须用 `shanghaiCalendarDay()`（Intl en-CA 取上海年月日再构造 UTC 午夜）：跑批 stat_date/deferredUntil、就绪校验 today、归因 today、demo 脚本。
   - Prisma `@db.Time` 读回为 UTC Date（业务 10:00 → 1970-01-01T10:00:00Z），窗口判定必须用 `getUTCHours/getUTCMinutes`；"当前上海墙上时间"用 `shanghaiMinutes()`（Intl en-GB, Asia/Shanghai）。禁发/可发窗口、下一窗口起点均按此口径。
4. **模块命名与架构 §12 目标态的差异**（实现取舍，语义不变）：`campaign→campaigns`、`push→push-records`、`lead` 同步在 `sync/lead-sync.service`、归因在 `attribution/`；新增 `catalog`（产品包/标签只读）与 `readiness.service`（就绪三态：标签/线索闸门/号码覆盖率 0.70）。Phase 2 增补 `audit`、客户线索时间线。
5. **加密与数据卫生**：`MOBILE_ENC_KEY_BASE64` 必须解码为恰好 32 字节（原默认值 33 字节会 AES Invalid key length，开发环境已换随机 32 字节值）；`suppression_list.target_type` 宽 16，客户键哈希统一写 `mobile_hash`（`customer_key_hash` 18 字符超长）；线索 merge 后物理删除 staging 明文手机号。
6. **人工中止不占用业务原因码**：queued/deferred 中止只写 `failReason=MANUAL_HALT`、reasonCode 留空，保证 14 原因码枚举纯净（前端以 failReason 识别并显示「人工中止」）。
7. **前端最小骨架结构**：未引入路由/状态管理/代码分割（四页 Tabs 单页，`api.ts` 统一 fetch 封装，`reason-codes.ts` 为 14 码文案/六组配色唯一来源）；主题经 ConfigProvider token 注入 #1D5A96，Lucide 图标零 emoji，demo/index.html 色板同步为墨钢蓝阶（#1D5A96/#3A73B0/#E8F0F8/#9DBBD6）。dev 期 /api 经 Vite proxy 到 :3000。
8. **@updatedAt 与裸 SQL 种子**：Prisma `@updatedAt` 不提供 DB 层默认值，裸 SQL 插入种子会违反非空约束；四处 updated_at 已补 `@default(now())`（ProductPackage/MappingRule/DailySendCounter/LeadRecord）。
