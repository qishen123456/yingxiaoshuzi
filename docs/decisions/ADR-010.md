# ADR-010: 以 OpenAPI 3.0 规范作为前后端唯一契约

## Status

Accepted (2026-09-18)

## Background

本系统前后端并行开发，涉及约 40 个端点（产品包、标签、规则/互斥组、跑批、推送明细/重推、频控、名单、海报模板、回执回调、审计）。若无单一契约，前后端字段/错误码会漂移，产生大量返工。

候选：

| 候选 | 单一事实源 | 工具链 | 团队成本 |
|------|-----------|--------|----------|
| OpenAPI 3.0 文件（openapi.yaml） | 强 | 类型生成、Mock、文档、校验 | 低 |
| 手写 API 文档（Markdown） | 弱（易漂移） | 无 | 低 |
| 代码优先（注解自动生成） | 中（易与实际不符） | 中 | 中 |

## Decision

选择 **OpenAPI 3.0.3 文件 `docs/openapi.yaml` 作为前后端唯一契约**。

约定：
- 所有端点必须带版本前缀 `/api/v1/`；MVP 只有 v1，后续不兼容变更新增 `/api/v2/`，v1 至少兼容 6 个月。
- 统一响应包裹 `{ code, data, message }`；错误码见 ARCHITECTURE §9。
- 前端据此**生成 TypeScript 类型**并配置 MSW Mock；后端据此实现与联调；变更必须先改 `openapi.yaml`，经 team-lead 同步前后端。
- 认证统一 `Authorization: Bearer <jwt>`；分页统一 `{ items, total, page, limit, hasMore }`。

## Consequences

正面：
- 前后端以同一份 schema 对齐，字段/错误码不漂移。
- 可直接生成类型与 Mock，加速并行开发；可用 swagger-ui 做接口文档。

负面：
- 契约变更需同步更新 `openapi.yaml` 并通知前后端（流程成本）。
- 需维护生成类型与手写逻辑的一致性（门禁：类型检查必过）。
