# ADR-001: 使用 NestJS 11 + TypeScript 作为后端框架

## Status

Accepted (2026-09-18)

## Background

本系统是「标签圈人 → 映射匹配 → 海报生成 → 触达下发」的营销闭环后台，核心复杂度在**配置化规则 + 每日定时跑批 + 严格分层**，不是高并发网关。团队级 P0 规则要求后端必须落地「routes/controllers → services → repositories 依赖只向下、单文件 ≤300 行、入口只装配零业务」。同时用户明确「这是一个小的系统功能」，不上微服务。

候选方案：

| 候选 | 版本 | 学习成本 | 分层强制力 | 生态 | 部署成本 |
|------|------|----------|-----------|------|----------|
| NestJS | 11.2.x / Node.js 22 LTS | 中 | 高（DI + Module） | 高 | 低 |
| FastAPI | 0.11x / Python 3.12 | 中 | 中（需自律） | 高 | 低 |
| Express 5 | 5.x / Node.js 22 | 低 | 低（需自律） | 高 | 低 |

## Decision

选择 **NestJS 11.2.x + TypeScript 5.x + Node.js 22 LTS**，ORM 用 Prisma。

理由：
1. NestJS 的 Module/DI 结构天然映射 P0 分层规范，`controller` 与 `service` 边界由框架强制，降低「把业务写进路由」的失效风险。
2. `@nestjs/schedule` 提供定时任务能力，跑批无需额外基础设施。
3. TypeScript 全栈统一，后端 DTO/类型可与前端复用，减少前后端契约漂移。
4. FastAPI 作为首选备选（若团队 Python 能力更强，或后续要重度使用 Python 数据生态）；Express 5 作为最轻量备选（若确需极简，但需自行保证分层纪律）。

## Consequences

正面：
- 分层与代码组织规范天然对齐，Phase 3 门禁（入口无业务、单文件 ≤300 行）更易通过。
- 单体应用、单容器部署，符合「不做微服务」的约束。

负面：
- NestJS 相对 Express 有装饰器与 DI 的学习成本。
- 装饰器 + DI 在测试时需要 mock provider，比纯函数式框架稍重。
