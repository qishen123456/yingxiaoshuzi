# ADR-008: 规则引擎采用内存全量评估 + 优先级/互斥组归并

## Status

Accepted (2026-09-18)

## Background

用户已拍板：映射规则必须支持【优先级】+【互斥】，「多个产品包命中同一客户时按优先级取一；互斥组内只能命中一个包」，且需**可视化配置与命中预览**。数据量：约 125.7 万房屋 × 规则数（预估几十~几百）。

候选：

| 候选 | 表达力 | 性能 | 运维 | 适用性 |
|------|--------|------|------|--------|
| 内存全量评估（规则加载进内存，逐行短路求值） | 满足 | 秒级–分钟级 | 极简 | 选中 |
| 数据库 SQL 关联（规则展开为 SQL 条件） | 受限于 SQL 动态拼接 | 中 | 中 | 备选 |
| 规则引擎库（如 json-rules-engine / Drools） | 强 | 中 | 中 | 过度设计 |

## Decision

选择 **内存全量评估 + 优先级/互斥组归并**（纯函数实现，置于 `src/engine/`，无 IO，便于单测）。

算法：
1. 一次性加载 `status=enabled` 的规则与互斥组，按 `priority` 升序（数字小=高优先）。
2. 分页读取房屋标签（每批 1 万），逐行评估 `condition_json`（AND 组合，短路求值）。
3. 先按**互斥组**归并：同组内只保留 `priority` 最小者。
4. 在剩余候选中取 `priority` 最小规则的 `package_id` 作为推荐。
5. 平级以 `rule_id` 升序兜底，保证**同输入同输出**（可回归）。

条件结构：`{ logic: AND, conditions: [{ tag, op, value }] }`，操作符 `eq/neq/in/not_in/gte/lte/between/exists`。MVP 只做 AND（OR 字段预留但不推荐，避免规则互相掩盖、不可解释）。

命中预览：`POST /rules/preview`，抽样模式（如随机 5 万条）同步秒级返回；全量预览异步返回 `preview_task_id` 轮询，并给出与更高优先级规则的**冲突提示**。

性能：6250 万次简单布尔评估，Node.js 单核约 30 秒–3 分钟；若不足，可用标签倒排（`label -> house_id set`）预筛，或分片并行。

## Consequences

正面：
- 规则表达与业务语义（优先级 + 互斥）一一对应，可解释、可回归。
- 纯函数引擎，测试与预览都便宜。

负面：
- 规则数若增长到数千级，全量内存评估需优化（倒排预筛 / 分片），但当前量级无需。
- 只支持 AND 组合是刻意限制，复杂 OR 需求需通过拆规则 + 优先级表达。
