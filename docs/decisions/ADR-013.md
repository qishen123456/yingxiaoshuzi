# ADR-013: 线索与推送的关联键采用「归一化手机号 HMAC-SHA256」并定义三级降级

## Status

Accepted (2026-09-18)

## Background

闸门 0（线索静默）与效果归因都要把**外部线索**与**本系统 `push_detail`** 关联到「同一个人」。但两侧数据来源不同：
- 推送侧基于 `house_id`（房源）圈人，触达对象是房主/客户，手机号在推送执行时可得。
- 线索侧来自外部线索系统，字段取决于对方系统。

可用的「人」标识候选：

| 候选 | 问题 |
|------|------|
| 明文手机号 join | 合规风险（个人敏感信息落库/跨系统传输明文） |
| 随机 IV 加密手机号 | **致命**：随机 IV 每次加密结果不同，**无法用于 join**，会导致关联恒为空、闸门与归因静默全 0 |
| 归一化手机号 + 确定性 HMAC-SHA256 | 相同输入恒定输出，可 join；不可逆，合规友好 |
| 统一客户 ID（外部提供） | 最理想，但取决于对方系统是否具备 |

核心风险：关联键若选错（如随机 IV 加密），系统**不会报错**，只会「查不到 → 放行全部」，表现为「闸门 0 从不拦截、归因为 0」——这是最危险的**沉默逻辑错误**。

## Decision

**首选以「归一化手机号的 HMAC-SHA256」作为 `customer_key`（`customer_key_type = phone_hmac`）**，并定义三级降级。`customer_key` 与 `push_detail.customer_key_hash` **必须使用同一归一化规则与同一密钥**。

归一化规则（双方必须一致，写死为契约）：
1. 去空格、去连字符；
2. 去国际前缀 `+86` / `86`（仅保留 11 位大陆号）；
3. 空值不参与关联（不得以空串哈希造成大量误关联）。

三级降级：

| 级别 | 条件 | `customer_key` 构造 | 闸门 0 / 归因能力 |
|------|------|---------------------|-------------------|
| 一级（推荐） | 两侧均有手机号 | `HMAC-SHA256(归一化手机号)` | 精度最高，个体级判定可用 |
| 二级 | 线索只有手机号、推送侧只有 `house_id` | 手机号哈希做**弱关联**；手机号缺失则退化为按 `house_id` 关联 | 弱关联，覆盖不全，看板须标注 |
| 三级（不得假装可用） | 完全拿不到客户级键 | `customer_key` 无法建立 | **闸门 0 不可实现 -> 必须关闭并告警**；线索只能做**包级/批次级宏观相关性**，看板显著标注「弱归因/包级归因，不可用于个体判定」 |

**前置确认项（blocking-external，未答复前按三级处理）**：
- 线索系统是否提供手机号或统一客户 ID？
- 归一化规则与 HMAC 密钥能否双方对齐？

## Consequences

正面：
- 关联键确定性、可 join、不可逆（合规）。
- 三级降级明确了「拿不到数据时系统应如何表现」，避免沉默全 0。

负面：
- 归一化规则与密钥**必须双方对齐**，任何一侧不一致都会导致关联失败——因此登记为 blocking-external 前置项，未确认前不得宣称闸门 0 已生效。
- 手机号归一化对境外号/多号用户覆盖有限（一期按大陆 11 位手机号假设）。

**铁律**：关联键不一致导致的关联失败**必须可见**（闸门按 `lead_gate_fail_mode` 告警、看板标注），禁止任何情况下静默跳过。
