# ADR-007: 标签数据经 DataWorks 数据集成同步至 RDS，本系统只读库

## Status

Accepted (2026-09-18)

## Background

核心宽表 `weijia.dwd_yanxuan_responsible_project_hosue_label` 约 125.7 万行、T+1 更新，另有若干上游表可作补充。需要把数据送达本系统供每日跑批消费。

候选：

| 候选 | 全量可行性 | 跑批耦合 | 成本 | 稳定性 |
|------|-----------|----------|------|--------|
| DataWorks 数据集成 → RDS PostgreSQL | 可行（并发通道，分钟级） | 低 | 低（同 VPC 内网） | 高 |
| DataWorks 导出 → OSS CSV → 本系统导入 | 可行 | 中（自建导入） | 低 | 高 |
| 本系统直连 MaxCompute（pyodps / Tunnel） | 勉强可行 | 高（每次全表扫描） | 高 | 低（会话易超时） |

## Decision

选择 **DataWorks 数据集成定时同步 MaxCompute → RDS PostgreSQL，本系统只消费库内快照**（主方案）；**OSS CSV 中转导入为备选**（若 DataWorks 资源组受限或需留档）。

实现要点：
- 为每张需要的上游表各建一个**批量同步节点**（DataWorks 官方限制：一个节点只能导一张表）。
- 写入用 `INSERT ... ON CONFLICT (house_id) DO UPDATE` 覆盖最新快照，不存历史全量。
- 同步完成写 `synced_at` 与 `stat_date`；跑批启动时先校验当日快照就绪，未就绪返回 `40900` 而非静默空跑。

理由：
1. **解耦**：MaxCompute 抖动不影响系统可用性，跑批只读本地 PG，性能可预期。
2. **成本**：同地域同 VPC 走内网，无公网流量费；125.7 万行在并发通道下分钟级完成。
3. **直连被否决**：MaxCompute 面向批量分析而非高并发点查；每次跑批全表扫描既慢又烧计算资源；Tunnel 下载会话有生命周期，长任务会报 `download session is expired`（阿里云官方 FAQ 明确说明）。

已知坑（写进实现）：
- RDS 默认不开公网，DataWorks 与 RDS 须同 VPC，并把数据集成资源组所在交换机网段加入 RDS 白名单，否则连通性测试失败。
- 同步任务「脏数据」阈值默认 0，任一条不合法即整任务失败；设合理阈值（如 100）并旁路落库排查。
- 联系方式在同步与入库阶段即加密，明文不落库、不进日志。

## Consequences

正面：
- 同步链路最短（DataWorks 原生 Writer）、成本低、稳定。
- 本系统与大数据侧职责清晰：数据团队负责同步，本系统负责消费。

负面：
- 依赖数据团队（脚本作者 唐爱玲）交付同步任务，属外部依赖（已在 OPEN-DECISIONS 登记）。
- 每张上游表一个同步节点，节点数随表数增长，需集中管理。
