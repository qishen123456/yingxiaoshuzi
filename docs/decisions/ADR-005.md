# ADR-005: 定时调度采用应用内 cron + PostgreSQL 幂等锁

## Status

Accepted (2026-09-18)

## Background

需要每日一次跑批（T+1）：数据同步校验 → 圈人匹配 → 频控 → 海报生成 → 产出待发送清单 → 下发。约束：用户明确「一天推一次」「不上消息队列集群」，且这是「一个小系统功能」。

候选：

| 候选 | 版本 | 持久化 | 多实例安全 | 运维成本 | 引入新组件 |
|------|------|--------|-----------|----------|-----------|
| 应用内 cron（@nestjs/schedule） | ^6.x（匹配 Nest 11） | 无（靠 DB 幂等） | 靠 PG 咨询锁 | 极低 | 无 |
| BullMQ | ^5.x + Redis | 有 | 原生 | 中 | Redis |
| DataWorks 调度 + 云函数触发 | — | 有 | 原生 | 低 | 无（复用现有） |

## Decision

选择 **`@nestjs/schedule` 应用内 cron 触发 + PostgreSQL 幂等保障**。

幂等设计（关键）：
1. `campaign_task.stat_date` 建 **UNIQUE 约束**，同日重复触发返回已存在任务，不重复跑。
2. 跑批入口获取 **PostgreSQL 咨询锁** `pg_advisory_lock(hashtext('daily_campaign'))`，保证同一时刻只有一个执行体。
3. 定时作业只负责「触发装配」，业务实现下沉到各 service（`jobs/` 目录不含业务逻辑）。
4. 部署为**单实例**；若未来多实例，跑批实例用环境开关隔离，咨询锁作为双保险。

理由：
- 满足「一天一次」「不上消息队列集群」，零新增基础设施。
- 跑批天然幂等，重复触发的代价只是空跑，不产生重复推送。

升级路径：若未来需要「失败重试 / 死信队列 / 并发 worker / 精细限流」，再引入 BullMQ + Redis（届时业务代码结构不变，仅替换触发与执行层）。备选方案 DataWorks 调度 + 云函数触发 HTTP 端点同样可行（外部调度器 + 无状态应用），可在运维侧评估后替换。

## Consequences

正面：
- 无 Redis/队列集群，运维极简。
- 幂等由数据库约束保证，可靠且可验证。

负面：
- 应用内 cron 在进程重启/宕机时会丢失当次触发；补偿手段是「启动时检查当日任务是否完成，未完成则补跑一次」。
- 多实例部署需额外隔离（已在设计中约束）。
