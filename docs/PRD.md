## 0. 产品定义

### 一句话定义
把「标签圈人 → 判断推什么 → 做海报 → 发短信」这条目前全人工线下的营销链路，收敛成一个由「产品包 × 标签」映射规则驱动、T+1 自动生成人群包并带频控与推送记录的小型营销闭环工作台。

### 目标用户
公司**营销管理岗**（总部，配置产品包与映射规则、设定频控）为主用户；**大区 / 营业部**（发起、查看、手动重推）为次用户。

### 核心问题
现状是四段完全人工的流程，问题不在「有没有工具」，而在**规则只存在于人脑**：
1. 圈人靠 Excel 手工筛标签，重复劳动、口径不统一、易错。
2. 「哪类房子推哪个产品包」的判断散在个人经验里，无法沉淀、无法复用、无法审计。
3. 海报一张张手工做，无法个性化、无法规模化。
4. 短信靠平台直接群发，**没有频控**导致扰民被拉黑，**没有记录**导致无法追溯和重推。

**系统要解决的本质问题**：把营销经验固化为**可配置、可预览、可追溯**的规则，让「推谁、推什么、什么时候推、推过没有」四件事从人脑搬到系统里。

## 1. 用户画像与典型场景

### 画像 A：营销管理岗 · 林敏（主用户）
- 总部营销管理，35 岁，业务熟练但**不是技术人员**，日常用 Excel 和后台管理界面。
- 关心的三件事：① 规则配一次以后能不能一直用；② 会不会配错、推错人；③ 推完有没有数据能跟领导交差。
- 痛点：现在每次活动都要重新拉表、重新想「这批房子推哪个产品」，活动一多就乱；去年因为群发太频繁被业主投诉到 12345。
- 技术水平：会 Excel 数据透视表，不会写 SQL，不会用「旅程编排画布」这种专业 MA 工具。

### 画像 B：大区 / 营业部运营 · 阿凯（次用户）
- 大区运营，28 岁，负责落地执行与结果。
- 关心的：① 今天这批推荐是不是合理；② 哪几条没发出去、为什么；③ 重推按钮在哪。
- 痛点：系统显示「已下发」但业主说没收到，无从查证；想对某几户单独重推，只能去求总部或找技术。
- 技术水平：会用企微、短信后台，能看懂表格。

### 场景故事 1：林敏配置「产品包 × 标签」规则（主流程）
> 场景：总部想推「水路维修责任套餐」，主要针对有漏水记录且装修 5 年以上的房子。
>
> 林敏打开「映射规则」页，新建一条规则：
> - 条件：水路标签 命中「卫生间漏水 / 厨房漏水 / 水管老化」**且** 装修状态 ∈「5-10 年 / 10 年及以上」
> - 动作：推荐产品包「水路维修优选包」
> - 优先级：2（数字越小优先级越高）
> - 互斥组：`water_repair_group`（一个房子在水路类只推一个包）
>
> 保存前系统提示：「预计命中 82,340 户（占比 6.5%）」，并提示冲突：「该互斥组内已有『水路紧急抢修包』，其优先级为 1（高于你当前的 2），两者条件重叠 12,410 户；重叠户将命中优先级更高的『水路紧急抢修包』（数字越小优先级越高）。」林敏确认后启用。
>
> 她**不需要写一行代码**，也不需要理解规则引擎原理。

### 场景故事 2：阿凯发起推送并手动重推（执行 + 补救流程）
> 场景：T+1 数据更新后，系统按规则自动生成当日推荐人群包并下发。
>
> 阿凯在「推送记录」页看到今日批次：应发 3,150 条，实际下发 2,980 条，**170 条因频控跳过**（同一房屋 7 天内已推过 / 超出每日上限 / 落在非发送时段）。
> 其中他发现有 20 户属于重点楼盘，明明符合条件却被频控拦下。他勾选这 20 条，点击「手动重推」，系统二次确认（提示「已脱敏频控，本次将强制下发，操作留痕」）后重推，并在记录里生成一条「人工重推」操作轨迹，包含操作人、时间、原因备注。
>
> 全程**可追溯**：谁在什么时间、对哪些房屋、推了什么包、结果如何。

### 2.2 差评洞察（市场空白）

围绕三类高频吐槽，提取设计机会：

| 痛点类别 | 竞品/行业吐槽原文特征 | 市场空白与设计机会 |
|----------|------------------------|--------------------|
| **规则配置太复杂** | 规则冲突无提示、「Rule A 说通过、Rule B 说拒绝，谁也不知道谁赢」；「未经管理的冲突只是把混乱搬进了一个专有 UI」；规则泛滥（rule sprawl）无人清理 | 用**业务语言**（不是画布/表达式）配置规则：优先级用数字直观表达、互斥组用「多选一」话术、保存前**主动冲突检测 + 命中人数预估**。让林敏这种人 5 分钟配完一条规则 |
| **群发扰民被拉黑** | 「天天推会被骂死」；行业基准：普通营销每月 ≤ 2-4 条、同一号码 7 天内 ≤ 2-3 条、单日 ≤ 1 条、22:00-次日 08:00 禁发、连续 3 次无互动应降频 | 频控**必须是一等公民**：同一房屋冷却期、同包冷却期、每日总上限、可发送时段全部可配置，且被频控拦下的记录**可见可追溯**，而不是静默丢弃 |
| **推送无记录不可追溯** | 「必须能证明：联系了谁、为什么、是否同意」；合规要求留存完整触达轨迹 | 推送记录**全字段可查 + 手动重推留痕**；每条跳过/失败都有原因码；重推带操作人、时间、备注 |

### 2.3 我们的差异化

**用户为什么选我们而不是竞品：**

1. **为「房源责任盘」而生的领域模型**——竞品是通用 MA/CDP，我们是「房屋 × 标签 × 产品包」专用闭环。通用平台没有「一个房子一个冷却期」「一个房子一次只推一个水路包」这种语义。
2. **业务人员自助配规则**——不做旅程画布、不做表达式编辑器，做「条件 + 动作 + 优先级 + 互斥组」四件套表单，带冲突检测和命中预估。这是竞品普遍的体验洼地。
3. **频控不是可选项而是 P0**——把用户最痛的一句话「不能天天推，会被骂死了」直接做成产品核心能力，而不是藏在某个高级设置里。
4. **轻量克制**——明确不做 CDP、不做商品中心、不做通道。定位是「一个小系统功能」，2-4 周可上线，不拖 IT 半年。

### 3.3 MVP 范围（P0 = 端到端闭环最小集）

MVP 采用「**闭环必需 + 用户拍板**」双原则，而非机械取 RICE 前 3。理由：本系统的价值在于**端到端跑通**，缺任一环闭环即断。Phase 1 补充「线索联动与效果归因」后，P0 为 **F1-F10 与 F17-F21 共 15 项**：原闭环 9 项（F1-F9）+ 基础效果看板（F10，team-lead 裁决由 P1 升为 P0）+ 新增线索联动与归因 5 项（F17-F21）。其中 F9（AI 海报）虽 RICE 偏低，但为用户明确要求的核心新增能力，列入 P0。

> 注：F16 报表导出 RICE 分高于部分 P1，但因非闭环必需、且可被「列表页直接查看 + 浏览器打印」临时替代，保留在 Backlog。

**P0 功能清单（MVP）：**
1. 产品包管理（业务方维护产品清单）
2. 标签 → 产品包映射规则配置（优先级 + 互斥组 + 冲突校验）
3. 规则命中人数预估预览
4. 标签圈人 / T+1 人群包生成
5. 频控与推送时间窗口配置
6. 数据出口与任务下发（对接公司现有短信/企微通道）
7. 推送记录查询
8. 手动重推（单条 / 按批次）
9. AI 个性化海报生成
10. 效果数据看板（发送量 / 线索量 / 有效线索率 / 分维度质量 / 最近线索时间）
11. 线索回填与关联（T+1 拉取外部线索 + 客户 ID / 手机号关联）
12. 客户最近一次线索时间
13. 线索静默期规则（同产品包长冷却 / 其他产品短冷却，**优先于现有全部频控**）
14. 首触 / 末触双口径归因（归因窗口固定 15 天常量）

**P1 / Backlog：** 规则版本管理、灰度 A-B、审批流、Lookalike、AI 文案、报表导出、**无互动降频 / 暂停（`no_engagement_pause`）**、**分批节流（`batch_throttle`，降级为系统内部自决）**、**点击 / 落地页埋点（依赖短链服务）**、**多模板 / 多文案 A-B 测试**、**短链服务对接与链路追踪**。

## 5. 映射规则模型（产品化描述）

### 5.1 核心模型：产品包 × 标签规则

一条规则的字段：

| 字段 | 说明 | 可配置项 |
|------|------|----------|
| 规则名称 | 业务可读命名，如「水路维修-老装修」 | 文本 |
| 命中条件 | 标签条件组合，支持「并且 / 或者」嵌套（默认根层「并且」） | 标签 + 操作符（∈ / ∉ / ≥ / ≤）+ 值 |
| 推荐产品包 | 命中后要推的产品包（引用产品包实体） | 单选 |
| 优先级 | **数值越小越优先**（priority 升序，**1 为最高优先级**，默认 10，取值 1-999） | 整数 |
| 互斥组 | 同组内只能命中一个包（多选一） | 文本标识 / 下拉选择已有组 |
| 生效范围 | 全局 / 指定大区 / 指定项目 | 多选 |
| 启停状态 | 启用 / 停用 | 开关 |

> **优先级口径（已裁决，全端统一）**：采用 **priority 升序 —— 数值越小优先级越高，1 为最高优先级**。理由：① UI 为「拖动排序列表」，列表第一行即最高优先级，序号从 1 递增，与视觉位置一致；② 架构规则引擎已按「`priority` 最小者优先」实现，无需改动，改动成本最低且无回归；③ 排序列表的通行惯例是「第一行优先」，与数值型评分（分值越高越重要）的惯例不同，此处取前者。**全端（PRD / 架构 / UIUX / 实现）统一按此口径，禁止反向表述。**

### 5.2 冲突消解规则（命中同一房屋时怎么办）

按以下顺序确定性求解，**保证同一输入永远得到同一结果**：

1. **先按互斥组收敛**：同一互斥组内多条规则命中同一房屋时，命中**优先级最高**（即 `priority` 数值最小）的一条；优先级相同时，命中**条件更具体**（条件项更多）的一条；再相同时按**创建时间更早**者胜（稳定兜底）。
2. **组间按策略收敛（已裁决：单包输出，Spec 锁定）**：不同互斥组的规则可以同时命中。系统采用「**单包优先**」策略——按优先级取数值最小的**一个**产品包下发，即**一个房屋在一个推送周期内只输出一个产品包**（对应架构侧实现「互斥组内留 `priority` 最小者 → 全局再取 `priority` 最小者定包」，`mutex_group.mode` 固定 `single`、不预留多包扩展）。多包需求走「一条短信内合并推荐」；变更代价见 5.4 决策留痕。
3. **完全无命中**：进入「未命中池」，不下发，可在记录中查询，用于反向优化规则。
4. **结果留痕**：每次求解记录「命中的规则 ID + 决策顺序」，写入推送记录的 `rule_trace` 字段，可审计。

> 设计依据：行业实践表明「默认求解策略」不足以支撑业务，「必须让业务方定义清晰、互斥、边界明确的规则」。因此系统将「优先级 + 互斥组 + 单包优先 + 决策留痕」作为硬约束，而非可选项。

### 5.3 规则预览（配置体验关键）

保存/启用规则前，系统基于最新 T+1 数据**实时预估**：

- **命中人数**：如「预计命中 82,340 户（占比 6.5%）」。
- **命中分布**：按大区/项目 Top N 展示，帮助判断是否会打爆某区域。
- **冲突预警**：与已启用规则的重叠户数与冲突规则名称、最终优先级裁决结果。
- **频控影响预估**：提示「其中约 X 户受冷却期影响本次不会下发」。
- **空命中预警**：命中 0 户时明确告警，避免配了一条永不生效的规则。

> 交互要求（来自 ERP 行业规范）：表单**失焦校验 + 提交前全量校验**；所有规则的启停、优先级调整在列表中**行内完成**；批量启用/停用用顶部浮动操作栏。

### 5.4 「单包输出」裁决与影响说明（决策留痕）

**已裁决：一个房屋在一个推送周期内，系统只输出一个产品包（单包输出）。**
- 裁决人：team-lead；架构侧已确认，Spec 生成时正式锁定（对应架构假设 A1）。
- 规则模型同步锁定：`mutex_group.mode` **固定为 `single`，不预留多包扩展**。
- 多包需求的产品出口：走「**一条短信内合并推荐多个产品包**」，而非「同一房屋发多条短信」。

> 原为「待用户确认」的假设，现已由 team-lead 裁决锁定。以下影响分析作为决策留痕保留，用于说明「为何维持单包」以及未来若确需改为多包须付出的代价。

**若未来改为「多包输出」，以下四处会受影响：**

1. **规则模型**：需新增「组间叠加策略」配置——可选择「单包优先 / 多包按优先级叠加 / 每组各出一个」。若为「每组各出一个」，则求解结果从「1 个包/房屋」变为「N 个包/房屋（N = 命中的互斥组数）」，需定义叠加数量上限与排序规则。
2. **表结构与数据量**：推送记录主键从「房屋 × 周期」变为「房屋 × 产品包 × 周期」，记录行数与下发任务量成倍增长（最坏情形 = 房屋数 × 平均命中组数），通道配额与全局日上限的消耗模型需重算。
3. **频控**：频次上限的计数口径从「按房屋」变为「按房屋 × 产品包」需重新定义——同一房屋一天收到多个不同产品包的短信，是否违反「单房屋日上限 1」？若不违反，则「不扰民」的核心诉求被削弱；建议对多包场景仍以「房屋」为计数锚点，并将多包合并为**一条**短信或**一个** H5 落地页触达。
4. **AI 海报与触达**：每个房屋需渲染 N 张海报或 1 张组合海报；短信文案需支持多产品包合并表达，海报模板与下发 payload 结构随之变化。

> 结论：变更成本高、且与「不能天天推，会被骂死了」的核心诉求存在张力，**故维持单包输出**。

## 6. 频控与推送时间窗口（P0 核心能力）

> 用户原话：「不能天天推，会被骂死了。」这是**核心功能而非优化项**，直接决定系统是否可用。

### 6.1 频控规格表（P0 硬约束）

> 四个维度必须齐：**冷却期（房屋 / 产品包）**、**频次上限（日 / 周 / 月）**、**可发送时段（支持多时段段）**、**全局日上限**。所有取值以竞品与行业基准为基准（普通营销每月 2-4 条、同一号码 7 天内 2-3 条、单日 ≤1 条、禁发 22:00-次日 08:00）。

| 维度 | 参数（建议字段名） | 默认值 | 取值范围 | 单次任务可否覆盖 | 超出 / 触发后行为 |
|------|--------------------|--------|----------|------------------|-------------------|
| 冷却期 | 同一房屋冷却期 `house_cooldown_days` | **7 天** | 1-30 天 | 可（需授权 + 强制留痕） | 跳过该房屋，原因码 `HOUSE_COOLDOWN`，记录标记「可重推」 |
| 冷却期 | 同一产品包冷却期 `package_cooldown_days` | **30 天** | 1-180 天 | 可（需授权 + 强制留痕） | 跳过，原因码 `PACKAGE_COOLDOWN`，记录标记「可重推」 |
| 频次上限 | 单房屋每日上限 `house_daily_cap` | **1 条/天** | 1-3 条/天 | **不可**（保护体验的硬约束） | 跳过，原因码 `HOUSE_DAILY_CAP` |
| 频次上限 | 单房屋每周上限 `house_weekly_cap` | **2 条/周** | 1-3 条/周 | **不可** | 跳过，原因码 `HOUSE_WEEKLY_CAP` |
| 频次上限 | 单房屋每月上限 `house_monthly_cap` | **4 条/月** | 1-8 条/月 | **不可** | 跳过，原因码 `HOUSE_MONTHLY_CAP` |
| 可发送时段 | 可发送时段段 `send_windows`（**支持多个时段段**，如 10:00-12:00、15:00-18:00） | **10:00-12:00、15:00-18:00（两段）** | 1-N 段，每段须「开始 < 结束」；支持跨天段（如 19:30-21:00）；多段自动合并重叠 | **不可** | 落在窗口外跳过，原因码 `OUT_OF_WINDOW`；未发送项顺延到下一窗口 |
| 可发送时段 | 禁发时段 `blocked_windows`（强制） | **22:00-次日 08:00** | **硬编码，不可配置、不可关闭**（合规要求） | **不可**（含手动重推） | 拒绝下发，原因码 `BLOCKED_WINDOW` |
| 全局日上限 | 全局每日发送上限 `global_daily_cap` | **5,000 条/天** | 100-100,000 条/天；可按渠道 / 大区分别配置 | **不可**（任何单次任务不得突破） | 当日停止剩余下发，未发送项标记 `GLOBAL_CAP_DEFERRED` 顺延次日；若次日仍超限则继续顺延并告警 |
| 其他 | 退订 / 投诉黑名单过滤 `opt_out_filter` | **强制开启** | **不可配置、不可关闭** | **不可**（含手动重推） | 强制跳过，原因码 `OPT_OUT`（退订）/ `BLACKLIST`（投诉黑名单） |

> **P1 频控增强（一期不做，已由 team-lead 裁决降级）**：以下两项**不属于 P0 规格，不出现在 EARS 验收中**：
> - `no_engagement_pause`（无互动降频 / 暂停，原「连续 3 次无互动 → 暂停 30 天」）：进阶防打扰能力。用户明确定位「这是一个小的系统功能」，一期不做，二期视效果数据评估。
> - `batch_throttle`（分批节流，原「每批 500 条 / 间隔 5 分钟」）：它属**通道限流保护，不是业务策略**。暴露给运营只会增加误配面（限流参数配错会导致发送被通道拒绝或压垮通道），故**改由系统内部按 `global_daily_cap` 与通道实际能力自决，不作为用户可见配置项**。

**维度齐备性自检**（对照 team-lead 要求）：
- 冷却期（房屋 / 产品包）：`house_cooldown_days`（7 天）、`package_cooldown_days`（30 天）— 齐备
- 频次上限（日 / 周 / 月）：`house_daily_cap`（1）、`house_weekly_cap`（2）、`house_monthly_cap`（4）— **周维度与月维度均已补全**（原 PRD 缺周、架构缺月，现三者齐备）
- 可发送时段（**支持多个时段段**）：`send_windows` 为 1-N 段列表，默认两段 — **多段能力已明确**
- 全局日上限：`global_daily_cap`（5,000 条/天）— 齐备

### 6.2 频控决策逻辑

- 频控校验**在下发前统一执行**，各条件**取交集（最严格优先）**：任一维度不满足即跳过。
- **原因码优先级顺序（P0 范围）**（多条同时触发时，记录优先级最高的一条，便于归因）：`OPT_OUT` / `BLACKLIST` > `BLOCKED_WINDOW` > **`LEAD_PACKAGE_COOLDOWN`** > **`LEAD_HOUSE_COOLDOWN`** > `OUT_OF_WINDOW` > `HOUSE_MONTHLY_CAP` > `HOUSE_WEEKLY_CAP` > `HOUSE_DAILY_CAP` > `HOUSE_COOLDOWN` > `PACKAGE_COOLDOWN` > `GLOBAL_CAP_DEFERRED`。（`ENGAGEMENT_PAUSED` 随 `no_engagement_pause` 降为 P1，不纳入 P0 原因码。）
- **线索静默期原因码置于全部频次 / 冷却类原因码之前**：即线索静默期**优先于现有全部频控**（规则定义与分级见 §12）。仅合规硬约束（退订 / 黑名单 / 禁发时段）排在它之前。
- **原因码总数 = 13**（11 个既有 + 2 个线索静默期新增）。全量枚举：`OPT_OUT`、`BLACKLIST`、`BLOCKED_WINDOW`、`OUT_OF_WINDOW`、`HOUSE_MONTHLY_CAP`、`HOUSE_WEEKLY_CAP`、`HOUSE_DAILY_CAP`、`HOUSE_COOLDOWN`、`PACKAGE_COOLDOWN`、`GLOBAL_CAP_DEFERRED`、`HOLIDAY_SKIP`（以上 11 个既有）+ `LEAD_PACKAGE_COOLDOWN`、`LEAD_HOUSE_COOLDOWN`（线索静默期新增 2 个）。命名遵循 `{SCOPE}_{LIMIT_TYPE}` 结构；`LEAD_*` 作用域为**客户 / 房源级**，与系统级的 `GLOBAL_CAP_DEFERRED` 明确区分，避免运维误读。
- 被跳过的记录**不静默丢弃**：写入推送记录并携带原因码，可在记录页按原因码筛选。
- **手动重推的覆盖边界**：可覆盖冷却期与频次上限（需二次确认 + 强制留痕，用于重点楼盘等例外），但**退订 / 投诉黑名单（`OPT_OUT` / `BLACKLIST`）、禁发时段（`BLOCKED_WINDOW`）、全局日上限（`GLOBAL_CAP_DEFERRED`）、线索静默期（`LEAD_PACKAGE_COOLDOWN` / `LEAD_HOUSE_COOLDOWN`）五类不可覆盖**（线索静默期为硬约束，一期不提供任何覆盖后门，见 §12.3）。
- 频控配置变更**全量记录审计日志**（操作人 / 时间 / 变更前后值 / 生效范围）。

### 6.3 扩展配置（P1，可选）与频控作用域边界

| 参数 | 默认值 | 说明 | 产品口径 |
|------|--------|------|----------|
| `cross_channel_count` 跨渠道合并计数 | **true（开启）** | 短信 / 企微等渠道的营销触达是否合并计入同一房屋的频次上限 | **默认必须为 true**：频控目的是保护业主体验，若按渠道分别计数，业主可能当日收到「1 条短信 + 1 条企微」= 2 次打扰，违背「不扰民」核心诉求。**计数锚点始终是「房屋」，不是渠道** |
| `day_type` 分日策略 | 工作日 / 周末共用同一 `send_windows` | 工作日与周末可配置不同可发送时段 | 可选。默认同一套；若启用需在 UI 明确展示两套时段，避免歧义 |
| `HOLIDAY_SKIP` 节假日跳过 | **关闭** | 法定节假日不发营销短信 | 可选。默认关闭以保持行为可预期；如开启需接入节假日日历 |

**频控回看口径（已裁决：不设 `lookback_days` 配置项）**：

> 原拟配置项 `lookback_days`（统一回看窗口）**取消**。它是一个「伪配置项」——其存在会诱使实现用一个窗口盖住所有维度，从而必然导致「长冷却期被短窗口覆盖而静默失效」。正确做法是**各维度按自身语义独立查询**，不对用户暴露任何回看窗口参数：

| 维度 | 查询内容 | 查询窗口 |
|------|----------|----------|
| 房屋冷却 | 该房屋对**任意**产品包的最近一次推送时间 | `house_cooldown_days` |
| 产品包冷却 | 该房屋对**该产品包**的最近一次推送时间 | `package_cooldown_days` |
| 日上限 | 该房屋近 1 天推送次数 | 1 天 |
| 周上限 | 该房屋近 7 天推送次数 | 7 天 |
| 月上限 | 该房屋近 30 天推送次数 | 30 天 |

> 各维度各查各的窗口，从结构上杜绝「窗口盖不住冷却期」。内部物理扫描上限只能动态推导为 `max(所有生效冷却期, 30)` + 缓冲，**不得写死、不得对用户暴露**。

**频控作用域边界（重要，需与架构 / 通道方对齐）**：
- 频控**只作用于营销类触达**；**服务 / 通知类消息（验证码、维修进度、缴费提醒、紧急通知等）不计入营销频控，也不被频控拦截**。原因：本场景同一通道既要发营销（产品包推荐）又要发服务（维修进度通知），若把服务通知也纳入频控，业主可能收不到关键服务信息。
- 区分依据：由下发任务的**消息类型标记**判定，架构侧需在任务下发 payload 中携带 `msg_type`；**频控校验入口按 `msg_type` 短路——`notice` 直接放行，仅 `marketing` 进入频控校验**。

## 8. 验收标准（EARS 格式）

> 句式：While / When / If / Where + 系统必须（shall）/ 应该（should）+ 行为。

### 8.1 产品包管理
- **When** 营销管理岗提交一个产品包（名称 + 产品清单 + 描述），**系统必须**创建产品包并允许其被映射规则引用。
- **If** 产品包名称重复，**系统必须**拒绝保存并提示具体冲突项。
- **Where** 产品包已被规则引用时，**系统必须**禁止直接删除，只能停用，并提示被引用的规则列表。

### 8.2 映射规则配置
- **When** 用户保存一条映射规则，**系统必须**校验「命中条件非空 + 已选产品包 + 优先级为整数」三项，缺一不可。
- **When** 用户点击预览，**系统必须**在 5 秒内返回命中人数、占比与大区/项目 Top 分布。
- **If** 新规则与已启用规则在同一互斥组内条件重叠，**系统必须**提示重叠户数、冲突规则名称与最终裁决结果。
- **While** 同一互斥组内多条规则命中同一房屋，**系统必须**只输出优先级最高（`priority` 数值最小）的一条（优先级相同取条件更具体者，再相同取创建更早者）。
- **If** 规则命中 0 户，**系统必须**给出空命中告警。

### 8.3 人群包生成与下发
- **When** T+1 数据就绪，**系统必须**每日自动执行一次「规则求解 → 频控校验 → 生成人群包 → 下发」全链路。
- **When** 求解完成，**系统必须**记录每条房屋命中的规则 ID 与决策顺序（`rule_trace`）。
- **If** 下发通道返回失败，**系统必须**记录失败原因并标记为「可重推」状态。

### 8.4 频控
- **While** 同一房屋在 `house_cooldown_days` 天内已被触达（**任意产品包**），**系统必须**跳过并写入原因码 `HOUSE_COOLDOWN`（按各维度独立窗口校验，不使用统一回看窗口）。
- **While** 同一房屋在 `package_cooldown_days` 天内已被推送**同一产品包**，**系统必须**跳过并写入原因码 `PACKAGE_COOLDOWN`。
- **When** 当日累计发送达到全局每日上限（`global_daily_cap`），**系统必须**停止当日剩余下发，未发送项标记 `deferred`（顺延次日）并写入原因码 `GLOBAL_CAP_DEFERRED`。
- **If** 当前时间落在禁发时段（22:00-次日 08:00），**系统必须**拒绝下发（此规则**不可关闭、手动重推不可绕过**），原因码 `BLOCKED_WINDOW`。
- **If** 房屋命中退订名单或投诉黑名单，**系统必须**强制跳过且**手动重推不得绕过**，原因码分别为 `OPT_OUT` / `BLACKLIST`。
- **If** 下发任务的 `msg_type` 为 `notice`（服务 / 通知类），**系统必须**短路跳过频控校验直接放行，且**不计入**营销频控计数。
- **When** 频控配置被修改，**系统必须**记录变更审计日志（操作人 / 时间 / 变更前后值）。

### 8.5 推送记录与重推
- **When** 任一推送任务执行完毕，**系统必须**生成可查询记录，字段至少含：房屋 ID、项目、产品包、规则来源、下发时间、状态、原因码、操作人。
- **When** 用户对单条或一个批次发起手动重推，**系统必须**二次确认并强制填写/记录操作人、时间与备注，生成独立的「人工重推」轨迹。
- **While** 记录列表展示时，**系统必须**支持按项目、大区、状态、时间范围、原因码筛选。

### 8.6 AI 海报生成
- **When** 人群包生成后，**系统必须**按「模板 + 标签变量」为每个房屋渲染个性化海报（如户型/项目/推荐产品包文案可变）。
- **If** 海报渲染失败，**系统必须**回退到该产品包的通用模板并记录失败日志，不阻断下发。

### 8.7 边界与异常
- **If** T+1 数据缺失或延迟，**系统必须**暂停本次下发并告警，不得使用过期数据生成人群包。
- **Where** 用户仅有本大区数据权限，**系统必须**在列表、预览、记录中隐藏其他大区数据。
- **When** 列表数据为空，**系统必须**展示空状态说明（引导创建产品包 / 配置规则），不得白屏。
- **While** 大批量生成（万级）执行中，**系统必须**展示进度与预计剩余时间，支持后台运行。

- 事件命名 `{对象}_{动作}`（如 `rule_created`, `push_dispatched`）。

## 12. 线索联动与效果归因（Phase 1 补充）

> 本章为 Phase 1 补充需求，追加于原章节之后，不改变前文既有定义；与频控的衔接点见 §6.2 原因码。

### 12.1 业务诉求与设计基线

**业务方原话**：「推完以后我肯定要看效果的，可以关联线索，然后这个系统能看到这个客户最近一次产生线索的时间，如果已经有线索了，在发就不合适了吧，然后也可以看出来每次发送后真实产生线索的质量，是不是需要埋个点呢」。

业务诉求可拆为四问：**推完有没有效果、这个客户最近有没有线索、已经有线索还要不要再推、每次推送带来的线索质量如何**。

**已确认设计基线（team-lead 定，本章按此展开）**：
1. **发送侧不需要「埋点」**：发送时间 / 对象 / 产品包 / 海报版本，本系统自有记录，直接可查。
2. **线索侧需要的是「回填 / 关联」，不是埋点**：线索由外部系统（销售 CRM / 呼叫中心 / 在线表单）产生，本系统 **T+1 拉取并关联**。
3. **关联键**：优先统一客户 ID，退化到手机号（手机号**脱敏存储**）。
4. **新增「线索静默期」规则**，**优先于现有全部频控**：同产品包已有线索 → 该包长冷却（默认 90 天，可配）；其他产品有线索 → 全量短冷却（默认 15 天，可配）；通知类（`msg_type=notice`）是否豁免列入待确认项。
5. **归因**：线索表同时记 `first_touch_push_id` + `last_touch_push_id`，看板同时出**首触 / 末触两个口径**，不押注单一归因。
6. **归因窗口**：一期**全通道统一固定 15 天常量，不可配、不分通道**（team-lead 定稿，覆盖初版「默认 7 天、可配、短信/企微分设」的基线）。

> 基线说明：为何「不埋点、做回填」——本系统是**发送与规则侧**，触点在业主手机（短信 / 企微），系统无法也不应在业主侧植入跟踪手段；因此效果数据只能靠**外部线索回流 + 关联**，而非埋点。这一判断与行业闭环报告（closed-loop reporting）实践一致：把销售侧结果回喂给营销侧，才能知道哪批线索真正成交。

### 12.2 线索数据来源与关联键

> **真实数据源已确认（字段级契约见 `docs/DATA-CONTRACT.md` §4，早期「CRM/呼叫中心未知」表述作废）**：
> 线索来自既有数仓表 **ADB PostgreSQL `yanxuan.ads_yx_clue_full_detail`**（T+1 `TRUNCATE+INSERT` 全量快照，约 180 列），
> 由 DataWorks 新增 **AnalyticDB PostgreSQL Reader → PostgreSQL Writer** 节点每日 02:30 同步，`clue_id` 幂等 upsert。

| 项目 | 说明（以真实资产为准） |
|------|------|
| 数据来源 | **ADB PostgreSQL `yanxuan.ads_yx_clue_full_detail`**（已包含物业联动/朴邻联动/PA自拓/NPS 等全渠道线索，`channel_category_l1` 标源） |
| 获取方式 | **T+1 拉取**（每日 02:30，晚于 02:00 的标签同步），不做实时 |
| 客户主关联键 | **归一化手机号 HMAC-SHA256**（`customer_key`，与 `push_detail.customer_key_hash` 同算法同密钥，ADR-013 一级方案）；统一客户 ID 暂无可用源，降级路径见下行 |
| 房屋关联键 | **双键体系**：pride 房屋码（线索 `house_code` = 标签 `code`）优先；为空时回落战图码（线索 `zhantu_housecode` = 标签 `house_code`）并打 `house_match_type=zhantu_fallback` 标记 |
| 无手机号 | 有 pride 码 → `customer_key_type='house_only'`，仅参与房屋级关联；两者皆无 → `unmatched` 进失败池 |
| 关联目标 | 关联到「房屋 / 客户」实体，进而关联到该实体的历史推送记录（push） |
| 幂等 | 同一线索以 `clue_id`（落库 `lead_id`）幂等去重；重复同步只覆盖外部字段，**不覆盖**归因回填字段 |
| 同步过滤 | 同步层仅排除 `is_test=true`、要求 `is_responsibility=true`；业务有效口径过滤全部下沉指标层（见 §12.4 维修向差异） |
| 关联失败处理 | **不得丢弃**：两码都对不上的线索 `house_id` 置空、进关联失败池并落事件 `lead_link_failed`，支持人工复核与重试 |

**外部依赖与依赖不成立时的风险（重要）**：
- 若 ADB 线索同步**中断或滞后**（`max(synced_at)` 距跑批 > 2 天），闸门 0 按 `lead_gate_fail_mode`（默认 **fail-open**）跳过静默判定但**显著告警**，跑批任务标注「线索静默未生效」，不得静默通过；若配置为 closed 则暂停营销下发。
- 只能依赖手机号关联时，手机号换绑 / 一号多房会带来**关联错误**，进而导致静默期误拦或漏拦、归因失真——故须在看板持续暴露「归因覆盖率」与双键命中分布。
- **降级方案**：无线索数据时，系统仍可完整跑通「圈人 → 规则 → 频控 → 下发 → 记录 → 重推」的发送闭环，仅效果与静默期能力暂缺。

### 12.3 线索静默期规则（分级）

线索静默期是**新增的一类前置拦截规则**，**执行顺序优先于现有全部频控**（§6）。业务名「线索静默期」对应代码 `LEAD_PACKAGE_COOLDOWN`（一级·同包）/ `LEAD_HOUSE_COOLDOWN`（二级·他包），命名遵循 `{SCOPE}_{LIMIT_TYPE}` 结构，作用域为**客户 / 房源级**。

| 级别 | 触发条件 | 冷却口径 | 默认值 | 原因码 |
|------|----------|----------|--------|--------|
| 一级（同包） | 该房屋/客户**对同一产品包**已产生线索 | 该产品包**长冷却** | 90 天（可配，1-365） | `LEAD_PACKAGE_COOLDOWN` |
| 二级（他包） | 该房屋/客户**对其他产品包**已产生线索 | **全量短冷却**（对所有产品包） | 15 天（可配，1-90） | `LEAD_HOUSE_COOLDOWN` |

**规则语义与衔接**：
- **为什么同包更长**：同一产品包已产生线索，说明该需求已在跟进中，再次推送同款产品是对业主的重复打扰，故冷却期最长。
- **为什么他包也拦**：客户已与公司建立线索关系（正在被跟进），此时**任何**营销推送都容易被视为骚扰，故设全量短冷却；待冷却期过后再评估。
- **与现有频控的关系**：线索静默期**前置判定**，与频控「取交集」一致（任一不满足即跳过），但在**原因码记录上优先**——即同时触发时记 `LEAD_*_COOLDOWN`（见 §6.2 优先级链）。
- **与手动重推的关系（硬约束，team-lead 已裁决）**：线索静默期**不可被手动重推覆盖——一期不提供任何覆盖能力，不设二次确认后门**。理由：已有线索仍推属投诉与合规风险，故列为硬约束（与 §6.2 手动重推覆盖边界一致）。
- **通知类豁免**：`msg_type=notice`（维修进度 / 缴费提醒等服务类）**建议豁免**（与 §6.3 频控口径一致），避免业主收不到关键服务信息；**此项为业务决策，保留待确认**（见 R12），不由系统单方设定。
- 线索静默期的判定基准时间 = 该客户**最近一次产生线索的时间**（见 12.5），系统须对该时间可查询、可展示。

### 12.4 线索质量分级定义

| 等级 | 定义 | 行业对应 | 判定信号（示例） |
|------|------|----------|------------------|
| **A（高意向 / 有效）** | 已明确需求并进入实质跟进 | 对标 SQL / SAO | 已预约上门 / 已报价 / 已确认维修或选购需求 |
| **B（意向）** | 主动咨询、表达需求，尚未到预约 | 对标 MQL | 主动留资并咨询、明确表示感兴趣 |
| **C（弱意向 / 待培育）** | 仅留下联系方式，无明确需求 | 对标 Lead（MQL 边缘） | 被动留电、仅填写表单、无互动 |
| **无效** | 不可用或明确拒绝 | Disqualified | 空号 / 停机 / 非本人 / 明确拒绝 / 重复线索 / 骚扰标记 |

**分级执行方（team-lead 已裁决）**：**由本系统翻译**。外部系统只提供原始**阶段字段**，本系统按**固定映射表**翻成 A / B / C / 无效。
- 映射表**写死在代码里、随发布调整，不进界面配置**（与「频控参数不外露」同一原则，避免业务方误配质量口径）。
- 若外部**只提供二值**（有效 / 无效），则一期**只出二分**，A / B / C 明确标注为**二期**——**不做半套**（不出现「有时三级、有时二级」的混乱口径）。
- 无阶段字段时，不用系统内信号硬凑分级；按 §12.9 A4 走降级。

**真实口径翻译表（已对齐公司统一「有效线索」口径，DATA-CONTRACT §4.2，写死代码）**：
源字段：`business_status`（落库 `lead_status`）、`customer_level`（A类客户~E类客户，落库 `lead_grade`）、`intention_type / is_repair / intention_first_type`。

```text
公司统一有效线索口径（装修向）：
intention_type = '自营' AND is_repair = '否' AND intention_first_type <> '家政维修'
AND is_test = false AND business_status NOT IN ('其他','无需求','待清洗')
```

| lead_quality | 判定（自上而下短路） |
|--------------|---------------------|
| **A** | `business_status='已成交'`；或满足有效口径且 `customer_level='A类客户'` |
| **B** | 满足有效口径且等级 ∈ {B类客户, C类客户} |
| **C** | 满足有效口径且等级 ∈ {D类客户, E类客户} 或等级为空 |
| **无效** | `is_test=true`（同步层已排除）或 `business_status ∈ {其他,无需求,待清洗}` |

> **产品包适用口径差异（防误杀，沉默逻辑错误最高危）**：
> - 刷新 / 浴改淋（**装修向**）：严格套用上述口径（`is_repair='否'`、排除家政维修）。
> - **渗漏（维修向）不套用该过滤**：防水补漏线索本身就是维修类，渗漏包的线索量/有效率改取 `is_repair='是'` 且意向命中防水词表（防水/补漏/渗水/漏水等，词表随 GAP-3 盘点固化）；若误套装修口径，渗漏包效果将恒为 0。
> - 线索全量同步、不在同步层做业务过滤；看板必须同时注明两个口径。

**行业口径依据**：
- 分级框架采用通行的营销-销售漏斗阶段划分（Lead → MQL → SAL → SQL → SAO → Customer），其中「有效线索率」= 有效线索（A / B 级）/ 线索量，是衡量营销质量的核心指标。
- 归因与质量回传采用**闭环报告（closed-loop reporting）**思路：把销售侧结果（成交 / 无效 / 原因码）回喂给营销侧，才能判断「哪批推送带来的线索真正有效」，而非只看线索数量。

### 12.5 归因窗口与双口径定义

**归因链路**：推送（push）→ 业主产生线索（lead）→ 线索关联回房屋 → 按归因窗口与口径判定「哪次推送贡献了这条线索」。

| 概念 | 定义 |
|------|------|
| 首触（First-Touch） | 归因窗口内，该客户**最早一次**被推送的记录 → `first_touch_push_id`。回答「谁把客户带进来的」 |
| 末触（Last-Touch） | 归因窗口内，该客户**最近一次**被推送的记录 → `last_touch_push_id`。回答「谁把客户推向转化的」 |
| 归因窗口 | 线索产生时间往前回溯的时间长度；窗口内更早的推送记为 `suppressed`，不参与该线索的归属 |
| 默认窗口（定稿） | **15 天**，一期**固定常量、不可配、不分通道**（team-lead 定稿值） |
| 双口径原则 | **看板同时出首触与末触两个口径，不押注单一归因**（单一口径必然过誉某一类触点：首触过誉认知类、末触过誉临门一脚类） |

**说明**：一期只做首触 + 末触两个**确定性口径**（字段可算、可解释）；多触点加权模型（线性 / 时间衰减 / W 型 / 数据驱动）**不做**（见 §7 O15），因其依赖更长链路与更大数据量，且难以向业务方解释。

**归因窗口与线索冷却期的关系（定稿口径）**：
- 归因窗口（**定稿 15 天，固定常量、不可配、不分通道**）与线索冷却期（短冷却 15 天 / 长冷却 90 天）**相互独立**：前者决定「一条线索算几次推送的功」，后者决定「有线索时要不要继续推」，二者**数值对齐但不同源、不互为约束**。
- 窗口取 15 天是为与短冷却期对齐，避免「线索晚于窗口到达 → 该条线索找不到窗口内的推送 → 未被归因」的空窗，保障归因覆盖率。

**一期口径声明（对外统一口径，业务汇报可直接引用）**：
> 1. 一期的「触达」= **发送成功**，**不是「已查看」**——系统只能确认消息发出去了。
> 2. 因此一期归因是「**发送相关性**」，**不是因果**——不能断言「因为发了这条短信，所以产生了这条线索」。
> 3. 一期**不做点击 / 落地页埋点**，因此**无法区分「发了但没产生线索」与「看了但没留资」**；漏斗只能算「发送量 ↔ 线索量」两端，中间的「查看 / 点击」环节不可见。

### 12.6 效果看板指标清单

| 指标 | 定义 | 维度（可下钻） |
|------|------|----------------|
| 发送量 | 实际下发条数（含成功 / 失败 / 被拦） | 产品包 / 标签 / 海报模板 / 大区 / 项目 / 日期 |
| 线索量 | 归因窗口内关联到的线索数 | 同上 |
| 有效线索率 | 有效线索（A / B 级）/ 线索量 | 同上（**核心质量指标**） |
| 首触线索量 / 末触线索量 | 按首触 / 末触口径分别统计的线索量 | 同上（双口径并列展示） |
| 分产品包 / 分标签 / 分海报模板线索质量 | 各维度下的 发送量 → 线索量 → 有效线索率 漏斗 | 产品包 / 标签 / 海报模板 |
| 客户最近一次线索时间 | 该客户/房屋最近一次产生线索的时间点 | 明细可查（用于静默期判定与人工判断） |
| 线索静默期拦截量 | 因 `LEAD_PACKAGE_COOLDOWN` / `LEAD_HOUSE_COOLDOWN` 跳过的条数 | 原因码 / 产品包 / 日期 |
| 归因覆盖率 | 能关联到 push 的线索 / 总线索 | 整体 / 分来源（用于暴露关联键质量问题） |
| 线索产品包来源分布 | `external` / `inferred` / `none` 三个来源的线索数与占比 | **必须分开统计，不混算准确率**（见 §12.7 `package_source`） |
| 未映射占比（`none`，**须拆两个子口径**） | ① 有码对不上字典（`external_package_code` 非空 → 集成问题）② 无码（`external_package_code` 为空 → 上游缺失） | 分来源 / 日期下钻；**两个子口径分开展示，不得合并成一个数** |

> 看板设计遵循企业级后台规范：**KPI 卡片 + 趋势图 + 占比图 + 排行榜**（来自行业设计规范），并提供高级筛选栏与可导出列表。
> **来源隔离要求**：`lead_package_id` 有三个来源 `external` / `inferred` / `none`，看板凡涉及产品包维度的指标，**必须可区分来源**；`inferred` 与 `none` 的准确性单独看，**不得与 `external` 的数据混在一起算准确率**。
> **两种 `none` 不得合并**：「未映射占比」必须按 `external_package_code` 是否为空拆成「有码对不上字典」与「无码」两个子口径（判定依据见 §12.7 判定链），否则集成问题与上游缺失会被混成一个数、无法定位责任方。
> **指标字段契约（与架构 §15 / openapi 对齐）**：线索计数统一为 `leadCount` —— **批次级** `PushTask.leadCount`、**明细级** `PushDetail.leadCount`；分维度质量接口 `/analytics/lead-quality` 支持 `groupBy ∈ {package, tag, poster_template}`（分别对应上表的「分产品包 / 分标签 / 分海报模板」维度，一一对应）。

| 线索 | `link_status` | string（枚举） | 关联状态：已关联 / 关联失败 / 待复核 |

**`package_source` 判定链（与 ARCHITECTURE §15 逐条对齐，避免两文档各说各的）**：
1. **外部给了包编码**（`external_package_code` 非空）→ 命中本系统产品包字典 = `external`；**未命中** = 保留原始编码、`package_source` 记 `none`（有码对不上字典，属集成问题）。
2. **外部没给包编码**（`external_package_code` 为空）→ 系统按 `first_touch_push_id` 对应推送的产品包推断：推断成功 = `inferred`；推断不出 = `none`（上游缺失）。
3. **两种 `none` 不得合并**：看板「未映射占比」须按 `external_package_code` 是否为空**拆成两个子口径**展示 —— ① 有码对不上字典 ② 无码。

### 12.8 验收标准（EARS 格式，仅本章新增能力）

- **When** T+1 线索数据到达，**系统必须**按「**统一客户 ID → 手机号**」顺序将线索关联到房屋/客户，写入线索表并回填 `first_touch_push_id` 与 `last_touch_push_id`。
- **If** 线索无法关联到任何房屋/客户，**系统必须**写入失败池并落事件 `lead_link_failed`，支持人工复核与重试，**不得静默丢弃**。
- **If** 同一 `lead_id` 被重复拉取，**系统必须**幂等去重，不重复计数、不重复归因。
- **While** 某房屋/客户已产生线索且仍在线索静默期内，**系统必须**在下发前拦截（**优先于现有全部频控**）。
- **If** 命中产品包与已有线索的产品包**相同**，**系统必须**按长冷却（默认 90 天）拦截，原因码 `LEAD_PACKAGE_COOLDOWN`。
- **If** 命中产品包与已有线索的产品包**不同**，**系统必须**按全量短冷却（默认 15 天）拦截，原因码 `LEAD_HOUSE_COOLDOWN`。
- **When** 用户查看某房屋/客户详情，**系统必须**展示「**最近一次产生线索的时间**」。
- **When** 计算归因，**系统必须**按统一的 **15 天固定归因窗口**（一期不可配、不分通道）判定首触与末触，并在看板**并列展示两个口径**。
- **When** `lead_package_id` 缺失而由系统推断得出，**系统必须**写入 `package_source=inferred`，并在看板中与 `external` 来源**分开统计**。
- **When** 线索无法归属到任何产品包，**系统必须**写入 `package_source=none`，并按 `external_package_code` 是否为空**拆成「有码对不上字典」与「无码」两个子口径**分别展示，**不得合并成一个数**。
- **When** 外部仅提供二值有效字段，**系统必须**只输出「有效 / 无效」二分结果，**不得**输出半套 A/B/C 分级。
- **When** 用户打开效果看板，**系统必须**展示发送量、线索量、有效线索率、分产品包 / 标签 / 海报模板的线索质量，以及客户最近一次线索时间。
- **While** `msg_type=notice`（服务 / 通知类），**系统必须**豁免线索静默期拦截（此条为建议口径，待用户确认后固化）。
- **If** 前置确认项未答复（外部线索系统无法提供手机号或统一客户 ID），**系统必须**将线索静默期置为「**未生效**」（不拦截），并将归因**降级为包级宏观相关性**（不做个体归因），同时在看板显著标注降级状态。

### 12.9 假设与前置依赖（前置确认项）

> 以下为**上线前置依赖**，任一不成立都会改变 §12 的能力边界。架构侧已标注为 blocking-external。

| # | 前置确认项 | 若未确认的后果 |
|---|------------|----------------|
| A1 | 外部线索系统**是否提供手机号或统一客户 ID** | 二者皆无 → **关联无法建立** → 线索静默期按「未生效」处理、归因只能做**包级宏观相关性** |
| A2 | 手机号**归一化规则**（如 E.164 / 去空格 / 脱敏前统一）与 **HMAC 密钥**能否双方对齐 | 归一化不一致或密钥不通 → 手机号匹配失败率飙升 → 静默期误拦 / 漏拦、归因覆盖率崩塌 |
| A3 | 线索是否携带**产品包标识**（`lead_package_id`） | **两级处理（已裁决）**：外部给了就用（`package_source=external`）；不给则**本系统按归因结果推断**（取 `first_touch_push_id` 对应推送的产品包，标记 `package_source=inferred`，看板分开统计）；若连归因都不成立，静默期二级分级（90 / 15 天）**退化为单一冷却** |
| A4 | 线索是否携带**状态 / 阶段字段** | **已裁决**：有阶段字段 → 本系统按**固定映射表**（写死在代码、不进界面配置）翻成 A/B/C/无效；**只有二值** → 一期**只出二分**，A/B/C 明确转二期；无字段 → 不用系统内信号硬凑分级 |

**降级口径（A1 未答复时的系统行为）**：
- **闸门 0（线索静默期）按「未生效」处理**——不做拦截，避免因关联不可靠而误拦正常营销。
- **归因降级为「包级宏观相关性」**：只能出「某产品包 / 某批次发送量 ↔ 线索量」的宏观相关性，不做「这条线索归因给哪次推送」的个体归因。
- 发送闭环（圈人 → 规则 → 频控 → 下发 → 记录 → 重推）**不受影响，仍可完整跑通**。

## 13. 附：端到端验证思路（供 Spec 收尾参考）

按「规格即契约」要求，后续 Spec 应内嵌一条可执行端到端验证：**造 3 条互斥/优先级冲突的规则（`priority` 分别为 1/2/3）→ 用含重叠标签的样本房屋求解 → 断言只输出 `priority` 最小（即 1）的产品包 → 触发频控跳过 → 断言记录原因码正确 → 手动重推 → 断言生成人工重推轨迹**。核心成功流 + 关键错误流（空命中 / 频控全拦 / 通道失败）均需覆盖。

**线索联动补充验证**：**灌入一条与某房屋手机号匹配的 T+1 线索 → 断言线索关联成功、`first/last_touch_push_id` 回填正确 → 再次求解该房屋命中同一产品包 → 断言被线索静默期拦截、原因码为 `LEAD_PACKAGE_COOLDOWN` → 看板断言「线索量 / 有效线索率 / 最近线索时间」随之一致**。边界流需覆盖：线索无客户 ID 且手机号不匹配（落 `lead_link_failed`）、重复线索幂等去重、`msg_type=notice` 豁免静默期。

**降级态验证（必含，team-lead 已采纳）**：**在「A1 前置确认项未答复」条件下重跑 —— 断言线索静默期置为「未生效」（不产生 `LEAD_*_COOLDOWN` 拦截）→ 断言归因走「包级宏观相关性」路径（不出个体归因）→ 断言看板显著标注降级状态 → 断言发送闭环（圈人 → 规则 → 频控 → 下发 → 记录 → 重推）仍可完整跑通**。降级路径必须有验收，否则等于未写。
